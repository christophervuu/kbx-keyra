## Summary

Apply the findings from T-02 to update `forge/architecture/mapping-engine.md` so that documented APIs, types, pipeline descriptions, and patterns accurately reflect the implemented mapping engine. Correct stale descriptions, add missing documentation for undocumented behaviors, and annotate intentional Phase 0 simplifications.

---

## Scope

### In Scope

- Correcting public API documentation to match actual exports
- Updating type contract documentation to match actual type definitions
- Correcting pipeline phase descriptions where they have drifted from implementation
- Updating module structure sections to match actual directory layout
- Adding documentation for implemented behaviors that are not currently described
- Annotating intentional simplifications (e.g., XSD stub) explicitly
- Ensuring internal consistency within the document (early sections consistent with later sections)
- Removing or correcting any "(Target Architecture)" labels that are now implemented

### Out of Scope

- Redesigning the document structure
- Adding speculative future architecture
- Changing code to match documentation
- Documenting UI consumption of the engine (that belongs in `ui-application.md`)
- Adding test documentation

## Change Requirements

Based on T-02 findings:

1. **Public API corrections**: Ensure documented exports match actual barrel exports exactly. Add missing exports, remove documented-but-non-existent exports.

2. **Type contract corrections**: Ensure documented type shapes match actual TypeScript definitions. Update field lists, add missing fields, remove phantom fields.

3. **Pipeline corrections**: Ensure validate and execute pipeline descriptions match actual implementation flow. Update phase lists, ordering, and behavior descriptions.

4. **Module structure corrections**: Ensure documented directory/file structure matches reality.

5. **Pattern corrections**: Update descriptions of registry pattern, error handling, null propagation, scope stack, etc. to match actual behavior.

6. **Simplification annotations**: For any area where implementation intentionally simplifies what was planned (e.g., XSD permissive stub), add an explicit annotation like: "Phase 0 simplification: [description]. [What Phase 1 would need if this is expanded]."

7. **Internal consistency pass**: After making individual corrections, read through the full document to ensure sections don't contradict each other (this is a risk with large documents that have been incrementally updated many times).
