## Summary

Add a search/filter input above the tree that filters nodes by field name (case-insensitive substring match), auto-expands ancestor nodes of matches, highlights matching text within field names, debounces input (200–300ms), and displays a result count. Clearing search restores the full tree with the previous expand/collapse state preserved.

---

## Scope

### In Scope

- Search input rendered above the tree (when `searchable` prop is true, which is the default)
- Debounced text input (200–300ms) triggering filter computation
- Case-insensitive substring matching on `fieldName`
- Filter result: only matching nodes and their ancestors are shown
- Auto-expand ancestor paths of all matching nodes
- Highlight matching substring within field names (bold or background color)
- Result count display (e.g., "12 results" or "No matching fields")
- Screen reader announcement of result count (aria-live region)
- "Clear search" button (X icon in input) that restores full tree
- Preserve pre-search expand state and restore it on clear
- Integration with virtualization (T-06) — filtered flat list fed to virtualizer
- Unit tests for filter logic
- Component tests for search interaction

### Out of Scope

- Search by path (only field name for now)
- Search by type or description
- Regex search
- Search result navigation (next/previous) — keyboard nav in T-09 covers tree traversal
- Debounce library (implement with setTimeout/useRef)

## Change Requirements

**Search input component:**
- Text input with placeholder "Search fields..."
- Lucide Search icon on the left
- Clear button (X icon) on the right when input has text
- Controlled input with local state
- Debounce: only trigger filter after 200–300ms of no typing (use `useRef` + `setTimeout`, no external debounce library)
- When `searchable === false`, the search input is not rendered

**Filter logic (`filterTree` or similar):**

Pure function that takes:
- `nodes: SchemaTreeNode[]` — full tree
- `query: string` — search term

Returns:
- `matchingPaths: Set<string>` — paths of nodes that match
- `visiblePaths: Set<string>` — matching paths + all ancestor paths (to show the path to each match)
- `matchCount: number` — total number of matching nodes

The filter should:
1. Traverse all nodes recursively
2. Test each node's `fieldName` for case-insensitive substring match
3. If a node matches, add it and all its ancestors to the visible set
4. Return the sets for use by the tree renderer

**Integration with tree rendering:**

When a search is active:
- The flattened tree list (from T-06's `useFlattenedTree`) should only include nodes whose paths are in `visiblePaths`
- All ancestor paths of matches should be force-expanded (regardless of user's manual expand state)
- Matching nodes have their `fieldName` rendered with the matching substring highlighted (wrap in `<mark>` or a styled `<span>`)

**State preservation:**
- Before applying a search filter, save the current `expandedPaths` set
- While searching, `expandedPaths` is overridden by the filter's ancestor expansion
- On search clear, restore the saved `expandedPaths`

**Result count and accessibility:**
- Display match count below search input or inline (e.g., "12 results")
- If no matches: "No matching fields"
- Use an `aria-live="polite"` region to announce the count to screen readers when it changes

**Performance:**
- For a 23,000-node tree, the filter must complete within 300ms (after debounce)
- The filter traverses the flat node list (or tree recursively) — either approach is acceptable as long as it meets the performance target
- Memoize filter results to avoid recomputation on unrelated re-renders

## Notes

- The filter logic should be a pure function (no React dependency) for easy unit testing and potential Web Worker offloading in the future if needed.
- The debounce implementation is intentionally built-in (no lodash or external library) to stay consistent with Phase 0 minimal-dependency philosophy.
- Text highlighting: use a utility function that splits `fieldName` into segments (before match, match, after match) and wraps the match segment in a highlight element. Handle multiple matches within a single field name if the substring appears more than once.
- This task must be compatible with T-06's virtualization. The filtered flat list is the input to the virtualizer, so the tree correctly renders only visible filtered nodes in the DOM.
