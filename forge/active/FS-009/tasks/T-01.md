## Summary

Define the `SchemaTreeNode` interface, `ParsedSchema` type, `SchemaNodeType` union, and `MappingNodeStatus` type in the shared domain types file (`ui/src/lib/types/domain.ts`), since downstream specs (FS-010–012) also consume them. Define parser function signatures, `SchemaParseError`, `SchemaTreeViewProps`, and any tree-rendering-specific types in the feature module (`ui/src/features/schemas/`). These types form the contract between parsers and the tree view component and must be compatible with the DynamoDB `SchemaNodes` shape (path, fieldName, type, description, depth, isArray, isRequired, parentPath, childCount) so Phase 1 backend-parsed schemas can feed directly into the same tree view.

## Change Requirements

Create the following type definitions:

### In `ui/src/lib/types/domain.ts` (shared domain types)

**`SchemaNodeType`** — union of: `'string' | 'number' | 'boolean' | 'object' | 'array' | 'enum' | 'null' | 'any' | 'union'`

**`MappingNodeStatus`** — union of: `'mapped' | 'unmapped' | 'warning'`

**`SchemaTreeNode` interface** must include:
- `path: string` — dot-notation path (e.g., `"address.street"`)
- `fieldName: string` — leaf field name
- `type: SchemaNodeType` — the field's data type
- `description?: string` — from schema annotations
- `depth: number` — nesting level (0 = root children)
- `isArray: boolean` — whether this is an array type
- `isRequired: boolean` — whether required in parent
- `parentPath: string | null` — parent's path (null for root-level)
- `childCount: number` — direct child count
- `children: SchemaTreeNode[]` — nested children for tree rendering
- `enumValues?: string[]` — for enum types
- `inferred?: boolean` — true if from sample data inference
- `unionTypes?: string[]` — member types for oneOf/anyOf/choice
- `minOccurs?: number` — XSD cardinality
- `maxOccurs?: number | 'unbounded'` — XSD cardinality

**`ParsedSchema` type** must include:
- `nodes: SchemaTreeNode[]` — root-level tree nodes
- `totalFieldCount: number` — total node count across all depths
- `format: SchemaFormat` — the source format that was parsed
- `parseTimeMs: number` — how long parsing took (for performance monitoring)
- `inferred: boolean` — whether this schema was inferred from sample data

### In `ui/src/features/schemas/types.ts` (feature-specific types)

**`SchemaTreeViewProps`** — the component's public API:
- `schema: ParsedSchema`
- `variant: 'source' | 'target'`
- `mappingStatus?: Map<string, MappingNodeStatus>`
- `onSelectNode?: (node: SchemaTreeNode) => void`
- `selectedPath?: string`
- `searchable?: boolean` (default: true)
- `editable?: boolean` (placeholder, default: false)

**`SchemaParseError`** — custom error class with `message`, `format`, and optional `details` field.

**Parser function signatures** (implementations are stubs that throw "not implemented"):
- `parseJsonSchema(content: string | object): ParsedSchema`
- `parseXsd(content: string): ParsedSchema`
- `parseInferredSchema(content: string, format: 'json' | 'xml'): ParsedSchema`

**Tree-rendering-specific types** (as needed for internal component state):
- Expanded node state, virtual row metadata, search state — define as implementation warrants

All types must use TypeScript strict mode conventions (readonly where appropriate for external consumption, but mutable internally for parser construction).

## Notes

- The `children` field on `SchemaTreeNode` is intentionally a mutable array (not `readonly`) because parsers build the tree by pushing children during traversal. Consumer code should treat it as read-only.
- Domain model types (`SchemaTreeNode`, `ParsedSchema`, `SchemaNodeType`, `MappingNodeStatus`) go in `ui/src/lib/types/domain.ts` because they are consumed by multiple feature specs (FS-009 through FS-012).
- Feature-specific types (`SchemaTreeViewProps`, `SchemaParseError`, parser signatures, internal rendering types) go in `ui/src/features/schemas/types.ts`.
- The feature barrel (`ui/src/features/schemas/index.ts`) should re-export the shared domain types for convenience, so consumers can import from either location.
- This task establishes the file/folder structure for the schemas feature module that all subsequent tasks build on.
