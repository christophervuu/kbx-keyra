## Summary

Add full keyboard navigation to the `<SchemaTreeView />` component: arrow keys to navigate between visible nodes, Enter/Space to toggle expand or select, Home/End to jump to first/last visible node, Left/Right arrows for collapse/expand, and proper focus management. Ensure screen reader compatibility with live announcements for search results and correct ARIA state attributes.

---

## Scope

### In Scope

- **Keyboard navigation:**
  - Down Arrow: move focus to next visible node
  - Up Arrow: move focus to previous visible node
  - Right Arrow: if on collapsed expandable node → expand; if already expanded → move to first child
  - Left Arrow: if on expanded node → collapse; if on leaf or collapsed → move to parent
  - Enter / Space: select the focused node (fire `onSelectNode`), or toggle expand if expandable
  - Home: move focus to first visible node
  - End: move focus to last visible node
- **Focus management:**
  - The tree container is focusable (`tabIndex={0}`)
  - One node at a time is the "active descendant" (roving tabindex or `aria-activedescendant`)
  - Focused node is visually distinct from selected node (focus ring vs. background color)
  - When search results update, focus moves to first matching node (or stays in place if current node is still visible)
- **Scroll into view:**
  - When keyboard navigation moves focus to a node outside the viewport, scroll it into view using T-06's `scrollToNode` utility
- **Screen reader announcements:**
  - `aria-activedescendant` points to the currently focused node's ID
  - Search result count announced via `aria-live="polite"` region (from T-07)
  - Expand/collapse state changes announced via `aria-expanded` attribute changes
- **Interaction with virtualization:**
  - Keyboard nav must work correctly with virtualized rendering (focused node may not be in DOM until scrolled to)
  - Use the flat visible node list (from T-06) as the navigation sequence

### Out of Scope

- Type-ahead search (typing letters to jump to matching nodes) — deferred
- Screen reader-specific mode switching
- Touch/mobile gestures
- Custom key bindings beyond the standard tree navigation pattern

## Change Requirements

**Keyboard event handling:**

Create a `useTreeKeyboardNav` hook (or integrate directly) that:
- Attaches a `keydown` handler to the tree container
- Maintains a `focusedIndex` (index into the flat visible node list)
- On arrow keys: compute new index, update `focusedIndex`, call `scrollToNode` if needed
- On Enter/Space: select the focused node (call `onSelectNode`) and/or toggle expand
- On Home: set `focusedIndex` to 0
- On End: set `focusedIndex` to last index
- Prevents default on handled keys (no page scroll on arrow keys)

**Navigation logic:**

```
Down Arrow → focusedIndex + 1 (clamped to list length - 1)
Up Arrow → focusedIndex - 1 (clamped to 0)
Right Arrow:
  - If node is expandable and collapsed → expand it (add to expandedPaths)
  - If node is expandable and expanded → move to first child (focusedIndex + 1)
  - If node is leaf → no action
Left Arrow:
  - If node is expanded → collapse it (remove from expandedPaths)
  - If node is collapsed or leaf → move to parent (find parent in flat list)
Home → focusedIndex = 0
End → focusedIndex = flatList.length - 1
Enter/Space → call onSelectNode(flatList[focusedIndex])
  - If node is expandable, also toggle expand
```

**Focus visualization:**

- Focused node row gets a focus ring (e.g., `ring-2 ring-blue-400 ring-inset`)
- Focus ring is visually distinct from selection highlight (selection = background, focus = ring)
- Both can be active simultaneously (node is both focused and selected)

**ARIA implementation:**

- Tree container: `role="tree"`, `aria-activedescendant={focusedNodeId}`, `tabIndex={0}`
- Each rendered node row: `id={unique-id}`, `role="treeitem"`, `aria-level={depth + 1}`, `aria-expanded` (if expandable), `aria-selected` (if selected), `aria-setsize` and `aria-posinset` for sibling count/position
- Focus: use `aria-activedescendant` pattern (container holds focus, points to active item ID)

**Virtualization compatibility:**

- The focused node might not be in the DOM if scrolled out of view
- When focus moves to a non-rendered node: first scroll it into view (triggering virtualization to render it), then set `aria-activedescendant`
- The `scrollToNode` from T-06 handles this

**Node IDs:**

- Each node row needs a stable, unique DOM ID (e.g., `schema-tree-node-${path.replace(/\./g, '-')}`)
- Used for `aria-activedescendant` reference

## Blockers / Risks

- `aria-activedescendant` referencing a node that isn't in the DOM (due to virtualization) may cause accessibility issues in some screen readers. Mitigation: always scroll to the focused node before updating `aria-activedescendant`, ensuring it's rendered.

## Notes

- The WAI-ARIA Tree View pattern (https://www.w3.org/WAI/ARIA/apg/patterns/treeview/) is the reference for correct keyboard behavior and ARIA attributes. Follow this specification.
- `aria-setsize` and `aria-posinset` are important for screen readers to announce "item 3 of 7" — compute from sibling count at each level.
- The focus index operates on the flat visible node list (same list used by virtualization). This means keyboard nav automatically respects search filters and expand state.
- When search is active and filters the tree, keyboard nav only traverses visible (matching + ancestor) nodes.
- The `Enter` key should both select and toggle expand (if expandable). This dual behavior is standard in tree views.
