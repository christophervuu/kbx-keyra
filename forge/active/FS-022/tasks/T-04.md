## Summary

Add a search/filter input to the RuleList component that allows users to find rules by matching a search string against the rule's target path, expression text, or type. The filter is applied locally with a debounce and displays the number of matching rules.

---

## Scope

### In Scope

- Add a search input to `RuleList.tsx`, positioned below the toolbar row (Add/Paste/Select All) and above the scrollable rule list.
- Filter rules by case-insensitive substring match against `rule.target`, `rule.expression`, and `rule.type`.
- Debounce filtering at 200ms.
- Display match count (e.g., "5 of 20 rules").
- Clear button resets the search.
- When search is active, only matching rules are rendered. The underlying rule data and indices are unchanged.
- Multi-select, CRUD, and reorder continue to work correctly with filtered view (operations use original indices).
- When search is active and no rules match, show "No rules match your search" empty state.
- Update component tests.

### Out of Scope

- Filter chips (like TargetWorklist's Unmapped/Warnings/Required/Arrays). Only a text search.
- Changes to TargetWorklist search.
- Persisting search state across view toggles.

## Change Requirements

**RuleList.tsx:**

Add internal state:
```ts
const [searchQuery, setSearchQuery] = useState('');
const [debouncedQuery, setDebouncedQuery] = useState('');
```

Debounce `searchQuery` into `debouncedQuery` at 200ms (useEffect with setTimeout, or a simple useRef-based debounce).

Compute filtered rule indices:
```ts
const filteredIndices = useMemo(() => {
  if (!debouncedQuery.trim()) return rules.map((_, i) => i);
  const q = debouncedQuery.toLowerCase();
  return rules.reduce<number[]>((acc, rule, i) => {
    if (
      rule.target.toLowerCase().includes(q) ||
      rule.expression.toLowerCase().includes(q) ||
      (rule.type && rule.type.toLowerCase().includes(q))
    ) acc.push(i);
    return acc;
  }, []);
}, [rules, debouncedQuery]);
```

Render search input:
- `<input>` with search icon, placeholder "Search rules...", clear button.
- `data-testid="rule-search"`.
- `data-testid="rule-search-clear"`.

Render match count when search is active:
- `"{filteredIndices.length} of {rules.length} rules"`.
- `data-testid="rule-search-count"`.

In the sortable rule list, only render rows for `filteredIndices`:
- Map over `filteredIndices` instead of the full `rules` array.
- Pass the original rule index to each `SortableRuleRow` (not the filtered position).
- Drag-and-drop reorder uses original indices. When search is active, DnD is disabled (disable `DndContext` or hide grip handles) to avoid confusing index remapping.

Empty state when filtering yields zero results:
- "No rules match your search" with a suggestion to clear the filter.
- `data-testid="rule-search-no-results"`.

**Multi-select interaction:**
- Selection state (`selection` Set) uses original indices.
- "Select All" checkbox when search is active selects all filtered indices (not all rules).
- Bulk actions operate on the selected original indices (unchanged behavior).

## Notes

- Follow the same search UX pattern as TargetWorklist (search icon, input, clear button) for consistency.
- The 200ms debounce is shorter than TargetWorklist's 250ms to make the feedback feel snappier for a flat list (no tree expansion).
- Rule type values are typically short strings like "string", "number", "array". Include them in the match for completeness even though path and expression are more commonly searched.
