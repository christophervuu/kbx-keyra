## Summary

Add a `suggestExpressionHttp()` function to the existing `ui/src/lib/api/ai-api-client.ts` module. This function makes an HTTP POST to the suggest-expression backend endpoint with instruction, target metadata, and source field context, then parses the AI envelope response and returns a typed `SuggestExpressionResult`. Follow the established pattern from `explainRuleHttp()`.

## Change Requirements

### `ai-api-client.ts`

Add to the existing module:

```typescript
export async function suggestExpressionHttp(
  apiUrl: string,
  input: SuggestExpressionInput,
): Promise<SuggestExpressionResult>
```

Implementation requirements:

1. **Request construction:**
   - `POST ${trimTrailingSlash(apiUrl)}/ai/suggest-expression`
   - Headers: `{ 'Content-Type': 'application/json' }`
   - Body: `JSON.stringify({ instruction: input.instruction, targetPath: input.targetPath, targetType: input.targetType, targetDescription: input.targetDescription, sourceContext: input.sourceContext })`
   - Omit undefined/null fields from the body (only include fields that are present in the input)

2. **Timeout:**
   - `AbortController` with 30-second timeout (longer than explain-rule's 15s)
   - Pass `signal` to `fetch`
   - Clear timeout on response

3. **Response handling:**
   - Same AI envelope parsing as `explainRuleHttp` (reuse internal helpers)
   - If `!response.ok`: error message mapped by status code (same `mapHttpStatusToMessage` but with "Suggest" service name)
   - If `result.success === true`:
     - Validate `data` is an object with a `string` `expression` field
     - Return `{ expression: data.expression, explanation: data.explanation }` (explanation optional)
   - If `result.success === false`: throw with code-mapped message

4. **Error handling:**
   - Same pattern as `explainRuleHttp`: AbortError → network message, TypeError → network message, other → re-throw

5. **Error messages** (specific to Suggest):
   - Timeout/network: "Could not reach the Suggest service. Check your connection and try again."
   - 400: "Invalid request — check the instruction and try again."
   - 429: "The AI service is temporarily busy. Please try again in a moment."
   - 500+: "The Suggest service encountered an error. Please try again."
   - Malformed: "Received an unexpected response from the server."

### Refactoring opportunity

Consider extracting shared helper functions (envelope parsing, error mapping) if duplication with `explainRuleHttp` becomes excessive. However, keep the two functions independent if extraction would increase complexity beyond the value gained.

### Test file

Add tests to the existing test file (or create a new describe block):

- Happy path: 200 + `{ success: true, data: { expression: "...", explanation: "..." } }` → returns `SuggestExpressionResult`
- Happy path without explanation: 200 + `{ success: true, data: { expression: "..." } }` → returns with `explanation: undefined`
- Error 400 → throws with "Invalid request" message
- Error 429 → throws with "temporarily busy" message
- Error 500 → throws with "encountered an error" message
- Success false response (AIError envelope) → throws with error message
- Network failure → throws with "Could not reach" message
- Timeout (30s) → throws with "Could not reach" message
- Malformed JSON response → throws with "unexpected response" message
- Data missing `expression` field → throws with "unexpected response" message
- Verify request body includes `sourceContext` when provided
- Verify request body omits `targetDescription` when undefined

## Notes

This follows the exact pattern established by `explainRuleHttp()` in FS-041 T-02. The main differences are:
1. Different endpoint path (`/ai/suggest-expression` vs `/ai/explain-rule`)
2. Richer request body (includes `targetType`, `targetDescription`, `sourceContext` as text string)
3. Longer timeout (30s vs 15s) due to richer prompt context
4. Different response validation (`expression` field instead of `explanation`)
5. Different error messages (service name references "Suggest" not "Explain")
