## Summary

Create the `HttpAdapter` class (`ui/src/lib/api/http-adapter.ts`) implementing `ApiAdapter` with full HTTP-backed CRUD methods for schemas, mappings, mapping versions, and projects. Each method uses the HTTP client utility from T-01 to make requests against the endpoint mapping convention defined in the spec.

---

## Scope

### In Scope

- New file `ui/src/lib/api/http-adapter.ts`
- Class `HttpAdapter implements ApiAdapter`
- Constructor accepting `apiUrl: string`
- All schema CRUD methods (`listSchemas`, `getSchema`, `createSchema`, `updateSchema`, `deleteSchema`)
- All mapping CRUD methods (`listMappings`, `getMapping`, `createMapping`, `updateMapping`, `deleteMapping`, `duplicateMapping`)
- All mapping version methods (`listMappingVersions`, `getMappingVersion`, `saveMappingVersion`)
- All project CRUD methods (`listProjects`, `getProject`, `createProject`, `updateProject`, `deleteProject`)
- Each method calls `httpRequest` with correct HTTP method, path, and body per the endpoint mapping table in the spec

### Out of Scope

- Non-CRUD methods (AI, GitHub, deployment, templates, search, activity, preview) — handled in T-03
- Retry logic
- Caching
- Auth headers

## Change Requirements

After this task:

- `HttpAdapter` class exists and implements `ApiAdapter`
- Constructor stores `apiUrl` (validated non-empty)
- Schema methods map to:
  - `listSchemas()` → GET `/schemas`
  - `getSchema(id)` → GET `/schemas/:id`
  - `createSchema(input)` → POST `/schemas` with body
  - `updateSchema(id, input)` → PUT `/schemas/:id` with body
  - `deleteSchema(id)` → DELETE `/schemas/:id`
- Mapping methods map to:
  - `listMappings(projectId)` → GET `/projects/:projectId/mappings`
  - `getMapping(id)` → GET `/mappings/:id`
  - `createMapping(input)` → POST `/mappings` with body
  - `updateMapping(id, config)` → PUT `/mappings/:id` with body
  - `deleteMapping(id)` → DELETE `/mappings/:id`
  - `duplicateMapping(id, newName)` → POST `/mappings/:id/duplicate` with `{ name: newName }`
- Version methods map to:
  - `listMappingVersions(mappingId)` → GET `/mappings/:mappingId/versions`
  - `getMappingVersion(mappingId, version)` → GET `/mappings/:mappingId/versions/:version`
  - `saveMappingVersion(mappingId, entry)` → POST `/mappings/:mappingId/versions` with body
- Project methods map to:
  - `listProjects()` → GET `/projects`
  - `getProject(id)` → GET `/projects/:id`
  - `createProject(input)` → POST `/projects` with body
  - `updateProject(id, input)` → PUT `/projects/:id` with body
  - `deleteProject(id)` → DELETE `/projects/:id`
- All methods properly type their return values per `ApiAdapter` signatures
- `deleteSchema`, `deleteMapping`, `deleteProject`, `saveMappingVersion` handle void returns correctly (204 with empty envelope or no body)

## Notes

- The HTTP client from T-01 handles envelope parsing and returns `data` directly. `HttpAdapter` methods simply pass through the typed result.
- For void-returning methods (`deleteSchema`/`deleteMapping`/`deleteProject`/`saveMappingVersion`), the HTTP client should support a void/empty response mode (e.g., return `undefined` for 204 responses or when envelope has `data: null`).
- The `httpRequest` function from T-01 may need a generic default or a specific no-body variant. Consider adding an overload or flag (e.g., `expectBody: false`).
- Retry logic is handled transparently by the HTTP client layer — `HttpAdapter` does not need retry awareness.
