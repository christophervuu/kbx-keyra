## Summary

Implement the 3 Mapping Version Lambda handlers (list versions, get version, save version) under `src/lambda/mapping/`. Version entries are stored in DynamoDB with the mapping config snapshot, capped at 50 entries per mapping with oldest-pruning on save.

---

## Scope

### In Scope

- `src/lambda/mapping/list-versions.ts` — GET /mappings/:mappingId/versions
- `src/lambda/mapping/get-version.ts` — GET /mappings/:mappingId/versions/:version
- `src/lambda/mapping/save-version.ts` — POST /mappings/:mappingId/versions
- DynamoDB table design: `MappingVersions` table with `mappingId` (PK) and `version` (SK)
- Sort descending by version for list
- Cap at 50 versions per mapping: on save, if count > 50, delete oldest
- Version entry stores full `MappingVersionEntry` shape (version, savedAt, savedBy, ruleCount, config)

### Out of Scope

- S3 storage for version configs (versions are stored directly in DynamoDB for simplicity — config size is typically < 400KB)
- Automatic version creation on mapping update (versions are explicitly saved by the UI)
- Version diffing

---

## Relevant Areas

- `src/lambda/mapping/` — co-located with mapping handlers
- `src/lambda/shared/` — utilities from T-01
- `ui/src/lib/types/domain.ts` — `MappingVersionEntry` shape

---

## Change Requirements

- `list-versions`: query MappingVersions table by `mappingId`, sort descending by `version` SK, return `MappingVersionEntry[]`
- `get-version`: get item by `mappingId` + `version` composite key, return `MappingVersionEntry` or 404
- `save-version`: validate required fields (`version`, `savedAt`, `savedBy`, `ruleCount`, `config`), write item to DynamoDB, then query count for this mappingId — if > 50, delete items with lowest version numbers to bring count to 50, return 204
- Path parameters: `mappingId` from `/mappings/:mappingId/versions`, `version` (numeric) from `/mappings/:mappingId/versions/:version`

## Blockers / Risks

- DynamoDB 400KB item size limit could be hit for very large mapping configs stored inline. For Phase 1, this is acceptable given typical mapping sizes (< 100KB). If a config exceeds 400KB, the handler should store config in S3 and reference it — but this is an edge case optimization that can be deferred.

---

## Notes

- The `MappingVersionEntry` includes a full `MappingConfig` embedded in the `config` field. This is a snapshot — it should be the complete config as it existed at save time.
- The UI's `saveMappingVersion` is fire-and-forget (does not use the response). The 204 response is intentional.
- Version number is provided by the client in the request body (matches the UI's current behavior of including `version` in the entry). The handler does not auto-generate version numbers for history entries.
