## Summary

Implement the two public entry points of the mapping engine — `validate()` and `execute()` — as stub functions with correct type signatures that return empty/placeholder results. These are the functions callers (UI and Lambda) will import and use. The stubs establish the API contract without implementing any transformation logic.

---

## Scope

### In Scope

- `validate(config: MappingConfig, sourceSchema: unknown, targetSchema: unknown, options?: EngineOptions): ValidationResult`
  - Returns `{ valid: true, diagnostics: [] }` (placeholder)
  
- `execute(config: MappingConfig, sourceData: unknown, sourceSchema: unknown, targetSchema: unknown, options?: EngineOptions): ExecutionResult`
  - Returns `{ output: {}, diagnostics: [], trace: undefined }` (placeholder)
  - If `options.trace` is true, returns `trace: []` instead of `undefined`

- Both functions exported from `src/engine/index.ts` as named exports
- JSDoc comments on both functions documenting their purpose, parameters, and return values
- The functions are pure (no side effects, no I/O) even as stubs

### Out of Scope

- Any actual validation logic (DSL parsing, path checking, type checking)
- Any actual execution logic (expression evaluation, rule application)
- Unmapped target handling
- Schema resolution or parsing

## Notes

- The `sourceSchema` and `targetSchema` parameters are typed as `unknown` for now because schema parsing (JSON Schema / XSD → internal tree) is a future spec. The engine will eventually define a `ParsedSchema` type.
- The `sourceData` parameter is also `unknown` — it's the raw JSON data the rules transform.
- The project structure doc references `parse()` as a third export. For this scaffold spec, `parse()` is excluded since DSL parsing is explicitly out of scope. It will be added in the parser spec. Only `validate()` and `execute()` are implemented as stubs.
- Ensure the `src/engine/index.ts` barrel export is clean and well-organized (types first, then functions).
