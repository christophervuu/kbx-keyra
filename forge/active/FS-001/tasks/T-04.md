## Summary

Implement the extensible function registry where DSL functions will be registered. The registry maps function names to their signature and implementation. No actual DSL functions are registered yet — only the registration mechanism and lookup API exist.

---

## Scope

### In Scope

- `src/engine/registry/function-registry.ts` — the registry implementation
- Registry API:
  - `registerFunction(name: string, signature: FunctionSignature, implementation: FunctionImplementation): void` — register a function. Throws if name is already registered (prevents silent overwrites).
  - `getFunction(name: string): RegisteredFunction | undefined` — look up a registered function by name
  - `hasFunction(name: string): boolean` — check if a function is registered
  - `listFunctions(): string[]` — return all registered function names
  - `createRegistry(): FunctionRegistry` — factory that creates a fresh registry instance (allows isolated registries for testing)
- A default registry instance exported for convenience
- The registry should be a class or a closure-based module — not a bare mutable global

### Out of Scope

- Registering any actual DSL functions (source, concat, map, etc.)
- Function execution logic
- Argument validation against signatures
- Type checking of arguments at registration time

## Change Requirements

After this task completes:

- A `FunctionRegistry` class or factory exists in `src/engine/registry/`
- The registry stores registered functions in a name-keyed map
- `registerFunction()` adds a function to the registry
- `registerFunction()` throws a descriptive error if the function name is already registered
- `getFunction()` returns the registered function entry or `undefined`
- `hasFunction()` returns a boolean
- `listFunctions()` returns an array of registered function name strings
- `createRegistry()` produces independent registry instances
- A default (singleton) registry instance is exported for production use
- All registry API is exported from `src/engine/index.ts`

## Verification Requirements

- `npm run typecheck` passes
- `npm run lint` passes
- Unit tests verify:
  - Registering a function makes it retrievable via `getFunction()`
  - `hasFunction()` returns `false` before registration and `true` after
  - `listFunctions()` returns registered names
  - Duplicate registration throws an error
  - `createRegistry()` produces isolated instances (registering in one does not affect another)

## Acceptance Checks

- `registerFunction("testFn", signature, impl)` succeeds
- `hasFunction("testFn")` returns `true` after registration
- `hasFunction("unknown")` returns `false`
- `getFunction("testFn")` returns `{ name: "testFn", signature, implementation }`
- `getFunction("unknown")` returns `undefined`
- `listFunctions()` includes `"testFn"` after registration
- Calling `registerFunction("testFn", ...)` a second time throws
- Two registries from `createRegistry()` are independent
- `npm run typecheck` exits 0
- `npm run lint` exits 0

## Notes

- The registry pattern should support future needs: signature-based argument validation, function metadata for AI prompt generation, and function categorization. Keep the data model extensible but don't implement these features now.
- Use a `Map<string, RegisteredFunction>` internally for O(1) lookup.
- The default registry export enables a convenient import pattern: `import { registerFunction, getFunction } from '@keyra/engine'` while `createRegistry()` enables isolated testing.
- Function names are case-sensitive per the DSL spec (§2.2) — the registry should respect this.
