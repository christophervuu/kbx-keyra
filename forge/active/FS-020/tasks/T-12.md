## Summary

Integrate the existing `RuleList` component as a toggleable "Rules View" within the new layout. When the user toggles to Rules View via the Global Toolbar, the center column switches from the Target Worklist to the traditional rules list, and the right panel shows the expression builder for the selected rule. All existing rule CRUD, reorder, bulk actions, and diagnostics functionality must remain fully accessible.

---

## Scope

### In Scope

- Rules View toggle integration: when "Rules View" is active in Global Toolbar, center column renders `RuleList` instead of `TargetWorklist`
- Right panel in Rules View: renders `ExpressionBuilderPanel` for the selected rule (existing Panel 4 behavior)
- All existing `RuleList` functionality preserved: CRUD, reorder, bulk selection, diagnostics inline
- Toggling back to "Target View" restores the Target Worklist center column
- **Selection persistence across view toggles:**
  - Target View → Rules View: the rule corresponding to the currently selected target field is highlighted/scrolled-to in the rules list
  - Rules View → Target View: the previously selected target field remains selected and the right panel restores its builder context
  - Edge case: if a rule selected in Rules View targets an array/object path (not a single scalar), switching to Target View selects the array/object node that best represents that rule's target path

### Out of Scope

- Modifying `RuleList` component internals
- Adding new features to Rules View
- Modifying `ExpressionBuilderPanel` internals
- Making Rules View the default (it is explicitly secondary)

## Change Requirements

After this task is complete:

- View toggle in Global Toolbar (T-04) controls which component renders in the center column
- When `view === 'rules'`: center column renders `RuleList` with all existing props/callbacks
- When `view === 'rules'`: right panel renders `ExpressionBuilderPanel` (existing expression editing UX)
- When `view === 'target'` (default): center column renders `TargetWorklist`, right panel renders node-type-specific builders
- The composition-level state tracks `currentView: 'target' | 'rules'` and conditionally renders
- Rule selection in Rules View uses existing `selectedRuleIndex` pattern
- **Selection persistence:**
  - Composition state preserves both `selectedTargetPath` and `selectedRuleIndex` independently
  - When switching to Rules View with a target selected: find the rule whose target path matches `selectedTargetPath`, set `selectedRuleIndex` to that rule's index, scroll it into view
  - When switching back to Target View with a rule selected: resolve `selectedRuleIndex` rule's target path, set `selectedTargetPath` to that path
  - If no matching rule/field found during switch, selection clears gracefully (no error)
- No functionality regression in Rules View — all Panel 3 + Panel 4 behaviors preserved

## Notes

- This task ensures power users retain full access to the rules-centric workflow they may prefer for bulk operations, debugging, or complex rule reordering.
- The toggle is intentionally simple — it swaps center + right panel content based on a single state variable.
- Selection persistence logic: The composition layer maintains a bidirectional lookup between target paths and rule indices. When rules are ordered, the lookup uses the rule's `targetPath` property to bridge views.
