## Summary

Update backend and persistence contracts so Schema Detail can consume canonical review/readiness and sample-payload metadata. This task establishes data model fields and API payload shape needed by later UI tasks.

---

## Scope

### In Scope

- Add/normalize schema metadata fields required by FS-090 (`reviewState`, review timestamps, readiness compatibility).
- Add schema sample payload metadata model and storage reference fields.
- Ensure schema detail/get/list responses expose required metadata in canonical shape.
- Preserve compatibility aliases where needed without regressing FS-089 contracts.

### Out of Scope

- Full UI rendering changes.
- Sample diff computation behavior.

---

## Relevant Areas

- `src/lib/persistence/types.ts`
- `src/lib/persistence/schema-metadata.ts`
- `src/lambda/schema/get-schema.ts`
- `src/lambda/schema/list-schemas.ts`
- `src/lambda/schema/create-schema.ts`
- `src/lambda/schema/*` (schema update helpers)

---

## Change Requirements

- Canonical schema payload includes review/readiness fields needed for inferred review workflow.
- Schema sample payload entity shape supports: sample identity, format, createdAt, source (`initial_upload|added_sample`), usedForInference, and content reference.
- Existing consumers remain backward compatible where feasible.

---

## Verification Requirements

- Add/update backend unit tests for schema metadata serialization/deserialization.
- Add tests proving inferred-create path stores initial sample metadata.
- Run backend lint/typecheck/tests for touched modules.

---

## Acceptance Checks

- Schema API responses expose canonical fields required by FS-090 without breaking existing baseline metadata.
- Initial inferred schema creation persists one sample payload record marked `usedForInference=true`.
- Backend lint/typecheck/test checks pass for touched areas.

---

## Blockers / Risks

- Existing storage schema may require migration handling for missing fields.
