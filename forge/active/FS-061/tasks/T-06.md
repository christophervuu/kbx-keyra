## Summary

Write integration tests that verify the system returns structured errors (not partial/empty successes) when DynamoDB records reference S3 objects that do not exist. This validates the failure mode for orphaned records — a critical persistence consistency scenario.

---

## Scope

### In Scope

- Integration tests for orphaned mapping config (DynamoDB record exists, S3 config missing)
- Integration tests for orphaned mapping version (DynamoDB version entry exists, S3 version snapshot missing)
- Integration tests for orphaned schema content (DynamoDB metadata exists, S3 content missing)
- Assertion on error response structure (matches error envelope standard)
- Verification that raw AWS SDK errors are NOT exposed to callers

### Out of Scope

- Orphan prevention/cleanup mechanisms (future spec)
- Orphaned DynamoDB records with no S3 reference at all (just missing data)
- Performance of error paths
- Multi-entity cascade failures

## Change Requirements

- Create `tests/lambda/integration/persistence/error-modes.test.ts`
- Test cases:
  1. **Orphaned mapping config**: Insert a mapping DynamoDB record with `configS3Key` pointing to a non-existent S3 object. Call the get operation. Assert: returns HTTP 500 with error code `CONTENT_UNAVAILABLE` — NOT a partial response with empty/null config.
  2. **Orphaned version snapshot**: Insert a MappingVersions DynamoDB record with `configS3Key` pointing to a non-existent S3 object. Call version get. Assert: HTTP 500 + `CONTENT_UNAVAILABLE`, not partial data.
  3. **Orphaned schema content**: Insert SchemaMetadata record. Do NOT write S3 content. Call schema detail retrieval (metadata + content). Assert: HTTP 500 + `CONTENT_UNAVAILABLE` indicating storage inconsistency.
  4. **Error structure validation**: For each error case above, verify the error includes:
     - Error code `CONTENT_UNAVAILABLE` (not raw `NoSuchKey` from AWS SDK)
     - HTTP status 500
     - A human-readable message indicating storage inconsistency
     - No stack traces or internal AWS details exposed
  5. **Non-orphan baseline**: For each entity type, create properly (DynamoDB + S3). Verify normal get succeeds — proving the error tests aren't false positives due to setup issues.
- If the persistence module currently returns `undefined`/`null` for missing S3 content instead of throwing, implement the `CONTENT_UNAVAILABLE` error behavior as part of this task

## Verification Requirements

- Error responses return HTTP 500 with code `CONTENT_UNAVAILABLE`
- No raw `NoSuchKey`, `AccessDenied`, or SDK error messages leak to callers
- Non-orphan baseline tests pass (proving the harness works correctly)
- Each orphan scenario is independently testable
- If fixes to persistence module error handling are required, they maintain backward compatibility

## Notes

- **Decided (Q1 resolved)**: Orphaned S3 references return HTTP 500 with error code `CONTENT_UNAVAILABLE`. Rationale: the entity exists but backing storage is inconsistent — this is a server-side integrity problem, not a user-facing "not found".
- To create an orphaned record, directly insert into DynamoDB (bypassing the normal create flow that would also write S3). The harness helpers should support direct DynamoDB put for this purpose.
- This task validates a defensive boundary: the system should never return "successful" responses with incomplete data. Users must be able to distinguish "entity exists with full data" from "entity record exists but storage is inconsistent".
- If `src/lambda/shared/errors.ts` does not already have a `CONTENT_UNAVAILABLE` error code, add it as part of this task (alongside `RESOURCE_NOT_FOUND`, `INTERNAL_ERROR`, etc.).
