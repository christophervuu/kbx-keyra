## Summary

Create the integration test infrastructure that simulates cross-session persistence scenarios at two layers: (1) persistence module level for correctness and edge cases, and (2) full-stack HttpAdapter → HTTP → Lambda → DynamoDB/S3 for real adapter behavior. This includes DynamoDB Local table creation utilities, LocalStack S3 bucket setup, fresh-instance factory functions that create isolated persistence module instances (simulating a "new session" with no shared in-memory state), and test lifecycle helpers for setup/teardown.

---

## Scope

### In Scope

- Test utility module at `tests/lambda/integration/persistence/helpers/`
- DynamoDB Local table creation scripts for all 5 tables (Projects, Mappings, SchemaMetadata, SchemaNodes, MappingVersions)
- LocalStack S3 bucket creation utility
- "Fresh session" factory: creates a new persistence module instance with no shared DynamoDB/S3 client singleton state
- Full-stack test helper: utility to invoke Lambda handlers directly (simulating API Gateway events) for full-stack layer tests
- Test lifecycle: `beforeAll` (create tables/bucket), `afterEach` (clean inserted items), `afterAll` (delete tables/bucket)
- Jest/Vitest configuration for integration test suite
- Environment variable setup for local endpoints

### Out of Scope

- Actual persistence round-trip assertions (T-02 through T-04)
- HttpAdapter audit (T-05)
- Error mode tests (T-06)
- Production infrastructure or CloudFormation

## Change Requirements

- Create `tests/lambda/integration/persistence/helpers/setup.ts` that exports:
  - `createTables()` — creates all 5 DynamoDB tables with correct key schemas and GSIs against DynamoDB Local
  - `deleteTables()` — tears down tables
  - `createBucket()` — creates the S3 bucket in LocalStack
  - `deleteBucket()` — removes the bucket and all objects
- Create `tests/lambda/integration/persistence/helpers/session.ts` that exports:
  - `createFreshSession()` — returns a complete set of persistence module operations (projects, mappings, schemaMetadata, schemaNodes, mappingVersions, S3 helpers) using freshly constructed clients that share NO in-memory state with prior calls
  - This simulates a "new Lambda cold start" or "new browser session" from the persistence layer's perspective
- Create `tests/lambda/integration/persistence/helpers/fixtures.ts` that exports:
  - Sample project, mapping, schema, and version data conforming to persistence module input types
  - Deterministic IDs for cross-test reference (using UUID-format constants)
- Create `tests/lambda/integration/persistence/helpers/cleanup.ts` that exports:
  - `cleanTable(tableName)` — scans and deletes all items
  - `cleanBucket(bucket)` — lists and deletes all objects
- Environment: tests must set `DYNAMODB_ENDPOINT=http://localhost:8000` and `S3_ENDPOINT=http://localhost:4566`
- Table schemas must exactly match `persistence-model.md` Section 2 (key structures + GSIs)

---

## Verification Requirements

- The harness itself must be validated with a smoke test:
  - `createTables()` succeeds without error
  - `createFreshSession()` returns a valid object with all expected methods
  - A simple put + get through the fresh session succeeds
  - `cleanTable()` removes all items
  - `deleteTables()` succeeds
- Environment variables correctly route to local endpoints
- Two successive `createFreshSession()` calls return independent instances (write in one, not visible in the other's in-memory state — though DynamoDB writes are of course shared)

## Blockers / Risks

- DynamoDB Local must be running on port 8000 during test execution
- LocalStack must be running on port 4566 during test execution
- If `src/lib/persistence/clients.ts` uses true module-level singletons (not resettable), the fresh-session factory may need to use dynamic imports or module re-evaluation — assess and document the approach

---

## Notes

- Reference `src/lib/persistence/config.ts` for table names and `src/lib/persistence/types.ts` for item shapes.
- The "fresh session" pattern must avoid Node.js module caching effects. Consider using `jest.isolateModules()` or separate client construction with explicit endpoint config.
- This harness is consumed by T-02, T-03, T-04, and T-06.
