## Summary

Extend existing value-table persistence into canonical scoped value-map storage with immutable global revisions, project link/overlay records, stable row IDs, and migration of existing project maps to `scope: project` defaults.

---

## Scope

### In Scope

- Persistence schema/model extensions for global maps, revisions, links, overlays, and usage counters.
- Stable row ID backfill/migration strategy.
- Migration scripts/utilities for existing project value tables/maps and existing mapping references.
- Backward-compatible read/write adapters across migration window.

### Out of Scope

- API route behavior implementation.
- UI changes.

---

## Relevant Areas

- `src/lib/persistence/types.ts`
- `src/lib/persistence/value-tables.ts` (or successor module)
- `src/lib/persistence/config.ts`
- `src/lib/persistence/index.ts`
- `tests/lib/persistence/**/*`
- migration utilities under `scripts/` or `src/lib/persistence/`

---

## Change Requirements

- Reuse canonical persistence strategy already in place (Dynamo metadata + S3 revision rows abstraction as applicable).
- Extend existing value-table asset and immutable revision model with scope/ownership/status/revision metadata.
- Do not introduce parallel global-map asset tables.
- Add project-link and overlay entities under one canonical `ValueMapService`/repository abstraction.
- Do not introduce arbitrary split by payload size.
- Retain existing physical resource names and `/value-tables` compatibility aliases during transition.
- Persist project overlay as operations, not full inherited row copies.
- Ensure migrated maps default to exact match and preserve current fallback behavior.

---

## Verification Requirements

- Persistence tests for create/read/update of global revisions and project links/overlays.
- Migration tests proving before/after fixture equivalence.
- Tests that stable row IDs persist across revisions and migration boundaries.

---

## Acceptance Checks

- Existing project maps migrate without behavior change.
- Scoped/global/link/overlay records persist and reload deterministically.
- Storage/resource naming compatibility is preserved without big-bang rename.
- Migration is idempotent and safe to rerun.

---

## Blockers / Risks

- Risk: row ID backfill mistakes breaking overlay reference stability.

---

## Notes

- Keep compatibility aliases where needed to avoid immediate UI/API breakage.
