## Summary

Define the canonical domain model for scoped value maps, immutable global revisions, project links, overlays, effective-row provenance, and update/orphan states so downstream engine/backend/UI work shares one contract.

---

## Scope

### In Scope

- `ValueMapScope`, `ValueMapMatchMode`, global metadata, revision, row, link, overlay, and effective-map contract definitions.
- Stable row identity requirements (`rowId`) and orphan semantics.
- Transition/state definitions for inherited/customized/project-only/update-available.

### Out of Scope

- Engine function implementation.
- API endpoint implementation.
- UI component changes.

## Change Requirements

- Produce explicit cross-document domain contracts for:
  - global map metadata and immutable revisions,
  - project link + overlay representation,
  - effective resolution order and provenance,
  - orphaned overlay detection and resolution states.
- Standardize user-facing/public-domain terminology as **Value Mapping**.
- Define preferred `/value-maps` API contracts and `/value-tables` compatibility aliases through one canonical service contract.
- Ensure compatibility with existing FS-096 `valueTableRef.resolvedEntries` deterministic runtime model.

---

## Verification Requirements

- Cross-check contract consistency across spec and architecture docs.
- Confirm no contradiction with existing deployment/runtime no-live-fetch invariants.

---

## Acceptance Checks

- Domain contracts are documented with deterministic field semantics.
- Row identity and orphan handling rules are explicit and testable.
- Preferred and compatibility route terminology/contracts are consistent and non-conflicting.
- Downstream tasks can reference these contracts without ambiguity.
