## Summary

Implement global library API endpoints for create/list/get/revision/archive/usage flows with immutable revision semantics and usage visibility across projects and mappings.

---

## Scope

### In Scope

- Global map routes and handlers.
- Request/response validation and error envelope behavior.
- Usage aggregation endpoint.
- Archive behavior rules (no hard delete when referenced).

### Out of Scope

- Project linking and overlay endpoints.
- UI integration.

---

## Relevant Areas

- `src/lambda/project/*` or new global value-map handler modules
- route wiring in `template.yaml` and lambda index barrels
- `src/lib/persistence/*`
- `tests/lambda/**/*`

---

## Change Requirements

- Add behaviorally equivalent routes to required global surface:
  - `POST /value-maps`
  - `GET /value-maps`
  - `GET /value-maps/:id`
  - `POST /value-maps/:id/revisions`
  - `GET /value-maps/:id/revisions`
  - `GET /value-maps/:id/revisions/:revision`
  - `POST /value-maps/:id/archive`
  - `GET /value-maps/:id/usage`
- Keep `/value-tables` route aliases for compatibility and route both through one canonical service implementation.
- Ensure revision creation is append-only and prior revisions remain immutable.

---

## Verification Requirements

- Handler tests for success, validation errors, and conflict cases.
- Tests for archive restrictions and usage payload integrity.

---

## Acceptance Checks

- Global API supports immutable revision lifecycle.
- Usage endpoint reports linked projects and mapping references.
- Preferred `/value-maps` and compatibility `/value-tables` surfaces are behaviorally consistent.
- Archived maps cannot be newly linked (enforced in linking task/API).

---

## Blockers / Risks

- Risk: route overlap with existing `/value-tables` semantics during migration window.

---

- Maintain adapter parity expectations for local/http clients.
