## Summary

Extend `useAsyncState` with a `retry` action that re-executes the last operation without requiring callers to manage their own promise factory reference. This enables UI components to offer a "Retry" button that transparently re-invokes the failed operation.

---

## Scope

### In Scope

- Add `retry` to `AsyncActions<T>` interface
- Store the last promise factory in a ref so `retry()` can re-invoke it
- `retry()` should only work when state is `error` and `retryable: true`; no-op otherwise
- Ensure race protection (requestIdRef) applies to retry attempts
- Ensure unmount safety (no state updates after unmount)
- Unit tests for the new retry action

### Out of Scope

- ErrorBanner component (separate task)
- Feature hook changes (they will consume this automatically via the hook interface)
- Modifying AsyncState type itself

---

## Relevant Areas

- `ui/src/hooks/use-async-state.ts` — main change
- `ui/src/lib/state/async-state.ts` — type reference (no changes)

---

## Change Requirements

- `AsyncActions<T>` gains: `retry: () => void`
- Internal implementation:
  1. Store the most recent promise factory (the function passed to `execute` or `refresh`) in a `lastOperationRef`
  2. `retry()` checks: if current state is `error` with `retryable: true` AND `lastOperationRef.current` exists, re-invoke via `execute(lastOperationRef.current())`
  3. If state is not `error` or not retryable, `retry()` is a no-op
- The `execute` and `refresh` signatures must be updated to accept a factory function `() => Promise<T>` in addition to (or instead of) a raw `Promise<T>` — OR the hook internally wraps to store the factory. Preferred: overload or accept factory.
- Backward compatibility: existing callers passing `Promise<T>` directly must continue to work. In that case, `retry` is unavailable (no factory to re-invoke).

**Design decision:** Change `execute` signature to accept `(() => Promise<T>) | Promise<T>`. When a factory is provided, store it and enable retry. When a raw promise is provided, existing behavior is preserved but retry is unavailable.

---

## Verification Requirements

- Unit test: `execute(factory)` → error with retryable → `retry()` → success
- Unit test: `execute(factory)` → error with non-retryable → `retry()` is no-op
- Unit test: `execute(rawPromise)` → error → `retry()` is no-op (no factory stored)
- Unit test: `retry()` when state is `success` → no-op
- Unit test: race protection — `retry()` followed by another `execute()` → only latest completes
- Unit test: backward compatibility — existing usage with raw promises still works identically
- `pnpm typecheck` passes in `ui/`

---

## Acceptance Checks

- `AsyncActions<T>` includes `retry` in its type signature
- `retry()` re-executes last operation when state is `error` and retryable
- `retry()` is no-op when state is not error or error is non-retryable
- Existing callers of `useAsyncState` continue to work without changes
- Race protection works correctly with retry
- TypeScript strict mode clean

---

## Blockers / Risks

- Signature change to `execute` must be backward-compatible. Using a union type `(() => Promise<T>) | Promise<T>` with runtime type check should preserve all existing call sites.

---

## Notes

- An alternative design is to always require factories and deprecate raw promise passing. However, for backward compatibility in this increment, the union approach is safer.
- Feature hooks that want retry support should migrate to passing factories: `execute(() => adapter.listProjects())` instead of `execute(adapter.listProjects())`.
