## Summary

Implement a `retryWithBackoff` utility in `ui/src/lib/api/retry.ts` that wraps async operations with exponential backoff, jitter, max attempt limits, and abort signal support. Integrate it into the HTTP client so retryable HTTP errors (500, 503, 504, network failures) are automatically retried before surfacing to callers.

---

## Scope

### In Scope

- New `ui/src/lib/api/retry.ts` module with `retryWithBackoff<T>()` function
- AbortSignal support for cancellation (component unmount, user navigation)
- Integration into HTTP client for automatic retry on retryable errors
- Retryable classification: 500, 503, 504 status codes + network errors (TypeError from fetch)
- Non-retryable bypass: 400, 401, 403, 404, 409 are never retried
- Unit tests for retry logic (timing, attempts, abort, non-retryable bypass)

### Out of Scope

- UI components or hooks (those consume the retry behavior transparently)
- Per-method retry configuration (all CRUD uses same defaults in this iteration)
- Circuit breaker patterns
- Retry for AI/long-running operations

## Change Requirements

- `retryWithBackoff<T>(fn, config?)` signature:
  ```typescript
  interface RetryConfig {
    maxAttempts: number;      // default: 3
    baseDelayMs: number;      // default: 500
    maxDelayMs: number;       // default: 5000
    jitter: boolean;          // default: true
    signal?: AbortSignal;     // cancellation support
    shouldRetry?: (error: unknown) => boolean; // override default retryable check
  }
  ```
- Backoff formula: `min(baseDelay * 2^attempt + jitter, maxDelay)` where jitter is `Math.random() * baseDelay * 0.5`
- On abort: immediately reject with `AbortError` (no further attempts)
- On max attempts exhausted: reject with the last error (preserving original error info)
- HTTP client integration: wrap the core fetch call with retryWithBackoff for all requests; use `shouldRetry` that checks error's `retryable` field or infers from status code
- HTTP client must accept optional `AbortSignal` parameter and pass it through to both fetch and retryWithBackoff
- HTTP client must accept optional per-request retry config override (e.g., `{ maxAttempts: 2 }` for time-sensitive operations)
- When a new request is initiated for the same logical operation (e.g., user saves again), the previous retry chain's AbortSignal must be triggered (latest-wins semantics)

## Verification Requirements

- Unit test: retries up to maxAttempts for retryable error, then throws last error
- Unit test: succeeds on attempt 2 without surfacing error
- Unit test: does NOT retry 400/404/409 errors
- Unit test: respects AbortSignal — aborts immediately when signaled
- Unit test: backoff timing is approximately correct (within tolerance for jitter)
- Unit test: jitter produces variable delays (not deterministic)
- Integration test: HTTP client retries 503 response and succeeds on next attempt
- `pnpm typecheck` and `pnpm build` pass in `ui/`

---

## Acceptance Checks

- `retryWithBackoff` retries retryable errors up to configured max attempts
- `retryWithBackoff` does not retry non-retryable errors
- `retryWithBackoff` aborts cleanly when AbortSignal fires
- HTTP client automatically retries 500/503/504 and network failures
- HTTP client does not retry 400/404/409
- After successful retry, caller receives success result (error is transparent)
- After exhausted retries, caller receives the last error with full AppError fields
- No memory leaks from dangling retry timers after abort

## Notes

- The retry utility is generic and could be reused for non-HTTP operations in the future, so keep it decoupled from HTTP-specific concerns in its interface.
- The `shouldRetry` callback default should check for the error's `retryable` property first, then fall back to status code inference (500-599 range = retryable, network TypeError = retryable).
