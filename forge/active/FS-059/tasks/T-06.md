## Summary

Implement the optimistic update with rollback pattern for mutation operations (`updateMapping`, `updateProject`, `updateSchema`) in their respective feature hooks. When a mutation fails after retries, the UI state rolls back to the pre-mutation snapshot, preserving consistency between displayed state and server state.

---

## Scope

### In Scope

- Define a reusable `useOptimisticMutation` hook or pattern utility
- Apply pattern to `use-mapping-editor.ts` save flow
- Apply pattern to project update flows (project name/description edit)
- Apply pattern to `use-schema-detail.ts` metadata update flow
- Snapshot capture before mutation
- Rollback to snapshot on failure
- Integration with `useAsyncState` error surfacing (after rollback, error state is set)
- Unit tests for the rollback mechanism

### Out of Scope

- Create/delete operations (these are not optimistic in the current UX)
- UI components (ErrorBanner integration is separate)
- Concurrent edit conflict resolution
- Partial rollback (all-or-nothing only)

---

## Relevant Areas

- `ui/src/features/mappings/hooks/use-mapping-editor.ts` — mapping save flow
- `ui/src/features/projects/hooks/` — project update hooks
- `ui/src/features/schemas/hooks/use-schema-detail.ts` — schema metadata update
- `ui/src/hooks/use-optimistic-mutation.ts` — new shared hook (if pattern warrants extraction)

## Change Requirements

- Pattern (either as a reusable hook or documented inline pattern):
  ```typescript
  // 1. Capture snapshot
  const snapshot = currentState;
  // 2. Optimistic update
  setState(optimisticValue);
  // 3. Attempt mutation (retries handled by HTTP client)
  try {
    await adapter.updateX(id, payload);
    // 4a. Success — optimistic state confirmed
  } catch (error) {
    // 4b. Failure — rollback
    setState(snapshot);
    // 5. Surface error via AsyncState
    throw error; // or set error state directly
  }
  ```
- `use-mapping-editor.ts`:
  - The `save()` function currently applies rules and saves. After this task, it should snapshot config before save, apply optimistically, and rollback on failure.
  - Draft state (`draftRules`) must NOT be cleared until save is confirmed (not on optimistic application).
- Project hooks:
  - Name/description edits should show new values immediately, rollback on failure.
- Schema metadata update:
  - Inline metadata edits (name, description) should optimistically update and rollback on failure.

---

## Verification Requirements

- Unit test: optimistic update succeeds → state remains at new value
- Unit test: optimistic update fails → state reverts to snapshot
- Unit test: draft state is preserved during optimistic save (not cleared prematurely)
- Unit test: error is surfaced after rollback (not swallowed)
- Unit test: multiple rapid saves — only latest snapshot matters for rollback
- `pnpm typecheck` passes in `ui/`

---

## Acceptance Checks

- Mapping save: failed save rolls back config to pre-save state
- Mapping save: draft rules preserved on failure (user doesn't lose work)
- Project update: failed name change rolls back displayed name
- Schema update: failed metadata edit rolls back displayed metadata
- Error state is set after rollback (enables ErrorBanner to show)
- No UI inconsistency between displayed state and what server has
- TypeScript strict mode clean

---

## Blockers / Risks

- The `use-mapping-editor` hook is complex with draft state management. Rollback must not interfere with the draft→commit flow.
- Need to verify that rollback doesn't trigger unnecessary re-renders or re-validation cycles.

## Notes

- The decision of whether to extract a `useOptimisticMutation` reusable hook or implement the pattern inline depends on code shape at implementation time. If 3+ hooks use the same pattern, extraction is warranted.
- This task applies the pattern to existing mutation flows. Feature hooks that don't yet use `useAsyncState` for their mutation paths may need minimal wiring to expose error state.
