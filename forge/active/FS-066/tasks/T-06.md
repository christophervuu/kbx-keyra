## Summary

Implement repository guardrails that prevent browser/UI code from importing or using direct model-provider clients so backend API endpoints remain the only AI invocation path.

---

## Scope

### In Scope

- Add lint/static policy preventing model client imports in `ui/`.
- Add/adjust tests or CI checks proving restricted import patterns fail.
- Add path-based static check for forbidden provider domains/imports in browser/client bundle paths.
- Document approved path: UI → ApiAdapter/HTTP backend endpoint only.

### Out of Scope

- Backend AI runtime logic.
- UI feature-level behavioral changes.

---

## Relevant Areas

- `ui/**`
- ESLint configuration files
- repository scripts/checks for static policy (if needed)
- `forge/config/*` (if guardrails are documented there)

---

## Change Requirements

- Policy must specifically block direct usage/imports of OpenAI/GitHub model SDK clients in browser code.
- Policy must allow backend runtime usage under `src/lib/ai/` and Lambda paths.
- Guardrail must be enforceable in normal lint/test workflows.
- Guardrail must use dual enforcement: ESLint restricted imports and path-based static checks.

---

## Verification Requirements

- Lint/static check includes explicit restricted-import validation.
- Add deterministic checks/assertions for both ESLint and static path-based policy behavior.

---

## Acceptance Checks

- [ ] Browser/UI code paths are protected by restricted-import/static guardrail.
- [ ] Guardrail is enforced by existing quality checks (`pnpm lint` or equivalent).
- [ ] Path-based static check blocks forbidden provider-domain/import patterns in client paths.
- [ ] Documentation/comments indicate approved backend-only AI invocation path.

---

## Blockers / Risks

- Overly broad import restrictions may block valid shared utility imports if scope patterns are not precise.

---

## Notes

- Keep rules narrowly scoped to provider client usage to minimize false positives.
