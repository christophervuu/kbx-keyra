## Summary

Build the DynamoDB lexical retrieval stage that returns deterministic capped candidates using indexed field/path/type signals. This task establishes the primary OpenSearch replacement for candidate generation.

---

## Scope

### In Scope

- Implement Dynamo-backed lexical lookup strategy (GSI, token table, or combined path per spec decisions).
- Normalize/tokenize query terms for candidate lookup.
- Add deterministic candidate scoring and hard cap behavior before rerank.
- Return retrieval metadata needed for telemetry.

### Out of Scope

- Embedding-based rerank.
- Structural enrichment fan-out.

---

## Relevant Areas

- `src/lib/schema/dynamo/*`
- `src/lib/persistence/schema-nodes.ts`
- `src/lib/schema/types.ts`
- `src/lib/schema/constants.ts`
- `tests/lib/schema/*`

---

## Change Requirements

- Candidate generation must be schema-scoped and deterministic.
- Candidate cap behavior must be configurable and enforced before rerank.
- Default caps must be wired per environment for this phase:
  - DEV: `lexicalCap=120`, `rerankCap=80`, `topK=12`, `contextExpansionCap=24`
  - QA: `lexicalCap=150`, `rerankCap=100`, `topK=15`, `contextExpansionCap=30`
  - PROD: `lexicalCap=180`, `rerankCap=120`, `topK=18`, `contextExpansionCap=36`
- Retrieval output must preserve fields required by existing consumers.

---

## Verification Requirements

- Unit tests for token normalization and deterministic ranking order.
- Integration tests for schema-scoped lexical query with cap enforcement.
- Lint/typecheck/test for touched modules.

---

## Acceptance Checks

- Dynamo lexical retrieval returns stable ordering for identical inputs.
- Candidate cap is enforced and observable in returned metadata.
- Query endpoint and AI callers can consume lexical results without contract breakage.

---

## Blockers / Risks

- Index strategy choice (GSI vs token table) may impact read-cost/latency tradeoffs.

---

## Notes

- Keep scoring deterministic; avoid non-stable sort behavior under ties.
