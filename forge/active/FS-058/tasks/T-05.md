## Summary

Implement `src/lib/persistence/schema-nodes.ts` with operations for the SchemaNodes DynamoDB table: batch-write (handling 25-item BatchWriteItem limit with retry), list-by-schema, query-contains (text search via filter), and delete-by-schema (batch delete all nodes for a schema). This is the highest-complexity persistence module due to batch operation handling.

---

## Scope

### In Scope

- `src/lib/persistence/schema-nodes.ts` — all 4 operations
- BatchWriteItem chunking (max 25 items per call)
- Unprocessed items retry with exponential backoff (max 3 retries)
- `queryContains` using Scan with FilterExpression
- `deleteBySchema` using Query (to get all keys) + batch DeleteItem
- Unit tests

### Out of Scope

## Change Requirements

- Implement `schemaNodes.batchWrite(schemaId: string, nodes: SchemaNodeItem[]): Promise<void>`:
  - Chunk `nodes` array into groups of 25
  - For each chunk, issue `BatchWriteCommand` with PutRequest items
  - If response includes `UnprocessedItems`, retry those items with exponential backoff (100ms, 200ms, 400ms)
  - After 3 retries with unprocessed items remaining, throw an error with details
  - All items must have `schemaId` set to the provided value

- Implement `schemaNodes.listBySchema(schemaId: string): Promise<SchemaNodeItem[]>`:
  - `QueryCommand` with `KeyConditionExpression: 'schemaId = :sid'`
  - Handle pagination (`LastEvaluatedKey`) — collect all pages
  - Return all items for the schema

- Implement `schemaNodes.queryContains(schemaId: string, query: string, limit?: number): Promise<SchemaNodeItem[]>`:
  - `QueryCommand` on PK `schemaId` with `FilterExpression` using `contains(#path, :q) OR contains(#fieldName, :q)`
  - Default limit: 50
  - Return matching items up to limit
  - Decision (Q3 resolved): uses Query on PK + FilterExpression — NOT full-table Scan

- Implement `schemaNodes.deleteBySchema(schemaId: string): Promise<void>`:
  - Query all items for the schema (get `schemaId` + `path` keys)
  - Batch delete using `BatchWriteCommand` with DeleteRequest items (chunks of 25)
  - Handle unprocessed items with same retry logic as batchWrite

## Blockers / Risks

- Large schemas (23,000+ nodes) will result in many batch operations. The retry/backoff logic must be robust. FS-056 may want configurable backoff parameters — expose them as optional config.

---

## Notes

- `queryContains` uses `Query` on PK (not Scan) + FilterExpression. This is efficient because it only scans items within the schema partition, not the entire table.
- The exponential backoff for unprocessed items should use a simple `await new Promise(r => setTimeout(r, delay))` pattern.
- Consider extracting the batch-write-with-retry logic into a shared utility since `deleteBySchema` also needs batch operations with retry.
