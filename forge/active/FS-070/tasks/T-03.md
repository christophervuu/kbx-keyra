## Summary

Adapt suggest-expression frontend orchestration so loading/success/error states handle validation-aware backend responses, including invalid-suggestion review states and deterministic non-mutation behavior on failures.

---

## Scope

### In Scope

- Update `use-suggest-expression` state model and response handling for validation metadata.
- Ensure invalid suggestions are represented as reviewable-but-not-ready states.
- Preserve retry/dismiss/reset semantics and abort behavior.
- Add/update hook tests covering valid suggestion, invalid suggestion, and failure paths.

### Out of Scope

- Visual redesign of suggestion components.
- Backend contract implementation.
- Broader mapping editor orchestration changes unrelated to suggest flow.

---

## Relevant Areas

- `ui/src/features/mappings/hooks/use-suggest-expression.ts`
- `ui/src/features/mappings/hooks/use-suggest-expression.test.ts`
- `ui/src/lib/types/domain.ts`

---

## Change Requirements

- Hook state must distinguish transport error vs validation-invalid suggestion outcome.
- Invalid suggestion outcome must not trigger implicit apply or success-ready state.
- Existing abort-on-reinvoke/unmount behavior remains correct.
- Error messages remain user-friendly and deterministic.

---

## Verification Requirements

- Hook tests cover: valid suggestion lifecycle, invalid validation lifecycle, backend error lifecycle, dismiss/reset non-mutation expectations.
- Typecheck and test pass for touched hook files.

---

## Acceptance Checks

- Hook can consume updated response contract without runtime narrowing hacks.
- Invalid suggestions are surfaced as non-apply-ready state.
- Dismiss/failure paths preserve existing field expression state.

---

## Blockers / Risks

- Existing tests may encode old “success only” assumptions and require targeted updates.

---

## Notes

- Keep state transitions explicit and predictable; avoid overloading `error` state for validation-invalid outcomes.
