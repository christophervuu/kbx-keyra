## Summary

Refactor the suggest-expression backend path so request inputs identify the selected mapping/target context while schema context is assembled server-side, then enforce engine validation on generated DSL before returning a suggestion result. This task establishes the canonical safe backend contract for NL→DSL generation.

---

## Scope

### In Scope

- Update suggest-expression Lambda request contract and validation.
- Add backend logic to retrieve/assemble relevant source/target schema context from persisted records.
- Preserve canonical `invokeAI('nl-to-rule', ...)` runtime usage with updated variables assembly.
- Add engine validation pass for generated expression and include deterministic validation payload in response.
- Enforce backend context assembly bounds (~64KB raw text or ~8k token-equivalent) with deterministic truncation/summarization.
- Map runtime/request/validation failures to normalized API responses.
- Add/adjust Lambda tests for new contract and validation-gating behaviors.

### Out of Scope

- UI component or hook updates.
- Prompt content rewrite/admin tooling.
- New infrastructure resources.
- Bulk suggestion generation.

## Change Requirements

- Request schema accepts NL instruction + selected-field context identifiers needed for backend data lookup.
- Backend assembles AI prompt context from stored schema/mapping data rather than relying on UI-passed context text.
- Generated candidate expression is validated before success response; gate includes syntax, function compatibility, and target-type compatibility, and response includes `valid` plus diagnostics details.
- Invalid generated expressions are returned in a structured invalid-suggestion response (not treated as normal success-ready candidate).
- Error envelope/status behavior remains consistent with backend conventions.
