## Summary

Extend the `useMappingEditor` hook to support config option mutations beyond rule edits. Currently the hook only tracks rule changes for unsaved detection and only persists rules on save. This task adds an `updateConfig` action, extends `hasUnsavedChanges` to detect config option changes, and ensures the save flow includes locally-mutated config options. This is the data-layer prerequisite for all Configuration Panel UI.

---

## Scope

### In Scope

- Add `updateConfig(partial: Partial<MappingConfigOptions>)` action to `MappingEditorActions`
- Add local state tracking for config options (separate from the loaded config)
- Extend `hasUnsavedChanges` to compare both rules AND config options against last-saved state
- Extend `validationConfig` memo to include locally-mutated config options
- Extend save flow to persist config option changes in the updated `MappingConfig`
- Update `UseMappingEditorResult` to expose current config options for panel consumption
- Ensure `useEngineValidation()` receives updated config options (triggers re-validation)

### Out of Scope

- Building any UI components for the config panel
- Changing the `useEngineValidation()` hook itself (it already accepts full MappingConfig)
- Adding new fields to `MappingConfigOptions` type (already complete)
- Undo/redo for config changes

## Change Requirements

After this task:

- `useMappingEditor` returns `configOptions: MappingConfigOptions` representing the current (potentially unsaved) config options
- `actions.updateConfig(partial)` merges partial config options into local state (shallow merge at the top level; for `constants` and `externalSources`, full replacement of those sub-objects)
- `hasUnsavedChanges` is `true` when either rules differ from last-saved OR config options differ from last-saved
- `validationConfig` memo produces a `MappingConfig` with current rules AND current config options applied (so `useEngineValidation` sees the live config)
- `save()` persists the full config including locally-mutated options; on save success, the new config options become the "last saved" reference
- After save, `hasUnsavedChanges` returns to `false` when both rules and config options match

Implementation approach for config comparison:
- Store `lastSavedConfigOptions` alongside `lastSavedRules`
- Compare with JSON serialization (same pattern as `rulesEqual`) — acceptable for Phase 0 with small config objects

## Notes

The existing `validationConfig` memo is `{ ...config, rules }`. After this task it should be `{ ...config, rules, config: currentConfigOptions }`. The outer `config` (MappingConfig) and inner `config` (MappingConfigOptions) share the field name — be careful with the spread to avoid accidentally overwriting the wrong level.

The `updateConfig` merge semantics: for top-level primitive fields like `unmappedTargets`, a simple spread works. For `constants` (Record) and `externalSources` (array), the caller (Panel UI) will pass the full replacement value — the hook does not need to implement deep merge logic for nested collections.
