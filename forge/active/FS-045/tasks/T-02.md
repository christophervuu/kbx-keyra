## Summary

Add post-AI expression validation to the auto-map Lambda handler. After `invokeAI` returns successfully, each generated rule's `expression` is validated using the engine's `parse()` function. Validation results (`valid`, `diagnostics`) are attached to each rule before the response is returned. This ensures the UI receives validation status for every suggestion without a separate validation call.

---

## Scope

### In Scope

- Import `parse` from `../../engine/index.js` (or `../../engine/dsl/index.js`) in `auto-map.ts`
- Import `defaultRegistry` from `../../engine/registry/function-registry.js` for parse options
- After a successful `invokeAI` result, iterate over `data.rules` and validate each `expression`
- Attach `validation: { valid: boolean, diagnostics: string[] }` to each rule
- `valid` = no error-severity diagnostics from `parse()`
- `diagnostics` = array of `message` strings from error-severity parse diagnostics
- Catch parse exceptions per-rule gracefully (return `{ valid: false, diagnostics: ["Validation failed"] }`)
- Return the enriched result

### Out of Scope

- Full `validate()` with schema context (requires structured schemas, not practical for this slice)
- Filtering out invalid rules (all rules are returned regardless of validation status)
- Modifying the shared AI runtime (`src/lib/ai/`)
- Modifying the engine (`src/engine/`)

- `src/lambda/ai/auto-map.ts` (modified)

- `src/engine/types/index.ts` — `Diagnostic` type (for severity checking)

## Change Requirements

Modify the success path in `auto-map.ts` to add validation:

1. **Import** `parse` from the engine's DSL module and `defaultRegistry` from the function registry
2. **Define** a `validateExpression(expression: string)` helper function within `auto-map.ts` that:
   - Calls `parse(expression, { registry: defaultRegistry })`
   - Filters diagnostics to those with `severity === 'error'`
   - Returns `{ valid: boolean, diagnostics: string[] }` where `valid = errorDiagnostics.length === 0` and `diagnostics = errorDiagnostics.map(d => d.message)`
   - Wraps the parse call in try/catch — on exception, returns `{ valid: false, diagnostics: ['Validation failed'] }`
3. **Modify** the success response path:
   - When `result.success === true`, iterate over `result.data.rules` (if it exists and is an array)
   - For each rule, call `validateExpression(rule.expression)` and attach the result as `rule.validation`
   - Return the enriched result
4. **Preserve** the existing response envelope — the `success`, `promptId`, `model`, and `usage` fields remain unchanged. Only the rules array is enriched.

The validation should be defensive:
- If `result.data.rules` is not an array, skip validation and return the result as-is
- If a rule's `expression` is not a string, set `validation: { valid: false, diagnostics: ['No expression to validate'] }`

## Notes

- The engine import introduces a dependency from `src/lambda/ai/auto-map.ts` to `src/engine/`. This is explicitly allowed by the project structure rules: "Lambda handlers import from `src/engine/` and `src/lib/` only." The constraint against engine imports applies only to `src/lib/ai/`, not to Lambda handlers.
- Import `parse` via the engine barrel (`../../engine/index.js`) rather than deep imports, to ensure `registerAllFunctions` is called. Verify this during implementation — if the barrel import triggers side effects, prefer `import { parse } from '../../engine/dsl/index.js'` with explicit `registerAllFunctions(defaultRegistry)` call.
- The validation enrichment must create a new result object (or mutate carefully) — the `AIResult` type has `readonly` fields. Consider creating a new response payload object rather than mutating the result from `invokeAI`.
