## Summary

Implement the DynamoDB writer module that persists SchemaMetadata records and SchemaNode records. The module handles metadata lifecycle transitions (`ingesting` → `ready` | `error`), batch-writes SchemaNodes in 25-item chunks with exponential backoff retry for unprocessed items, and provides read operations for metadata status checks.

---

## Scope

### In Scope

- `createSchemaMetadata(metadata: SchemaMetadata): Promise<void>` — PutItem for new metadata
- `updateSchemaStatus(schemaId: string, status: SchemaStatus, updates?: Partial<SchemaMetadata>): Promise<void>` — UpdateItem for status transitions
- `batchWriteSchemaNodes(nodes: SchemaNode[]): Promise<{ written: number, failed: number }>` — BatchWriteItem in 25-item chunks with retry
- `getSchemaMetadata(schemaId: string): Promise<SchemaMetadata | null>` — GetItem
- Exponential backoff retry for `UnprocessedItems` (max 5 retries, base 100ms, factor 2)
- Table names from environment variables (`SCHEMA_METADATA_TABLE`, `SCHEMA_NODES_TABLE`)
- DynamoDB document client usage (marshall/unmarshall handled)

### Out of Scope

- Table creation (infrastructure)
- GSI queries (those belong in the query module)
- Delete operations
- Transaction writes (not needed for ingestion)
- Optimistic locking / conditional writes

## Change Requirements

- Use AWS SDK v3 `@aws-sdk/lib-dynamodb` (DynamoDBDocumentClient) for simplified marshalling
- DynamoDB client instantiated once per module
- `batchWriteSchemaNodes` must:
  - Split input into chunks of 25
  - Call `BatchWriteCommand` per chunk
  - Inspect `UnprocessedItems` in response
  - Retry unprocessed items with exponential backoff
  - Track written vs failed counts
  - Not throw on partial failure — return counts
- `createSchemaMetadata` must set `createdAt` and `updatedAt` to current ISO timestamp
- `updateSchemaStatus` must update `updatedAt` and conditionally merge additional fields (like `fieldCount` when transitioning to `ready`)
- Errors from DynamoDB operations wrapped in domain-specific types

## Notes

The retry logic with exponential backoff is critical for large schemas where DynamoDB throttling is likely during burst writes. Use `setTimeout`/`await` for delay implementation in the retry loop.
