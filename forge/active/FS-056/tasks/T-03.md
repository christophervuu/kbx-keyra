## Summary

Implement the S3 storage module responsible for uploading the original schema file and the processed schema content to the designated S3 bucket. The module provides `storeOriginalSchema` and `storeProcessedContent` functions that handle key construction, content type detection, and PutObject operations.

---

## Scope

### In Scope

- `storeOriginalSchema(schemaId: string, content: string, format: SchemaFormat): Promise<string>` — stores original file at `schemas/{schemaId}/original.{ext}` and returns the S3 key
- `storeProcessedContent(schemaId: string, content: object): Promise<string>` — stores processed JSON at `schemas/{schemaId}/content.json` and returns the S3 key
- `getSchemaContent(schemaId: string): Promise<string>` — retrieves processed content for downstream use
- S3 key pattern enforcement (`schemas/{schemaId}/original.json`, `schemas/{schemaId}/original.xsd`, `schemas/{schemaId}/content.json`)
- Content type headers set correctly (`application/json` for JSON, `application/xml` for XSD)
- Bucket name from environment variable (`SCHEMA_BUCKET`)

### Out of Scope

- S3 bucket creation (infrastructure concern)
- Schema deletion/cleanup
- Presigned URLs
- Multipart upload (schema files are well under 5GB)

## Change Requirements

- Use AWS SDK v3 `@aws-sdk/client-s3` (already a project dependency via AI lambdas)
- S3 client instantiated once per module (cold start optimization)
- Key construction must follow product spec patterns exactly
- File extension for original: `.json` for json-schema, `.xsd` for xsd
- All functions are async and return the S3 key on success
- Errors wrapped in domain-specific error types (not raw SDK errors)
- Environment variable `SCHEMA_BUCKET` read at module initialization
