## Summary

Implement the Step Functions worker Lambda that processes a single batch of SchemaNodes. Each invocation receives a batch reference (S3 key pointing to a batch manifest), reads the node data, writes nodes to DynamoDB, indexes documents into OpenSearch, and returns batch processing results. This Lambda is invoked in parallel by the Map state in the ingestion state machine.

---

## Scope

### In Scope

- Worker Lambda at `src/lambda/schema/process-batch.ts`
- Parse/Aggregate Lambda at `src/lambda/schema/orchestration-tasks.ts` (ParseSchema, AggregateResults, UpdateMetadata, HandleError tasks)
- Worker input: `{ batchIndex: number, s3Key: string, schemaId: string, nodeCount: number }`
- Worker flow:
  1. Read batch data from S3 (array of SchemaNode objects)
  2. Write nodes to DynamoDB via `batchWriteSchemaNodes`
  3. Index nodes into OpenSearch via `bulkIndexSchemaNodes`
  4. Return `{ batchIndex, nodesWritten, nodesIndexed, errors? }`
- ParseSchema task:
  1. Read original schema from S3
  2. Parse into SchemaNode[] using T-02 parser
  3. Split nodes into batches of 500
  4. Write each batch to S3 as JSON (`schemas/{schemaId}/batches/batch-{N}.json`)
  5. Return array of batch references
- AggregateResults task:
  1. Sum nodesWritten/nodesIndexed from all batch results
  2. Store processed content in S3
  3. Return totals
- UpdateMetadata task:
  1. Update SchemaMetadata with `status: "ready"`, `fieldCount`
- HandleError task:
  1. Update SchemaMetadata with `status: "error"`, error details

### Out of Scope

- State machine definition (T-07)
- OpenSearch index creation (T-05, called by first-run setup)
- Inline ingestion path (T-06)

## Change Requirements

- Worker Lambda:
  - Reads batch file from S3 (JSON array of SchemaNode)
  - Calls `batchWriteSchemaNodes` from T-04 DynamoDB module
  - Calls `bulkIndexSchemaNodes` from T-05 OpenSearch module
  - Returns structured result for Map state aggregation
  - Handles errors gracefully (catches, returns error info instead of throwing — allows other batches to succeed)
- ParseSchema Lambda:
  - Memory: 1024MB minimum (environment configuration, not code)
  - Uses T-02 parser to produce full SchemaNode[]
  - Chunks into arrays of 500 nodes
  - Writes each chunk to S3 as `schemas/{schemaId}/batches/batch-{index}.json`
  - Returns batch reference array for Map state
- AggregateResults Lambda:
  - Accepts array of batch results from Map state
  - Computes totals (written, indexed, failed)
  - Calls `storeProcessedContent` from T-03
  - Returns summary
- HandleError Lambda:
  - Receives error context from Catch
  - Calls `updateSchemaStatus(schemaId, "error", { errorDetails })`
- All Lambdas: typed events, structured responses, error wrapping

## Blockers / Risks

- ParseSchema Lambda for 23,000-field schema starts at 1024MB memory (Q3 decision). If profiling shows this is insufficient, raise to 1536MB or 2048MB operationally — prefer tuning over premature streaming implementation.
- Batch S3 writes add latency to the parse step. For 46 batches, parallel S3 puts may be needed.

---

## Notes

The worker Lambda is designed to be stateless and idempotent. If a Step Functions retry occurs, the worker can re-process the same batch safely (DynamoDB PutItem and OpenSearch index are idempotent operations with the same keys/IDs).

The batch manifest S3 keys are temporary artifacts. A cleanup step (future enhancement) can remove them after successful ingestion.
