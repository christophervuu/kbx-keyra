## Summary

Create integration and performance test suites that verify the full ingestion pipeline end-to-end. Tests exercise the inline path with 500-field schemas, the Step Functions path with 23,000-field schemas (mocked orchestration), and the query endpoint with real indexed data. Performance benchmarks verify that ingestion and query meet the specified time targets.

---

## Scope

### In Scope

- Integration test suite at `tests/integration/schema-ingestion/`
- Test fixtures: generated JSON Schemas at 50, 499, 500, and 23,000 fields
- Fixture generator utility (programmatic schema construction)
- Inline path integration test (mocked AWS services, real module orchestration):
  - Verify 50-field schema produces correct SchemaMetadata + SchemaNodes
  - Verify 499-field schema processes inline
  - Verify field count, node paths, types, depths are correct
- Step Functions path integration test (mocked SFN client, real parse + batch logic):
  - Verify 500-field schema triggers SFN
  - Verify 23,000-field schema parses + chunks correctly
  - Verify batch worker produces correct DynamoDB items + OpenSearch docs
- Query integration test (mocked OpenSearch + DynamoDB, real query construction):
  - Verify keyword match returns relevant results
  - Verify type filter narrows results
  - Verify parent chain enrichment
- Performance benchmarks (real code, mocked AWS I/O):
  - 500-field parse time < 1 second
  - 23,000-field parse time < 10 seconds
  - Query construction + result mapping < 50ms
  - DynamoDB batch write for 500 nodes (chunking logic) < 100ms excluding I/O

### Out of Scope

- Actual AWS service calls (tests use mocks/local emulators)
- Frontend integration
- Load testing
- OpenSearch cluster setup

## Change Requirements

- Schema fixture generator:
  - `generateJsonSchema(fieldCount: number): object` — produces a valid JSON Schema with specified leaf field count
  - Mix of nested objects, arrays, various types (string, number, boolean, array)
  - Deterministic output for given field count (seeded generation)
  - Realistic field names (e.g., `Order.LineItems[].Product.Name`)
- Inline path integration tests:
  - Instantiate all modules with mocked clients
  - Call ingestSchema handler with generated schema
  - Assert metadata status, node count, S3 calls, DynamoDB writes, OpenSearch indexing
  - Verify 499-field stays inline, 500-field triggers SFN
- Step Functions path tests:
  - Call ParseSchema task logic directly
  - Verify 23,000-field schema produces ~46 batches of 500
  - Call worker logic with one batch, verify DynamoDB + OpenSearch calls
- Query integration tests:
  - Pre-populate mock OpenSearch responses
  - Call query handler
  - Assert result structure, filtering, parent chain enrichment
- Performance tests:
  - Use `performance.now()` or `Date.now()` for timing
  - Assert parse, batch, and query timings under specified thresholds
  - Use longer test timeouts for large schema tests (30+ seconds)

## Notes

These integration tests use mocked AWS SDK clients throughout. They test the orchestration logic, data flow between modules, and correctness of the pipeline — not actual AWS service behavior. Actual AWS integration is verified during manual deployment testing.

For the 23,000-field performance test, consider using `vitest`'s `test.concurrent` or custom timeout to avoid CI timeouts.
