## Summary

Implement the schema parsing module that converts raw JSON Schema content and XSD content into arrays of `SchemaNode` records. The parser traverses the schema structure, computes paths, types, depths, parent paths, child counts, subtree field counts, required status, and array indicators. It also generates embedding text for each node. This is a pure-function module with no AWS dependencies.

---

## Scope

### In Scope

- `parseJsonSchema(content: string, schemaId: string): ParseResult` — parse JSON Schema into SchemaNode[]
- `parseXsd(content: string, schemaId: string): ParseResult` — parse XSD into SchemaNode[]
- `ParseResult` type: `{ nodes: SchemaNode[], fieldCount: number, errors?: string[] }`
- JSON Schema traversal: `properties`, `items`, `$defs`/`definitions` (local $ref resolution), `allOf` (shallow merge), `anyOf`/`oneOf` (treated as alternatives)
- XSD traversal: `xs:element`, `xs:complexType`, `xs:sequence`, `xs:choice`, `xs:all`
- XSD type mapping: `xs:string` → `string`, `xs:integer`/`xs:int`/`xs:long`/`xs:short` → `number`, `xs:decimal`/`xs:float`/`xs:double` → `number`, `xs:boolean` → `boolean`, `xs:date`/`xs:dateTime` → `string`
- XSD array detection: `maxOccurs="unbounded"` or `maxOccurs` > 1
- Dot-notation path construction (e.g., `Order.Header.DocumentType`)
- `parentPath` computed for each node
- `childCount` = number of direct children
- `subtreeFieldCount` = total leaf fields in subtree (recursive)
- `isRequired` derived from JSON Schema `required` array or XSD `minOccurs` > 0
- `embeddingText` generated via `generateEmbeddingText` from T-01
- Error handling: invalid JSON returns parse error; invalid XSD returns parse error; no exceptions thrown

### Out of Scope

- Remote `$ref` resolution (only local refs within the document)
- XSD `xs:import` / `xs:include` (external file references)
- Schema inference from sample data
- DynamoDB/S3/OpenSearch interaction
- Large-schema chunking (that's the Step Functions concern)

## Change Requirements

- JSON Schema parser must handle:
  - Nested objects (`properties` within `properties`)
  - Arrays (`type: "array"` with `items`)
  - `$ref` to `$defs` or `definitions` within the same document
  - `allOf` merging (combine properties from all subschemas)
  - `anyOf`/`oneOf` (include all alternatives as optional children)
  - `required` arrays for `isRequired` determination
  - Missing/empty `properties` as valid (0 fields)
  - Circular `$ref` detection (break infinite loops, emit warning)
- XSD parser must handle:
  - Simple and complex types
  - `xs:sequence` ordering preserved in path construction
  - `xs:choice` alternatives all included as sibling nodes (all `isRequired: false`) — this is a lossy structural approximation of XSD choice semantics (Q5 decision). Document this behavior in code comments.
  - `xs:all` treated similar to sequence
  - Attribute → node mapping (attributes become leaf nodes)
  - Type inheritance via `xs:extension`
- Both parsers must:
  - Produce deterministic output (same input → same nodes in same order)
  - Compute `subtreeFieldCount` correctly via bottom-up accumulation
  - Compute `childCount` as direct children only
  - Set `depth` starting from 0 at root level
  - Generate `embeddingText` for every node
  - Return fieldCount as total leaf node count

## Notes

The UI already has parsers at `ui/src/features/schemas/lib/parsers/` (parse-json-schema.ts, parse-xsd.ts) that produce `SchemaTreeNode[]` for the UI tree view. The backend parser produces `SchemaNode[]` with different fields (DynamoDB-oriented). Do not import from or depend on UI parser code — the backend parser is independent with different output requirements (embeddingText, subtreeFieldCount, etc.).

An XML parsing library will likely be needed for XSD. `fast-xml-parser` is lightweight and has no native dependencies. Confirm it's acceptable before proceeding.
