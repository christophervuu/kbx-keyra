## Summary

Modify backend schema/project APIs so schema availability is shared across projects and project-level schema linkage is treated as relevance metadata only, including upload/link/unlink semantics.

---

## Scope

### In Scope

- Update schema handlers to stop using scope as access filter semantics.
- Ensure create/upload/link flows create shared schema entries and attach project links where appropriate.
- Ensure unlink behavior removes project link without deleting schema.
- Enforce hard-block unlink when active mappings in the same project reference the schema; return dependent mapping list.
- Update project detail aggregation contracts for linked schemas.

### Out of Scope

- UI rendering and copy changes.
- Deployment subsystem changes unless directly required by schema handler behavior.

---

- `src/lambda/schema/create-schema.ts`

- `src/lambda/schema/link-cdm-schema.ts`
- `src/lambda/project/get-project.ts`
- related shared utilities in `src/lambda/shared/*`

---

## Change Requirements

- `GET /schemas` returns shared library without scope gating.
- Project linkage endpoints/read models remain explicit and independent of schema ownership (canonical linkage toward `linkedSchemaIds` with compatibility where required).
- Upload-from-project flow persists schema once and links to project.
- Guard unlink/delete interactions to avoid breaking existing mapping references; unlink must be blocked while dependencies exist.
- Maintain compatibility for legacy payloads where required.

---

## Verification Requirements

- Handler-level unit/integration tests for shared listing, linking, unlink semantics, and migration compatibility.
- Validate API response contracts remain deterministic.

---

## Acceptance Checks

- Backend no longer treats schema scope as access boundary.
- Linking/unlinking affects project references only.
- Shared schema list behavior and project-linked behavior match FS-087 acceptance examples.

---

## Blockers / Risks

- Risk: existing delete conflict semantics may rely only on project refs and miss mapping refs; verify before finalizing behavior.

## Notes

- Align implementation with audit outcomes from T-02 where existing handler names/flows differ.
- Implemented handler compatibility-forward semantics across schema/project routes:
  - `GET /schemas` returns shared-library list with no scope-based access filtering.
  - `create-schema` upload flow supports optional `projectId` linkage while persisting one shared schema record.
  - `get-schema` / `list-schemas` normalize legacy origin aliases (`local|published -> uploaded`) and sync-status aliases at read boundaries.
  - project read/write flows canonicalize linkage toward `linkedSchemaIds` with read-time fallback from legacy `schemaRefs`.
- Implemented unlink hard-block in `update-project`:
  - detects removed `linkedSchemaIds` in update payload,
  - queries mappings for the same project,
  - returns `409 CONFLICT` with `details.dependentMappings` when source/target schema refs still depend on removed link(s).
- Strengthened delete guard behavior in `delete-schema`:
  - blocks deletion when schema is still referenced by any project link (`linkedSchemaIds` or legacy `schemaRefs`) or mapping references.
- Added/updated handler tests for shared list, upload+link behavior, project linkage compatibility, unlink conflict details payload, and schema delete/reference guards.
