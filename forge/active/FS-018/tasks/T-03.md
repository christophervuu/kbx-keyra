## Summary

Extend the `useMappingEditor` hook's save flow to persist a `MappingVersionEntry` snapshot after every successful save. This is a small but critical integration point: every `adapter.updateMapping()` success is followed by `adapter.saveMappingVersion()` to capture the version in history. The version save is fire-and-forget — it must not block the save flow or surface errors to the user (log only).

---

## Scope

### In Scope

- After successful `adapter.updateMapping()` in `useMappingEditor.save()`, build and persist a `MappingVersionEntry`
- Fire-and-forget semantics: catch errors from `saveMappingVersion()` and log a console warning, do not surface to user or affect save status
- Build the `MappingVersionEntry` from the saved config: `version`, `savedAt`, `savedBy: "You"`, `ruleCount`, `config`

### Out of Scope

- Loading version history (T-04)
- UI for displaying versions (T-05, T-06)
- Restore flow (T-06)
- Changing the save status indicators or top bar behavior
- Backfilling version history for existing saved mappings

## Change Requirements

After this task:

In the `save` callback of `useMappingEditor`, after `adapter.updateMapping()` succeeds and state is updated:

```typescript
// After successful save...
// Fire-and-forget version snapshot
const versionEntry: MappingVersionEntry = {
  version: newVersion,
  savedAt: new Date().toISOString(),
  savedBy: 'You',
  ruleCount: updatedConfig.rules.length,
  config: updatedConfig,
};

adapter.saveMappingVersion(mappingId, versionEntry).catch((err) => {
  console.warn('Failed to save version history entry:', err);
});
```

Key requirements:
- The `saveMappingVersion` call is NOT awaited (fire-and-forget)
- Errors are caught and logged but do not affect save status
- The `versionEntry` uses the same `updatedConfig` that was just persisted (ensures snapshot matches saved state exactly)
- `savedAt` uses `new Date().toISOString()` at the moment of save completion
