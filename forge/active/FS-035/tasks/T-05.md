## Summary

Extend the TestCaseManager component to show pass/fail/not-run status indicators next to each saved test case. Status is derived from the most recent execution result for that test case and persisted to `sessionStorage` (keyed by mapping ID) so indicators survive page navigations within the same browser session. When a loaded test case is modified, execution results apply to the working copy and do not update the canonical saved test case's indicator.

---

## Scope

### In Scope

- Define a `TestCaseResult` type to hold per-test execution results
- Create a `testResults` state map (`Map<string, TestCaseResult>`) managed at the AdvancedTestingPage level, backed by `sessionStorage`
- Persist results to `sessionStorage` under key `keyra:test-results:{mappingId}` — survives page navigations, cleared on tab/window close
- Load results from `sessionStorage` on mount; write back on every result update
- After each execution (single or batch), record the result keyed by test case ID — but only when the loaded test case is NOT in a modified state
- Track modified state: compare working source data / expected output against the saved test case's data
- Pass result map to TestCaseManager for indicator rendering
- Render status indicators in the test case list rows:
  - Green check icon: passed
  - Red X icon: failed
  - Amber alert icon: error/timeout
  - No icon: not yet run
- Show a "modified" visual cue on the loaded test case when working data differs from saved data

### Out of Scope

- Persisting results to localStorage (durable history across browser sessions)
- Batch execution implementation (that is T-06)
- Changes to test case CRUD operations
- Changes to how test cases are saved or loaded

## Change Requirements

### TestCaseResult Type

```typescript
interface TestCaseResult {
  readonly verdict: ExecutionVerdict;  // 'pass' | 'fail' | 'error'
  readonly durationMs?: number;
  readonly diagnosticCount?: number;
  readonly diffMismatchCount?: number;
  readonly executedAt: number;  // Date.now() timestamp
}
```

### State Management

In `AdvancedTestingPage`:
- Add `testResults` state: `Map<string, TestCaseResult>`, initialized from `sessionStorage` on mount
- sessionStorage key: `keyra:test-results:{mappingId}`
- On mount: read and parse stored results from sessionStorage; fall back to empty map on missing/corrupt data
- On every result update: serialize and write the map back to sessionStorage
- After each single execution completes, if the current source data was loaded from a test case AND the test case is NOT in a modified state, record the result:
  - `verdict` from `deriveExecutionVerdict(state, diffResult)`
  - `durationMs` from `state.result.stats?.durationMs`
  - `diagnosticCount` from `state.result.diagnostics.length`
  - `diffMismatchCount` from `diffResult?.summary.total`
- Track which test case is currently loaded via `loadedTestCaseId` state
- Track whether the loaded test case is modified via `isTestCaseModified` state

### Modified Test Case Tracking

When a test case is loaded via `handleLoadTestCase`:
- Set `loadedTestCaseId` to the test case's ID
- Snapshot the test case's `sourceData` and `expectedOutput` as `loadedSourceData` and `loadedExpectedOutput`
- Set `isTestCaseModified` to `false`

When the user edits source data or expected output after loading:
- Compare current working values against `loadedSourceData` / `loadedExpectedOutput`
- Set `isTestCaseModified` to `true` if either differs, `false` if both match

When `isTestCaseModified` is `true` and execution completes:
- Display results normally in the UI (summary bar, tabs)
- Do NOT update `testResults` for `loadedTestCaseId`
- The canonical indicator for that test case retains its previous value

When a different test case is loaded or source data is cleared:
- Reset `loadedTestCaseId`, `loadedSourceData`, `loadedExpectedOutput`, `isTestCaseModified`

### TestCaseManager Integration

Add a `results` prop to TestCaseManager:

```typescript
results?: ReadonlyMap<string, TestCaseResult>;
```

Per test case row:
- Look up `results.get(testCase.id)`
- If found, render a verdict icon (left of the test case name):
  - `pass` → `CheckCircle2` (green, `text-green-400`)
  - `fail` → `XCircle` (red, `text-red-400`)
  - `error` → `AlertCircle` (amber, `text-amber-400`)
- If not found, render no icon (or a subtle gray dash for visual consistency)

## Notes

- sessionStorage key pattern: `keyra:test-results:{mappingId}`. Serialized as JSON. Parsing failures fall back to an empty map (no crash).
- The modified-state tracking uses simple string comparison of `sourceData` and `expectedOutput` against snapshots taken at load time. No deep diffing needed.
- Batch execution (T-06) will bulk-update the `testResults` map. This task sets up the state shape, sessionStorage persistence, modified-state tracking, and rendering; T-06 adds the batch population path.
