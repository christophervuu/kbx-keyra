## Summary

Implement the mode toggle between Builder and Editor with bidirectional conversion. Builder→Editor is trivial (show the generated DSL string in the editor). Editor→Builder requires AST decomposition — parse the expression, check if it matches a supported builder pattern, and either populate the builder steps or show a "too complex" warning.

---

## Scope

### In Scope

- **Mode toggle UI refinement:**
  - Segmented control at top of panel: "Builder" / "Editor"
  - Active mode highlighted
  - Toggle fires mode switch logic (not just state change)
- **Builder → Editor transition:**
  - Take the current generated expression from builder state
  - Set it as the raw editor's value
  - Switch view to raw editor
  - Expression is immediately editable
- **Editor → Builder transition:**
  - Parse current expression with `parse()`
  - Run AST decomposition check: does the AST match a supported builder pattern?
  - If decomposable: populate builder state from AST (source fields, function, arguments)
  - If not decomposable: show warning modal/banner, remain in Editor mode (or switch but show warning)
- **AST decomposition logic (`ast-decomposer.ts`):**
  - `decomposeExpression(expression: string): DecompositionResult`
  - `DecompositionResult` = `{ success: boolean; builderState?: BuilderState; reason?: string }`
  - Supported patterns:
    - `source("path")` → Direct Copy (1 source field, no transform)
    - `static(literal)` → Static Value
    - `functionName(source("path"), ...)` → Single function with literal/source args
    - `functionName(source("path"), source("path2"), literal)` → Multi-arg
    - `map(source("arr"), { ... })` → Array map with template (if template values are simple)
    - `filter(source("arr"), simpleCondition)` → Array filter with simple condition
  - NOT supported (returns `success: false`):
    - Deeply nested functions (more than 1 level of function nesting beyond the outermost)
    - Object templates with nested function values (beyond source/static/item)
    - Patterns using functions not in the builder's supported set
    - Very complex conditionals with multiple nested branches
  - `reason` provides user-friendly explanation when decomposition fails
- **Warning display for complex expressions:**
  - Banner/dialog: "This expression is too complex for the guided builder. You can edit it in raw mode."
  - "Stay in Editor" and "Try Builder anyway" options (Try = populate what can be populated, mark rest as custom)
- **Expression synchronization:**
  - Both modes share the same expression string (single source of truth in `useExpressionBuilder`)
  - Switching modes does not lose the expression
  - Edits in either mode update the shared expression state

### Out of Scope

- The raw editor component itself (T-02)
- The guided builder component itself (T-05/T-06)
- Autocomplete or validation (T-03/T-04)
- Undo/redo of mode switches

## Change Requirements

- Create `ui/src/features/mappings/lib/ast-decomposer.ts`:
  - `decomposeExpression(expression: string): DecompositionResult`
  - Uses `parse(expression, { registry: defaultRegistry })` to get AST
  - If parse fails: return `{ success: false, reason: "Expression has syntax errors" }`
  - Walk AST and match against supported patterns:
    - Root is `FunctionCall("source", [StringLiteral])` → Direct Copy
    - Root is `FunctionCall("static", [Literal])` → Static Value
    - Root is `FunctionCall(name, args)` where all args are simple (source/static/literal/item) → Single transform with args
    - Root is `FunctionCall("map", [source, ObjectTemplate])` where template values are simple → Array map
    - Root is `FunctionCall("filter", [source, FunctionCall(comparison, [item, literal])])` → Array filter
    - Else → `{ success: false, reason: "..." }`
  - Return `BuilderState` that can directly populate the GuidedBuilder
  - Define "simple argument": StringLiteral, NumberLiteral, BooleanLiteral, NullLiteral, or FunctionCall("source"|"static"|"item"|"parent", [StringLiteral])

- Create `ui/src/features/mappings/components/ComplexExpressionWarning.tsx`:
  - Props: `reason: string`, `onStayInEditor: () => void`, `onTryBuilder: () => void`
  - Renders warning banner with amber styling
  - Shows reason text
  - Two action buttons: "Stay in Editor" (primary), "Try Builder" (secondary/ghost)

- Update `use-expression-builder.ts`:
  - Add `switchToEditor()`: trivial — just set mode to 'editor'
  - Add `switchToBuilder()`: run decomposition, handle success/failure
  - Add `canDecompose: boolean` (eagerly computed or lazy on toggle)
  - Add `decompositionWarning: string | null` state
  - On successful decomposition: update builder state fields (selectedSourceFields, selectedFunction, argumentValues, etc.)

- Update `ExpressionBuilderPanel.tsx`:
  - Mode toggle calls `switchToEditor()` / `switchToBuilder()` (not raw setMode)
  - When decomposition fails, show `ComplexExpressionWarning` instead of builder content
  - "Try Builder" partially populates whatever is possible and shows gaps

  - `source("name")` → success, Direct Copy state

  - `concat(source("first"), source("last"))` → success, function with 2 source args
  - `if(eq(source("x"), 10), static("yes"), static("no"))` → success (if supported) or failure with reason

## Blockers / Risks

- AST decomposition complexity: the number of patterns to recognize could grow — keep it simple for Phase 0 (cover the 80% from spec: source, static, single-function, map, filter)
- Builder state shape must align between what T-05/T-06 produce and what the decomposer generates — use the same `BuilderState` type

## Notes

- The decomposer does NOT need to handle every valid DSL expression — it handles the common 80% and gracefully falls back to raw editor for the rest
- "Try Builder" option is a stretch goal — if complex, it can show the outermost function selected and mark arguments as "custom (edit in raw mode)"
- This task depends on both T-02 (raw editor) and T-05 (guided builder) being implemented, since it bridges the two modes
