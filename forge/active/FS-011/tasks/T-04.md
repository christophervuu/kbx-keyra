## Summary

Integrate the engine's `parse()` function into the raw DSL editor for real-time inline validation. Parse the expression on every change (debounced 300ms), map diagnostic character positions to editor positions, and render error indicators (red underline + tooltip) inline. Invalid expressions are not committed to the rule state.

---

## Scope

### In Scope

- `useDslValidation()` hook:
  - Accept expression string
  - Debounce parse() calls by 300ms
  - Call engine `parse(expression, { registry: defaultRegistry })` for full validation
  - Map returned diagnostics (with character offsets) to editor error decorations
  - Track validation state: valid/invalid/validating
  - Return: `{ diagnostics, isValid, isValidating, errorDecorations }`
- Error decoration data model:
  - `{ start: number; end: number; message: string; code: string; severity: 'error' | 'warning' | 'info' }`
  - Maps to underline positions in the editor overlay
- Editor error rendering:
  - Red wavy underline on error character ranges
  - Yellow underline for warnings (E002 unknown function, E003 arity)
  - Tooltip on hover showing error code + message
- Integration with `useExpressionBuilder`:
  - Only commit expression to rule state when `isValid === true`
  - Show "uncommitted" indicator when expression is locally modified but invalid
- Error tooltip component:
  - Positioned relative to the error underline
  - Shows: error code (styled), message text
  - Appears on hover/focus of error range
  - Dismisses on blur/mouseout

### Out of Scope

- Semantic validation (source path existence, type compatibility) — handled by `useEngineValidation()` at mapping level
- Autocomplete (T-03)
- Guided builder validation (T-06 handles step-level validation)
- Fix suggestions (Phase 2 AI)

## Change Requirements

- Create `ui/src/features/mappings/hooks/use-dsl-validation.ts`:
  - Hook accepts `expression: string`
  - Uses `useRef` for debounce timer (300ms)
  - Calls `parse(expression, { registry: defaultRegistry })` after debounce
  - Maps `ParseResult.diagnostics` to `ErrorDecoration[]`:
    - Each diagnostic with `location` data produces a decoration
    - If no character position in diagnostic, underline the full expression
    - Fatal errors (KEYRA-E001, KEYRA-E004): `success === false`, severity error
    - Registry warnings (KEYRA-E002, KEYRA-E003): `success === true`, severity warning
  - Returns: `{ parseResult, diagnostics, isValid, isValidating, errorDecorations }`
  - `isValid` = parseResult.success (syntax is valid)

- Update `RawDslEditor.tsx`:
  - Accept `errorDecorations?: ErrorDecoration[]` prop
  - Render error decorations in the overlay layer:
    - For each decoration, apply underline styling to the character range
    - Error: red wavy underline (`decoration-wavy decoration-red-500 underline`)
    - Warning: yellow underline (`decoration-wavy decoration-yellow-500 underline`)
  - On hover over error-decorated range: show `ErrorTooltip`
  - Error decorations do not interfere with syntax highlighting (both layers coexist)

- Create `ui/src/features/mappings/components/ErrorTooltip.tsx`:
  - Props: `code: string`, `message: string`, `severity: string`, `position: { top: number; left: number }`
  - Renders small tooltip card with code badge and message
  - Styled per severity (red border for error, yellow for warning)
  - Positioned absolutely relative to editor

- Update `use-expression-builder.ts`:
  - Integrate `useDslValidation()` result
  - Only debounce-commit to `updateRule()` when `isValid === true`
  - When expression is modified but invalid: set local `uncommitted` flag
  - Expose `isValid`, `uncommittedExpression` in hook return

## Blockers / Risks

- Engine parse diagnostics may not always include precise character offsets for all error types — implement graceful fallback (underline full expression)
- The 300ms debounce timing is shared with the commit debounce — ensure they don't conflict (validation should fire independently of commit)

---

## Notes

- The validation here is pure syntax validation (can the expression be parsed?). Semantic validation (does the source path exist? type match?) is handled at the mapping level by `useEngineValidation()` in FS-010.
- Use `{ registry: defaultRegistry }` in parse options to also catch unknown function names and arity mismatches during typing — these show as warnings, not errors (expression is still syntactically valid).
- The "uncommitted expression" pattern ensures the rule list always has valid expressions while the user is mid-edit.
