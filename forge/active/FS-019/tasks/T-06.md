## Objective

Write E2E tests that verify form validation, error messages, and graceful handling of edge cases and error states.

## Context

Users will inevitably submit forms with missing or invalid data. These tests ensure the app provides clear feedback without crashing. They complement happy-path tests by exercising the "unhappy" paths through the application.

## Requirements

### Form Validation (`tests/e2e/specs/validation.spec.ts`)

**Project Form**
- Submit empty project form — verify required field errors appear
- Submit with name too short/long (if constraints exist) — verify error message
- Verify error messages clear when valid input is provided
- Verify form does not navigate away on validation failure

**Schema Upload**
- Attempt to upload a non-JSON file — verify error feedback
- Attempt to upload invalid JSON (not a valid JSON Schema) — verify error message
- Verify the schema list is unchanged after failed upload

**Mapping Form**
- Submit mapping form without selecting schemas — verify errors
- Attempt to create a mapping with no project context — verify appropriate handling

### Edge Cases
- Navigate to a project that doesn't exist (stale bookmark) — verify graceful handling
- Navigate to a schema that doesn't exist — verify graceful handling
- Navigate to a mapping that doesn't exist — verify graceful handling
- Verify the app doesn't crash with corrupted localStorage data
- Verify the app handles empty state gracefully (no projects, no schemas)

### Error Boundaries
- Verify that if a component throws, the error boundary catches it (may need to simulate)
- Verify error boundary displays a user-friendly message

## Acceptance Criteria

- [ ] `tests/e2e/specs/validation.spec.ts` exists and passes
- [ ] Empty form submissions show appropriate validation errors
- [ ] Error messages are visible and associated with correct fields
- [ ] Invalid navigation (bad IDs) doesn't crash the app
- [ ] Empty states (no data) render appropriate UI (empty state messages)
- [ ] Form errors clear when corrected input is provided
- [ ] App remains functional after encountering errors (can navigate away)

## Notes

- Use `page.getByRole('alert')` or `data-testid` for error message selectors
- For invalid file uploads, create small fixture files: `invalid.txt`, `not-schema.json`
- Store error fixture files in `tests/e2e/fixtures/invalid/`
- The "corrupted localStorage" test should set malformed JSON and verify the app recovers
- Empty state tests require starting with completely clean localStorage (no seed)
- These tests may be more brittle than happy-path — use resilient selectors
