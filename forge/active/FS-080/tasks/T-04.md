## Summary

Emit consistent structured telemetry/logging for CDM GitHub read flows so incidents can be diagnosed using operation context, retry behavior, failure class, and request lineage identifiers.

---

## Scope

### In Scope

- Add/standardize log payload fields for CDM read operations and retries.
- Ensure fields include operation, repo/path, status code, retry count, failure class, correlation/request IDs, and retry-after metadata when available for rate-limited responses.
- Emit both per-attempt and terminal outcome logs at appropriate levels.
- Add tests around logger payload shape where practical.

### Out of Scope

- External log pipeline/alerting stack rollout.
- Dashboard authoring and SLO management.
- Non-CDM subsystem logging redesign.

## Change Requirements

- Emit required observability fields consistently for failure and success where relevant.
- Preserve request lineage (`requestId`/`correlationId`) through retries.
- Ensure retry attempt logs include attempt index/count and retry decision reason.
- Ensure terminal sync failure log is present and class-tagged.

---

## Verification Requirements

- Verify required fields are present in structured logs for representative failure classes (AE-06).
- Verify retry logs show incrementing retry count with bounded terminal condition (AE-02).
- Verify terminal sync failures produce explicit classed log entries (AE-05).

---

## Acceptance Checks

- Logs include operation, repo/path, statusCode, retryCount, failureClass, and request lineage IDs.
- Retry attempt logs and terminal outcome logs are both emitted.
- Log payloads are consistent across browse/link/sync failure paths.
- `forge/architecture/project-structure.md` updated if new files/folders are created.

---

## Blockers / Risks

- Inconsistent field naming across modules can degrade incident triage quality.
- Missing request lineage propagation can break cross-layer debugging.

---
