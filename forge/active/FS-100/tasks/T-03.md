## Summary

Implement SANDBOX deploy command path that builds immutable snapshot artifacts from saved mapping versions, validates readiness/schema policy, and atomically updates active snapshot pointers with idempotency guarantees.

---

## Scope

### In Scope

- Deploy API request/response contract updates.
- Snapshot assembly/hash generation and S3 persistence.
- Deployment record write + active pointer conditional update ordering.
- Idempotency key handling for repeated deploy requests.
- SANDBOX schema promotability tagging.

### Out of Scope

- Promotion across higher environments.
- UI card/action rendering.

---

## Relevant Areas

- `src/lambda/deployment/deploy-mapping.ts`
- `src/lib/persistence/{deployments.ts,deployment-orchestrations.ts}`
- `src/lib/persistence/s3/deployment-snapshot.ts`
- `src/lambda/shared/{request.ts,response.ts,errors.ts}`

---

## Change Requirements

- Deploy route accepts only SANDBOX in normal pipeline path.
- Snapshot is immutable, content-hashed, and verified readable before pointer update.
- Active pointer update must be last write and conditionally safe.
- Idempotency key replay returns deterministic prior result.
- Deployment record must persist who/when/source version/snapshot metadata.

---

## Verification Requirements

- Unit/integration tests for atomic ordering and idempotent replay.
- Failure-path test ensuring incomplete artifacts never become active.
- Tests for SANDBOX-only deploy route gating.

---

## Acceptance Checks

- SANDBOX deploy creates exactly one immutable snapshot per new operation.
- Pointer updates only after artifact verification.
- Duplicate idempotency requests do not produce duplicate operations.
- SANDBOX deployments with non-promotable schema provenance are flagged accordingly.

---

## Blockers / Risks

- Race conditions on concurrent deploy attempts for same mapping.

---
