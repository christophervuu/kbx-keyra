## Summary

Define the `BuilderValidationState`, `BuilderValidationIssue`, and `OutputTypeMismatch` types and implement the `useBuilderValidation` hook. This hook is the validation orchestrator for the Builder panel — it performs structural completeness checks against `ExpressionBuilderState` by mode, integrates output type inference via the engine boundary layer, and returns a combined validation state that downstream components and gating logic consume.

---

## Change Requirements

The `useBuilderValidation` hook must:

1. Accept these inputs:
   - `builderState: ExpressionBuilderState | null` — null in Editor mode
   - `expression: string` — the current DSL expression string
   - `targetType: string` — the target field's schema type
   - `mode: 'builder' | 'editor'` — current authoring mode
   - `parseResult: ParseResult | null` — from `useDslValidation`
   - `isParseValid: boolean` — from `useDslValidation.isValid`

2. Perform structural validation (synchronous, no debounce) when `mode === 'builder'` and `builderState` is non-null. Return `structureValid: true` and empty `structureIssues` when in Editor mode.

3. Perform output type inference when `parseResult` is available and successful. Use the engine's AST-based type inference to determine the expression's output type. Compare against `targetType` using the compatibility matrix from the spec.

4. Expose a `BuilderValidationState` object with `structureValid`, `structureIssues`, `outputTypeValid`, `outputTypeMismatch`, `canApply`, `canSave`.

5. `canApply` = `(mode === 'editor' ? isParseValid : (structureValid && isParseValid)) && expression.trim().length > 0`

6. `canSave` = `canApply && outputTypeValid`

For engine type inference integration:
- Check if `inferExpressionType` is available through the existing `ui/src/lib/engine/` barrel. If not, add a re-export.
- The engine's `inferExpressionType(ast, schemaTree?, registry?)` returns a `ValueType | undefined`. `undefined` means inference was uncertain — treat as compatible (no mismatch).
- The hook should handle cases where the AST is null (parse failed) — skip type inference.

## Verification Requirements

- Unit tests covering:
  - Value mode: empty state → `missing_source`. Source selected, no transforms → valid. Source + transform with missing arg → `incomplete_transform`.
  - Conditional mode: no conditions → `missing_condition`. Condition missing operand → `incomplete_condition`. Missing then → `missing_then`. Missing else → `missing_else`. Complete → valid.
  - Value Map mode: no source → `missing_source`. No rows → `empty_map_rows`. No default → `missing_default`. Complete → valid.
  - Editor mode: always `structureValid: true` regardless of builder state.
  - Output type: `number` expression vs `string` target → mismatch. `string` vs `string` → match. `unknown` inferred → match (no mismatch). Null parse result → no inference (match by default).
  - `canApply` and `canSave` derivation for various combinations.
- `pnpm tsc --noEmit` passes.
- `pnpm lint` passes.

## Notes

- The structural validation logic inspects `ExpressionBuilderState` directly — it does not parse DSL or invoke the engine. It is a pure function over the discriminated union state.
- Output type inference uses the engine's existing AST-based inference, which is best-effort. When uncertain, it returns `undefined` — the hook must treat this as "no mismatch" to avoid false positives.
- This hook does not replace `useDslValidation`. Both run in parallel: `useDslValidation` for parse-level syntax, `useBuilderValidation` for structural + type. They are composed in `ScalarFieldBuilder`.
