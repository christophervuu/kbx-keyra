## Summary

Add backend-enforced deploy-context validation that evaluates mapping-referenced CDM schemas before deploy/promote and blocks requests with deterministic schema-level reasons when any referenced CDM schema is not deployable.

---

## Scope

### In Scope

- Add/extend deployment pre-check logic in deploy and promote handlers.
- Validate CDM schema sync status, ingest readiness, and source metadata completeness.
- Return blocking error payload with schema-specific reason codes (stable API enum values: `unsynced`, `update-failed`, `metadata-incomplete`, `ingest-not-ready`, `schema-missing`), reference role per schema (`source`/`target`), and remediation hint keys.
- Ensure no deployment history/current-pointer write occurs when blocked.
- Add backend tests for blocked and unblocked paths.

### Out of Scope

- Deployment page UI rendering updates.
- Auto-sync behavior during deploy attempt.
- Non-CDM deployability rule redesign.

## Change Requirements

- Introduce a reusable deploy-context validator for referenced CDM schemas.
- Enforce validator invocation before deployment writes for both deploy and promote flows.
- Implement deterministic reason taxonomy for blocking causes:
  - unsynced
  - update-failed
  - metadata-incomplete
  - ingest-not-ready
  - optional canonical extension for schema-missing if chosen during execution
- Structure error envelope data so UI can render schema-specific reason + remediation CTA.
- Preserve existing deployability matrix behavior and error contracts for unrelated validations.
- `schema-missing` must be a distinct reason code from `metadata-incomplete` (missing schema ID vs incomplete metadata fields).

---

## Verification Requirements

- Add/extend unit/integration tests to cover:
  - deploy blocked on invalid referenced CDM schema state (AE-01)
  - promote blocked on invalid referenced CDM schema state (AE-01)
  - schema-specific reason payload shape (AE-02)
  - previously blocked schema unblocks after valid sync/ingest state (AE-03)
  - fully valid CDM references are not blocked (AE-05)
- Run typecheck and touched deployment handler test suites.

---

## Acceptance Checks

- Deploy request is blocked when referenced CDM schema state is invalid.
- Promote request is blocked when referenced CDM schema state is invalid.
- Block response includes schema identity + exact reason code per blocking schema.
- Guardrail does not block when all referenced CDM schemas are valid.
- No deployment write side effects occur on blocked requests.
- `forge/architecture/project-structure.md` updated if new files/folders are created.

---

## Blockers / Risks

- Potential legacy status-value mismatch between schema metadata producers and deployment validator.
- Mapping→schema reference resolution may vary by endpoint path and require careful normalization.

---

## Notes

- Keep validator pure and reusable to avoid drift between deploy and promote handlers.
- Prefer enum-like stable reason codes over free-form strings.
