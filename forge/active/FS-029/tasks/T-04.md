## Summary

Export the engine's supported date format tokens (`YYYY`, `MM`, `DD`, `HH`, `mm`, `ss`, `ISO8601`) for UI consumption, and create a `PARAMETER_HINTS` registry that maps `(functionName, parameterName)` pairs to their hint sources (dropdowns, known values). This enables the Argument Form to show contextual suggestions derived programmatically from the engine rather than a static curated list.

---

## Scope

### In Scope

- Export `SUPPORTED_FORMAT_TOKENS` from `src/engine/functions/date.ts` (or a dedicated export module) — includes the `TOKENS` array values plus `ISO8601`.
- Export common format compositions (e.g. `YYYY-MM-DD`, `MM/DD/YYYY`, `YYYY-MM-DDTHH:mm:ssZ`) derived from the base tokens as suggested presets.
- Create `ui/src/lib/data/parameter-hints.ts` with:
  - `PARAMETER_HINTS` map: `Record<string, Record<string, ParameterHint>>` keyed by `functionName` → `parameterName` → hint config.
  - `ParameterHint` type: `{ type: 'enum', options: string[] } | { type: 'tokens', tokens: string[], presets: string[] }`.
  - Entries for:
    - `formatDate.inputFormat` → tokens + presets from engine export.
    - `formatDate.outputFormat` → tokens + presets from engine export.
    - `cast.targetType` → enum: `['string', 'number', 'boolean']`.
- Wire the engine export into the UI parameter hints (import path or build-time extraction).

### Out of Scope

- UI rendering of the hints (that's T-03's ArgumentForm).
- Changes to the engine's date parsing/formatting logic.
- Adding new format tokens to the engine.

## Change Requirements

- The engine's `TOKENS` constant and `ISO8601` keyword must be exported in a way consumable by the UI build.
- `PARAMETER_HINTS` must be type-safe and extensible (easy to add new function/parameter hint entries in the future).
- The format token presets should be compositions of base tokens (demonstrating common date format patterns) — derived, not hardcoded magic strings.
- `cast.targetType` options should align with what the engine's `cast` implementation actually supports.
