## Summary

Implement the multi-level array-specific validation model (collection, item-template, leaf-output, final-output) with the critical distinction between incomplete draft state and real validation errors. Integrate validation feedback into the pinned BuilderFeedbackArea and per-field indicators within the item template. Incomplete fields show muted indicators during editing; they become blocking at save/final validation time.

---

## Scope

### In Scope

- `ArrayValidationState` type: collection-level, item-level, leaf-level, and final-output validation results
- `deriveArrayValidation(state: ArrayBuilderState, sourceSchema, targetSchema): ArrayValidationState` pure function
- Collection-level validation:
  - Source must resolve to array type in source schema
  - Filter predicate must produce boolean
  - Merge branches must each resolve to arrays
  - Build-from-values entries must be structurally valid
- Item-template validation:
  - Required target item fields must be present
  - Item template shape must match target schema item type
  - Nested array validity
- Leaf-output validation:
  - Each mapped field's output type must be compatible with target field type
- Final-output validation:
  - Generated expression must parse successfully
  - Result type must match target array schema
- Incomplete vs Invalid visual distinction:
  - Incomplete: muted/gray indicators (empty circle, "Not yet mapped" label)
  - Invalid: red error indicators (error icon, error message)
- `BuilderFeedbackArea` integration:
  - Expression row: shows generated DSL (or "Expression (incomplete)" when state is incomplete)
  - Validation row: shows collection validation status + item coverage + leaf type compatibility
- Per-field indicators in `ItemFieldRow`:
  - Unmapped required: gray incomplete indicator
  - Mapped valid: green check
  - Mapped invalid: red error with message
  - Unmapped optional: no indicator (or faint optional label)
- Array node status badge in Target Worklist:
  - Not started: default
  - In progress: yellow/amber indicator
  - Complete: green check
  - Has errors: red error

### Out of Scope

- Engine-level validation changes
- Validation for custom expression mode (uses engine parse/validate directly)

## Change Requirements

- Create `ui/src/features/mappings/lib/array-validation.ts`:
  - `deriveArrayValidation()` pure function
  - Collection validation: check source path against source schema, filter predicate return type, merge branch source types
  - Item validation: check required fields against `itemTemplate.fields`, nested array recursive validation
  - Leaf validation: type-compatibility check for each mapped field's chain output vs target field type
  - Final validation: parse generated expression via engine `parse()`, check result type
  - Return `ArrayValidationState` with per-level arrays of validation entries (each entry has: level, field path, message, severity: 'incomplete' | 'warning' | 'error')
- Update `ArrayBuilder.tsx`:
  - Render `BuilderFeedbackArea` in pinned position (above scrollable content)
  - Expression row: show generated expression or "(incomplete)" label
  - Validation row: show summary from `ArrayValidationState` — error count, warning count, incomplete count
- Update `ItemFieldRow.tsx`:
  - Show validation indicator per field: incomplete (gray), valid (green), error (red)
  - Tooltip on hover showing validation message for errors
- Update `use-target-status.ts`:
  - Derive array node status from `deriveCompletionStatus()` — map to existing status categories
- Incomplete vs Invalid distinction:
  - During editing: incomplete fields are muted, not error-styled. Only real validation errors (type mismatch, source not found, boolean violation) show as errors.
  - At save time: incomplete required fields remain as-is (save is never blocked in the current model per FS-039). Validation feedback persists after save.

---

## Notes

- The distinction between incomplete and invalid is a key UX requirement. Non-technical users should not see red errors when they simply haven't finished mapping all fields yet. The error indicators should be reserved for genuine issues.
- Validation runs derivatively (computed from state) rather than as an explicit user action. It updates as the user configures the builder.
