## Summary

Create the canonical Smart Fix backend flow so rule-level diagnostic inputs are validated, enriched with schema context, sent through the shared AI runtime, and returned as a validation-aware corrected-expression suggestion artifact.

---

## Scope

### In Scope

- Implement/update Smart Fix Lambda handler request validation and response contract.
- Accept deterministic rule/diagnostic context inputs (mapping/rule identity, target path, failing expression, diagnostic code/message), with default diagnostics scope = all diagnostics on selected rule and optional explicit single-diagnostic scope.
- Assemble backend-owned schema/mapping context for prompt variables.
- Invoke Smart Fix prompt through shared runtime.
- Validate returned corrected expression and include `validation.valid` + diagnostics in response.
- Enforce context envelope guardrail (~64KB / ~8k tokens) and truncation priority (latest/high-severity diagnostics first).
- Include request-time `ruleVersion`/`ruleHash` snapshot handling for stale-apply protection support.
- Normalize request/runtime/provider/parser errors to canonical backend envelope.
- Add backend tests for success, invalid suggestion, and failure paths.

### Out of Scope

- UI component/hook behavior.
- Adapter method/type updates outside backend contract needs.
- Prompt authoring/admin tooling.
- Batch/multi-rule Smart Fix.

## Change Requirements

- Smart Fix request contract is rule-scoped and includes diagnostic identity fields required by FS-071, with all-diagnostics default scope and optional single-diagnostic scope.
- Backend constructs Smart Fix context server-side; UI does not pass prebuilt large context blobs.
- Smart Fix response includes original expression, corrected expression, explanation, and validation metadata.
- Invalid generated expressions are returned as invalid suggestions, not apply-ready success artifacts; no “apply anyway” path is exposed by contract.
- Error status/code mapping follows canonical AI endpoint conventions.
