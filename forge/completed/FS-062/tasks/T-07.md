## Summary

Configure SAM's esbuild integration for Lambda function bundling. Each function should be independently bundled with tree-shaking, AWS SDK externalized, and source maps for non-production builds. Add a build verification script that reports bundle sizes and fails if any exceed 5MB.

---

## Scope

### In Scope

- SAM `Metadata.BuildMethod: esbuild` and `BuildProperties` on each function (or via shared configuration)
- esbuild configuration: target `node20`, format `esm` or `cjs`, tree-shaking, external `@aws-sdk/*`
- Source map generation for dev/staging (configurable)
- Bundle size reporting script (`scripts/check-bundle-sizes.sh` or `.ts`)
- 5MB per-function bundle size threshold
- TypeScript compilation settings compatible with esbuild bundling

### Out of Scope

- Lambda layers (evaluate if needed for shared code, but prefer bundling per-function)
- Custom webpack or rollup configurations
- Production optimization beyond tree-shaking (minification is optional)
- CI/CD pipeline integration (separate spec)

---

## Relevant Areas

- `template.yaml` (modify — add BuildProperties to functions)
- `scripts/check-bundle-sizes.sh` or `scripts/check-bundle-sizes.ts` (new)
- `tsconfig.json` (may need verification of compatibility)

---

## Change Requirements

For each `AWS::Serverless::Function` in `template.yaml`, add Metadata section:

```yaml
Metadata:
  BuildMethod: esbuild
  BuildProperties:
    Minify: false
    Target: 'node20'
    Sourcemap: true
    EntryPoints:
      - handler.ts  # (or the specific entry point file)
    External:
      - '@aws-sdk/*'
```

Alternatively, if SAM supports shared build properties via Globals (verify), configure once there.

Create bundle size verification:
- After `sam build`, iterate `.aws-sam/build/*/` directories
- Report each function's total size
- Fail with non-zero exit if any function exceeds 5MB
- Output: table of function name → bundle size

Ensure `tsconfig.json` (or relevant TS config) has settings compatible with esbuild:
- `module`: `ESNext` or `CommonJS` (depending on chosen format)
- `moduleResolution`: `bundler` or `node`
- Decorators, paths, and other features that esbuild doesn't support should not be used in Lambda code

---

## Verification Requirements

- `sam build` completes successfully for all functions
- Each function produces an independent bundle (no shared node_modules)
- `@aws-sdk/*` is not included in any bundle
- Bundle sizes are reported and all < 5MB
- Source maps are present in dev builds

---

## Acceptance Checks

- All Lambda functions in template have esbuild BuildMethod configured
- `sam build` succeeds (with stub handlers if full implementations don't exist yet)
- `@aws-sdk/*` is marked external and not bundled
- Bundle size check script exists and runs
- No bundle exceeds 5MB threshold
- Source maps are generated

---

## Blockers / Risks

- SAM esbuild integration requires SAM CLI >= 1.78. Ensure local tooling is compatible.
- If Lambda handler files don't exist yet, `sam build` will fail. May need to create minimal stubs (export an empty handler function) for build verification to work.

---

## Notes

- SAM's built-in esbuild support is preferred over a custom build script because it handles the bundling → packaging → upload workflow seamlessly.
- The `External: ['@aws-sdk/*']` setting is critical: AWS SDK v3 is available in the Node.js 20.x Lambda runtime. Bundling it would waste bundle size.
- Each function gets its own bundle (not a monolithic package). This keeps cold starts fast by loading only the code each function needs.
- If shared utility code in `src/lambda/shared/` is used by all handlers, esbuild will inline it into each bundle. This is acceptable for Phase 1 scale.
