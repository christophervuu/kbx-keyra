## Summary

Create a new `decomposeExpression()` function that parses DSL expression strings and maps them back into the `ExpressionBuilderState` model. The decomposer **auto-detects expression type** (value pipeline, conditional, value map) from the AST structure and returns the corresponding state with the correct `mode` field, enabling the UI to auto-switch to the appropriate builder tab.

---

## Scope

### In Scope

- Implement `decomposeExpression(expression: string): PipelineDecompositionResult` in a new file.
- Pipeline detection: recognize nested single-argument transform chains (e.g., `lower(trim(source("x")))`) and decompose into Value mode state with ordered transforms.
- Conditional detection: recognize `if(condition, then, else)` as the outer call and decompose into Conditional mode state. Detect nested `if()` in else branch as else-if chains.
- Value Map detection: recognize `valueMap(source, mappings, fallback)` and decompose into Value Map mode state.
- Simple source detection: `source("x")` -> Value mode with 1 source, no transforms.
- Static value detection: `static(...)` -> Value mode with static value.
- Transforms with additional parameters: extract parameter values from the AST and populate `TransformParameterValue[]`.
- Failure cases: unsupported function nesting, expressions that don't fit any mode pattern, or nesting depth beyond limit -> return `{ success: false, reason: "..." }`.
- Decomposition depth limit: configurable, default 5 levels for pipeline, 5 levels for conditional nesting (matches the form's 5 else-if cap).
- Unit tests covering success and failure cases, including mode auto-detection verification.

### Out of Scope

- UI components or mode toggle logic (T-07).
- Modifying the existing `ast-decomposer.ts` (the new decomposer is a parallel file; old one removed in T-07).
- Changes to the parser or engine.

## Change Requirements

**Decomposer function** (`pipeline-decomposer.ts`):

- Export `decomposeExpression(expression: string): PipelineDecompositionResult`
- `PipelineDecompositionResult = { success: true; state: ExpressionBuilderState } | { success: false; reason: string }`

**Detection algorithm:**

1. Parse expression using `parse()` from `ui/src/lib/engine/`.
2. If parse fails -> return failure with reason from diagnostics.
3. Examine the root AST node:
   - If root is `FunctionCall` with name `valueMap` -> attempt Value Map decomposition.
   - If root is `FunctionCall` with name `if` -> attempt Conditional decomposition.
   - If root is `FunctionCall` with name `source` -> Value mode, single source, no transforms.
   - If root is `FunctionCall` with name `static` -> Value mode, static value.
   - If root is `FunctionCall` with name matching a transform function -> attempt pipeline decomposition (walk nested first arguments until reaching `source()`).
   - Otherwise -> failure.

**Pipeline decomposition:**

- Walk the nested `FunctionCall` chain: each outer call is a transform step. The first argument of each call is the inner expression. Additional arguments are parameter values.
- Resolve parameter names by matching against `DSL_FUNCTION_CATALOG` entry for the function.
- Innermost call must be `source("path")` for a valid pipeline.
- Build `TransformStep[]` in pipeline order (innermost = first step).
- If any node in the chain is not a recognized transform or the chain exceeds max depth -> failure.

**Conditional decomposition:**

- Extract condition from first argument of `if()`. Detect comparison operator from the condition function name.
- Extract then/else branches. If else is another `if()`, detect as else-if (recursive).
- Map branch values to `BranchValue` (literal -> static, `source()` -> source, other -> expression string).

**Value Map decomposition:**

- First arg: must be `source("path")` -> `inputSource`.
- Second arg: must be `ObjectTemplate` -> convert properties to `ValueMapEntry[]`.
- Third arg: fallback value (literal or null).

## Verification Requirements

- Unit tests for pipeline decomposition:
  - `source("email")` -> Value mode, 1 source, 0 transforms
  - `upper(trim(source("name")))` -> Value mode, 1 source, 2 transforms [trim, upper] (AE-09)
  - `substring(source("code"), 0, 3)` -> Value mode, 1 source, 1 transform with params
- Unit tests for conditional decomposition:
  - `if(eq(source("status"), "active"), "Yes", "No")` -> Conditional mode (AE-04 roundtrip)
  - `if(eq(source("p"), "h"), "1", if(eq(source("p"), "m"), "2", "3"))` -> nested conditional
  - `if(gt(source("amount"), 100), "high", "low")` -> Conditional mode with mode auto-detection (AE-16)
- Unit tests for value map decomposition:
  - `valueMap(source("country"), {"US": "United States"}, "Unknown")` -> Value Map mode
- Unit tests for failure cases:
  - Complex expression (AE-10) -> `{ success: false, reason: "..." }`
  - Unsupported function -> failure
  - Max depth exceeded -> failure
- Roundtrip tests: `generateExpressionFromState(decomposeExpression(expr).state) === expr` for canonical forms.
- Typecheck passes
- Lint passes

## Notes

- The existing `ast-decomposer.ts` uses a max depth of 3 and a limited `BUILDER_SUPPORTED_FUNCTIONS` set. The new decomposer should be more permissive (support all catalog functions as transform steps) with a higher depth limit (5).
- For the "Complex expression" fallback, the reason string should be human-readable: e.g., "Expression uses unsupported nesting pattern" or "Function '{name}' is not supported in the guided builder."
- Parameter name resolution from the catalog: when extracting additional parameters from a function call AST, match the argument index to the catalog entry's `parameters` array to derive the `name` and `type` fields for `TransformParameterValue`.
