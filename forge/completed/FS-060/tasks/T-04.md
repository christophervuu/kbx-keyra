## Summary

Write the Playwright E2E spec files that exercise adapter parity across the four required domains: project CRUD, mapping CRUD, schema upload/load, and error handling. These specs are written once and run identically in both `localStorage` and `httpBackend` modes via the dual-project Playwright configuration.

---

## Scope

### In Scope

- `tests/e2e/specs/project-crud.spec.ts`:
  - Create project with name/description
  - Verify project appears in list
  - Navigate to project overview
  - Update project name
  - Delete project and verify removal
- `tests/e2e/specs/mapping-crud.spec.ts`:
  - Create mapping within a seeded project
  - Open mapping editor
  - Select a single target field and enter a simple expression (e.g., `source("fieldName")`)
  - Save the mapping
  - Navigate away and return to the mapping → verify rule persisted
  - Duplicate mapping → verify copy exists with same rule
  - Delete mapping → verify removal
- `tests/e2e/specs/schema-flows.spec.ts`:
  - Upload a JSON schema fixture file
  - Navigate to schema detail page
  - Verify schema metadata renders
  - Verify schema tree renders expected fields
  - Reference schema in a project
- `tests/e2e/specs/error-handling.spec.ts`:
  - Navigate to non-existent project URL → verify error state
  - Navigate to non-existent mapping URL → verify error state
  - Attempt to create project with invalid/empty data → verify validation feedback
- All specs use:
  - Unified `seedData()` / `resetData()` from fixtures
  - Page objects for interactions
  - Deterministic factory data for assertions

### Out of Scope

- AI, deployment, template, or GitHub flows
- Full mapping editor authoring (complex multi-step DSL building)
- Cross-browser testing
- Performance assertions
- Visual regression

## Change Requirements

- Every spec must be adapter-agnostic: no conditional logic based on which mode is active
- Tests must follow seed → execute → assert → teardown isolation pattern
- Use `test.describe()` for logical grouping within each spec file
- Assertions must verify user-visible state (text content, element presence/absence) not implementation details
- Each spec file should be independently runnable (`npx playwright test specs/project-crud.spec.ts`)
- All tests must pass in under 10 seconds individually (per `e2e-testing.md` budget)
- Tests must not depend on execution order within or across files

---

## Verification Requirements

- All specs pass in `localStorage` project: `npx playwright test --project=localStorage`
- All specs pass in `httpBackend` project: `npx playwright test --project=httpBackend`
- Both runs produce identical pass/fail results
- No test contains adapter-mode-specific conditional logic
- Total suite duration < 60 seconds per mode (per `e2e-testing.md` budget)

## Blockers / Risks

- UI must have sufficient `data-testid` attributes for page objects to locate elements — if missing, page objects from T-03 may need fallback strategies (ARIA roles, text content)
- Mapping editor interactions may be complex; keep to minimum viable interactions (single field + save/verify)
- Error state rendering depends on how the UI surfaces errors for non-existent routes — verify actual behavior before asserting

---

## Notes

- Start with `project-crud.spec.ts` as the simplest domain; use it to validate the full pipeline works before writing other specs
- For mapping editor tests, the minimum viable interaction is: open editor → select a target field → type an expression → save → verify on reload
- Error handling tests should verify the error UI renders (not the specific error message text, which may differ between adapters if messaging is adapter-specific)
- If any test surfaces a genuine behavioral difference between adapters, that's a finding — document it and verify whether it's acceptable or a bug
