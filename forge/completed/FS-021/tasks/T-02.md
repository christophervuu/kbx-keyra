## Summary

Introduce a two-tier persistence model in the Mapping Editor: "Apply" commits the current rule expression to the working session (in-memory), and "Save" persists the entire working config to storage. This includes renaming the builder's "Save mapping" button to "Apply", tracking unsaved change count, wiring the global Save button and Ctrl+S shortcut, and implementing navigation guards for both unapplied builder edits and unsaved session changes.

---

  - `unsavedRuleCount: number` tracking
  - `hasUnappliedExpression: boolean` state

  - `canNavigateAway()` and navigation guard logic

## Change Requirements

- **`useMappingEditor` hook changes:**
  - Add `unsavedRuleCount` state (starts at 0, increments on each `applyRule` call, resets on `save()`).
  - Add `hasUnappliedExpression` state (set by builder components when expression text differs from the committed rule).
  - Add `applyRule(targetPath: string, expression: string)` — upserts the rule in the working config, increments `unsavedRuleCount`.
  - Modify existing `save()` to reset `unsavedRuleCount` to 0 on success.
  - Add `canNavigateAway(): { allowed: boolean; reason: 'unapplied' | 'unsaved' | null }`.
  - Maintain existing `beforeunload` handler but ensure it fires on both unapplied and unsaved states.

- **Button rename:**
  - `ScalarFieldBuilder`: rename "Save mapping" (or similar) button label to "Apply". Callback becomes `applyRule` instead of `onSave`.
  - `ExpressionBuilderPanel`: same rename if applicable.

- **Ctrl+S binding:**
  - Ensure Ctrl+S / Cmd+S calls the global `save()` (persist all changes), not `applyRule`.
  - If the builder has an unapplied expression when Ctrl+S is pressed, auto-apply it first, then save.

- **Focus advance after Apply:**
  - After `applyRule` succeeds, compute the next unmapped target path and fire `onSelectNode(nextPath, type)` at the composition level.
  - "Next unmapped" = first field below the current field in document order that has status `'unmapped'` in the `statusMap`.

- **Navigation guards:**
  - When user clicks a different target field and `hasUnappliedExpression` is true: show ConfirmDialog with "Apply & Continue" / "Discard" / "Cancel".
    - "Apply & Continue": applies the current expression to the *current* target, then navigates to the *clicked* target field (the user's original intent). Does NOT auto-advance to next unmapped.
    - "Discard": discards the unapplied expression and navigates to the clicked field.
    - "Cancel": stays on the current field.
  - When user navigates to a different route and `unsavedRuleCount > 0`: show ConfirmDialog with "Save & Leave" / "Discard" / "Cancel".
  - Use React Router's `useBlocker` or `useBeforeUnload` for route-level blocking.

- **Focus advance after Apply (normal flow only):**
  - After a *normal* Apply (user clicks Apply button without switching targets), compute the next unmapped target path and fire `onSelectNode(nextPath, type)` at the composition level.
  - "Next unmapped" = first field below the current field in document order that has status `'unmapped'` in the `statusMap`.
  - This auto-advance does NOT apply to "Apply & Continue" in the navigation guard — that always goes to the field the user clicked.

- **Auto-preview event:**
  - After `applyRule` succeeds, emit an `onRuleApplied` callback (or equivalent) that the inline preview strip can subscribe to for auto-run behavior (wired in T-05).

- **Save state display:**
  - Pass computed `saveState` and `unsavedCount` props to `EditorTopBar` (from T-01).
