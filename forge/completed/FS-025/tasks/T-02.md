## Summary

Ensure the builder fully resets and loads the new target field's configuration when the user navigates between target fields. Integrate with the navigation guard (FS-021 AE-05) so that unapplied changes trigger a confirmation before the reset proceeds. This task ensures no stale state from the previous field persists in the builder.

---

## Scope

### In Scope

- Implement a reliable builder reset mechanism when `selectedTargetPath` changes. Options:
  - Key the `UnifiedExpressionBuilder` component on `selectedTargetPath` (forcing unmount/remount), OR
  - Implement explicit reset signals in `useExpressionBuilder` that clear all state before calling `loadExpression()`.
- Integrate with the existing navigation guard (FS-021 AE-05):
  - Before resetting, check if unapplied changes exist in the current builder.
  - If yes, fire the navigation guard dialog: "You have unapplied changes to this rule. Discard?" with "Apply & Continue", "Discard", "Cancel".
  - "Apply & Continue": apply current expression to the current target, then proceed with navigation.
  - "Discard": proceed with navigation without applying.
  - "Cancel": abort navigation (stay on current target).
- After the guard passes (or no guard needed), fully reset builder state and call `loadExpression()` with the new target's rule expression (from T-01).
- Update the builder header (field name, type badge, required/optional, mapped status) to reflect the new target field.
- Ensure this works identically in both Target View and Rules View.

### Out of Scope

- The hydration mechanism itself (that's T-01).
- Conditional branch expression support (that's T-03).
- Apply/advance behavior changes (that's T-04).
- Changes to the navigation guard dialog component itself (it already exists per FS-021).

## Change Requirements

- The builder must not retain any state from the previous target field after navigation completes. This includes:
  - Expression builder state (sources, transforms, conditions, value map entries)
  - Builder/Editor mode selection (reset to Builder if decomposition succeeds, or Editor if it fails)
  - Warning banners
  - Apply button state
  - Live Expression and Live Result content

- The navigation guard check must happen before the reset. The guard should detect unapplied changes by comparing the current expression state against the last-applied expression for the current target.

- The builder header (displayed in `ScalarFieldBuilder`) must update reactively when `selectedTargetPath` changes:
  - Field name (last segment of target path)
  - Type badge (string/number/boolean/etc.)
  - Required/optional indicator
  - Mapped/unmapped status icon

- If using component keying (recommended approach): set `key={selectedTargetPath}` on the `UnifiedExpressionBuilder` or its wrapper so React unmounts the old instance and mounts a fresh one. The new instance initializes via the T-01 hydration flow.

- If using explicit reset: `useExpressionBuilder` must expose a `reset()` method that clears all internal state atomically before `loadExpression()` runs.

- The "Apply & Continue" option in the navigation guard must:
  1. Call `applyRule(currentTargetPath, currentExpression)` (commits the current work).
  2. Then proceed with the navigation (set new `selectedTargetPath`, triggering the load flow).

## Blockers / Risks

- Component keying approach forces full remount which may flash briefly. If performance is a concern, the explicit reset approach avoids remount cost but is more error-prone (must clear ALL state paths).
- The navigation guard dialog is already implemented per FS-021. If its implementation has changed or has edge cases, this task may need to adapt.

## Notes

- The recommended approach is to key `UnifiedExpressionBuilder` on `selectedTargetPath`. This is simpler and guarantees no stale state. The fresh instance will initialize via the T-01 hydration flow on mount.
- The `useExpressionBuilder` hook should detect `selectedTargetPath` changes via its dependencies. If keying is used, the hook reinitializes naturally on remount.
- Test the "rapid click" scenario: user clicks field A, then immediately clicks field B before A's decomposition completes. The final state should always reflect field B.
