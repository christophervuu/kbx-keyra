## Summary

Wire `decomposeExpression()` into the target-field-selection lifecycle so that when a user selects a mapped target field, the builder automatically decomposes the existing rule's expression and hydrates the `UnifiedExpressionBuilder` state. When decomposition fails, fall back to Editor mode with the raw expression loaded. When the field is unmapped, show the empty/default builder state.

---

## Scope

### In Scope

- Add a `loadExpression(expression: string | null)` method (or equivalent) to `useExpressionBuilder` that triggers decomposition and state hydration.
- Wire the target-selection change event (from composition layer / `selectedTargetPath`) to call `loadExpression` with the matching rule's expression.
- On successful decomposition: set `ExpressionBuilderState` from the decomposition result, auto-detect and switch to the correct mode tab (Value / Conditional / Value Map), and set mode to Builder.
- On decomposition failure: load the raw expression into Editor mode, show the "Complex expression -- edit in Editor mode" warning banner.
- On no matching rule (unmapped): reset to default empty state (Value mode, no sources, no transforms), set mode to Builder.
- Ensure Editor mode also receives the loaded expression (populate `RawDslEditor` with the expression text when in Editor mode).
- Live Expression section displays the loaded/current expression.

### Out of Scope

- Navigation guard logic (that's T-02).
- Builder component keying/reset mechanics on navigation (that's T-02).
- Conditional branch expression support (that's T-03).
- Apply/advance behavior changes (that's T-04).
- Changes to `decomposeExpression()` itself (unless a clear bug is found).

## Change Requirements

- `useExpressionBuilder` must expose a mechanism to load an expression from an external source (target selection). This should:
  1. Accept `expression: string | null` (null = unmapped / empty).
  2. When `expression` is non-null and non-empty: call `decomposeExpression(expression)`.
  3. On decomposition success: set the builder state to the returned `ExpressionBuilderState`, set mode to Builder, clear any warning banner.
  4. On decomposition failure: set mode to Editor, load the raw expression string into the editor state, set the decomposition warning flag.
  5. When `expression` is null or empty: reset to default state (Value mode, empty sources, empty transforms), set mode to Builder.

- The composition layer (where `selectedTargetPath` lives) must look up the existing rule for the selected target and call the load mechanism. The lookup should match `rules.find(r => r.target === selectedTargetPath)?.expression`.

- `ScalarFieldBuilder` must propagate the selected target's expression to the builder hook when the target path changes.

- `ExpressionBuilderPanel` (Rules View) must propagate the selected rule's expression when `selectedRuleIndex` changes.

- The `LiveExpressionDisplay` must show the loaded expression immediately upon hydration (before any user edits).

- The `RawDslEditor` must be populated with the expression text when the builder is in Editor mode and a target with an existing rule is selected.

## Verification Requirements

- Unit tests for `useExpressionBuilder.loadExpression()`:
  - Verify Value mode expression (`lower(trim(source("email")))`) decomposes into correct state (sources: email, transforms: trim, lower).
  - Verify Conditional expression (`if(gt(source("amount"), 100), "high", "low")`) decomposes into Conditional mode state.
  - Verify Value Map expression decomposes into Value Map mode state.
  - Verify complex/undecomposable expression triggers Editor mode fallback + warning.
  - Verify null/empty expression resets to default state.
- Component tests for `ScalarFieldBuilder`:
  - Verify that when `selectedTargetPath` changes to a mapped field, the builder renders the decomposed state (source chips, transform steps visible).
  - Verify that when `selectedTargetPath` changes to an unmapped field, the builder shows empty state.
- Component tests for Editor mode loading:
  - Verify that when in Editor mode and a mapped field is selected, the `RawDslEditor` textarea contains the expression text.
- Typecheck passes for all touched files.
- Lint passes for all touched files.

## Blockers / Risks

- The existing `decomposeExpression()` from FS-023 may not handle all expression patterns that users have created via Editor mode. Expressions outside the decomposer's capability should trigger the fallback path, not crash.
- The hook's state management must handle rapid target-selection changes (debounce or abort previous decomposition if selection changes again quickly).

## Notes

- The `decomposeExpression()` function from `pipeline-decomposer.ts` is the critical dependency. Review its current capabilities before implementation to understand which expression patterns it handles vs. which trigger fallback.
- The composition layer (likely in `MappingEditorPage.tsx` or `useMappingEditor`) already tracks `selectedTargetPath` and the rules array. The wiring connects these existing pieces.
- This task establishes the hydration mechanism that T-02 (navigation reset) and T-03 (branch expression loading) depend on.
