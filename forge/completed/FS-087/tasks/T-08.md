## Summary

Implement and validate migration/normalization strategy so existing localStorage and backend records with scope distinctions are treated as shared schemas without breaking project links or mapping references.

---

## Scope

### In Scope

- Client-side normalization path for Phase 0/localStorage legacy records.
- Backend compatibility handling for legacy scope values.
- Default read-time compatibility rollout; optional one-time migration/backfill tooling only when required by audit outcome.
- Preservation of project link relationships and mapping schema references.

### Out of Scope

- Unrelated data cleanup outside schema linkage/scope compatibility.
- New authorization/tenancy migration behavior.

---

## Relevant Areas

- `ui/src/lib/api/local-storage-adapter.ts`
- `src/lib/persistence/*`
- `src/lambda/schema/*`
- optional migration scripts under `scripts/` ?
- tests for migration/compatibility paths

---

## Change Requirements

- Legacy `global` and `project` scope records normalize to shared-library semantics.
- Legacy `schemaRefs` normalize to canonical `linkedSchemaIds` model for project linkage.
- Legacy `origin: local` normalizes to canonical `origin: uploaded`.
- Existing project schema associations are preserved as linked schemas.
- Existing mappings continue referencing same schema IDs with no remap required.
- Any retained legacy fields are explicitly marked non-authoritative.
- Introduce one-time migration/backfill only when audit finds unsafe key/index/query constraints (DynamoDB/GSI/OpenSearch/Lambda route behavior).

---

## Verification Requirements

- Fixture-based migration tests for representative legacy records.
- Backward-compat API tests for old payload variants.
- Manual smoke check for previously stored localStorage datasets.

---

## Acceptance Checks

- Legacy records load and behave under shared-library model.
- No mapping breakage from normalization.
- Read-time compatibility path is default when audit says safe; migration script is only required when audit says unsafe.
- Compatibility strategy is documented and test-covered.

---

## Blockers / Risks

- Risk: partial/inconsistent legacy data may expose edge cases; include fallback behavior for malformed records.

---

## Notes

- Implemented deterministic read-time compatibility (no one-time backfill script required per T-02 audit outcome):
  - Legacy `origin: local|published` is normalized to canonical `uploaded` in UI adapter and backend schema/project read paths.
  - Legacy linkage (`schemaRefs`) normalizes to canonical `linkedSchemaIds` with trimming/deduplication and preserved order.
  - `scope` remains compatibility-only metadata and does not drive schema availability behavior.
- Hardened project-link normalization across backend/UI surfaces to avoid malformed/duplicate legacy IDs causing inconsistent schema loads.
- Updated schema-link write compatibility in schema upload flow to avoid introducing new `schemaRefs.type: local` values (`published` used for upload compatibility bridge).
- If migration script is deferred, read-time normalization must be complete and deterministic.
