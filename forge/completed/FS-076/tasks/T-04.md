## Summary

Implement the explicit user-triggered CDM re-sync endpoint/service that compares upstream commit SHA, updates local schema content/metadata when changed, and sets sync state outcomes including failure handling.

---

## Scope

### In Scope

- Add/enable backend re-sync endpoint/service for CDM-linked schemas.
- Add/enable lightweight status-refresh read behavior that computes `update-available` without content mutation.
- Validate schema is CDM-linked and has required source metadata.
- Compare stored `commitSha` with upstream SHA.
- Update schema content and `commitSha` when changed; no-op when unchanged.
- Persist/return sync-state outcomes (`synced`, `update-available`, `sync-failed`) with consistent semantics between status-refresh and explicit re-sync.
- Map GitHub read failures to actionable API errors.

### Out of Scope

- Auto-sync/webhook scheduling.
- Diff visualization payloads.
- Non-CDM sync logic.

## Change Requirements

- Re-sync must be explicit and user-invoked.
- Changed upstream SHA must update stored SHA/content.
- Unchanged upstream SHA must preserve stored SHA/content and return no-op semantics.
- Failures must set sync state to failed and return user-safe error messages.
- No GitHub write endpoints may be invoked.

---

## Verification Requirements

- Tests for changed, unchanged, and failure paths.
- Tests for status-refresh `update-available` behavior without mutation.
- Tests for malformed/missing source metadata handling.
- Tests proving no GitHub write usage across re-sync flow.

---

## Acceptance Checks

- Re-sync updates `commitSha` and content when upstream changed.
- Re-sync keeps `commitSha` unchanged when upstream unchanged.
- Re-sync failure path persists/returns failed sync state and actionable message.
- Status-refresh path surfaces `update-available` without mutating stored content/SHA.
- No write-path GitHub API calls occur in re-sync flow.
