## Summary

Write integration tests that prove mappings (including full MappingConfig from S3) and mapping version snapshots are durable across session boundaries. Tests verify that the version auto-increment model works correctly, that version retrieval returns the exact config snapshot saved at that version, and that mapping metadata + S3 config blob round-trip together.

---

## Scope

### In Scope

- Integration tests for mapping cross-session persistence (DynamoDB metadata + S3 config)
- Integration tests for mapping version snapshot persistence (DynamoDB version metadata + S3 versioned config)
- Deep equality verification of `MappingConfig` objects across sessions
- Version auto-increment behavior verification
- Multiple version save/retrieve scenarios
- `listByProject` query across sessions

### Out of Scope

- Schema persistence (T-04)
- Mapping duplication logic
- Version pruning behavior (covered by FS-058 unit tests)

## Change Requirements

- Create `tests/lambda/integration/persistence/mapping-persistence.test.ts`
- Test cases for **mapping CRUD**:
  1. **Create in A, Get in B**: Create mapping with full config (rules, schema refs, status). Fresh session retrieves by ID. Assert DynamoDB metadata AND S3 config body are complete and correct.
  2. **Update in A, Get in B**: Create mapping, update config (add rules). Fresh session gets updated config. Assert version incremented, all rules present.
  3. **List by project in B**: Create 3 mappings under one project. Fresh session calls `listByProject`. Assert all 3 returned with correct metadata.
  4. **Delete in A, Get in B**: Create, delete. Fresh session get returns not-found.
- Test cases for **mapping versions**:
  5. **Save version 1, retrieve in B**: Save version with config `C1`. Fresh session `get(mappingId, 1)` returns config deeply equal to `C1`.
  6. **Save versions 1 and 2, retrieve both in B**: Save V1 with 2 rules, V2 with 4 rules. Fresh session retrieves each independently. Assert deep equality — V1 has 2 rules, V2 has 4 rules. They are NOT conflated.
  7. **List versions in B**: Save 3 versions. Fresh session lists versions. Assert descending order by version number, correct `savedAt` timestamps and `ruleCount` per version.
  8. **Version config isolation**: Verify that updating the current mapping config does NOT retroactively change previously saved version snapshots.
- Fixture configs should be non-trivial: include `rules` arrays, `sourceSchemaId`, `targetSchemaId`, `options`, varying `status` values

---

## Verification Requirements

- Deep equality on `MappingConfig` objects (JSON.parse/stringify round-trip safe)
- S3 config body matches original (verified by fetching S3 directly and comparing)
- Version numbers are monotonically increasing
- `configS3Key` in DynamoDB points to the correct S3 location
- `savedAt` timestamps are valid ISO 8601
- `ruleCount` matches actual rules array length in config
- Tests isolated and repeatable

## Notes

- The mapping `version` field in DynamoDB metadata is the current version (auto-incremented on update). The `MappingVersions` table stores historical snapshots separately. These are distinct concepts — test both.
- Use config objects with diverse field types (strings, arrays, nested objects) to catch serialization edge cases.
- Verify that `null` vs `undefined` handling is consistent: DynamoDB drops `undefined` attributes. If a config contains fields set to `undefined`, verify they survive round-trip correctly (likely as absent/omitted).
