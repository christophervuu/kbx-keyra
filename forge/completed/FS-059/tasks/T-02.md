## Summary

Extend the `AppError` interface with an optional `requestId` field. Update the HTTP client utility (`http-client.ts`) to parse the backend error envelope structure (`{ error: { code, message, statusCode, retryable, requestId } }`) and construct errors with all fields populated from the envelope rather than inferring solely from HTTP status codes.

---

## Scope

### In Scope

- Add `requestId?: string` to `AppError` interface
- Update `toAppError()` to preserve `requestId` when present on source error
- Update HTTP client error parsing to detect and extract the backend error envelope
- Fallback behavior when response body is not a valid error envelope (status-code-based inference preserved)
- Unit tests for envelope parsing and fallback behavior

### Out of Scope

- Retry logic (separate task)
- UI component changes
- Changes to `AsyncState` type
- Changes to `ApiAdapter` interface

---

## Relevant Areas

- `ui/src/lib/state/app-error.ts` — AppError interface and `toAppError()`
- `ui/src/lib/api/http-client.ts` — HTTP client utility (error normalization)
- `ui/src/lib/api/http-adapter.ts` — HttpAdapter (consumer, no changes expected)
- `tests/` — unit tests for app-error and http-client

---

## Change Requirements

- `AppError` interface gains: `requestId?: string`
- `toAppError()` must check for `requestId` on the source error object and include it in the output
- HTTP client error path must:
  1. Attempt to parse response body as JSON
  2. Check for `response.error` object structure
  3. If valid envelope: extract `code`, `message`, `statusCode`, `retryable`, `requestId` directly
  4. If not valid envelope: fall back to current status-code-based classification
  5. Construct an `Error` subclass or enriched Error with all fields set as enumerable properties
- The enriched Error must be compatible with existing `toAppError()` conversion (properties must be accessible)

---

## Verification Requirements

- Unit test: response with valid error envelope → AppError has all fields from envelope
- Unit test: response with non-JSON body → fallback to status-code classification
- Unit test: response with partial envelope (missing `requestId`) → other fields still extracted
- Unit test: `toAppError()` preserves `requestId` from enriched Error
- `pnpm typecheck` passes in `ui/`
- `pnpm build` passes in `ui/`

## Acceptance Checks

- `AppError` type includes optional `requestId` field
- HTTP client correctly parses `{ "error": { "code": "SERVICE_UNAVAILABLE", "message": "...", "statusCode": 503, "retryable": true, "requestId": "req-abc" } }` into an error with all fields
- `toAppError()` on an error with `requestId` produces `AppError` with `requestId` set
- Fallback path still works for non-envelope responses
- No breaking changes to existing consumers of `AppError` or `toAppError()`
- TypeScript strict mode clean
