## Summary

Extend `FunctionSignature` with a `lazyArgs` field and update the evaluator's function dispatch logic to pass raw AST nodes (instead of pre-evaluated values) for arguments at the specified indices. This is the foundational mechanism that enables `map()`, `filter()`, and `find()` to receive unevaluated template/condition expressions and re-evaluate them per array element with different scope contexts.

---

## Scope

### In Scope

- Add `lazyArgs?: number[]` field to `FunctionSignature` type definition
- Update evaluator function dispatch in `src/engine/dsl/evaluator.ts` to:
  - Check if the resolved function has `lazyArgs` defined
  - For argument indices in `lazyArgs`, pass the raw `AstNode` directly (skip recursive evaluation)
  - For other arguments, evaluate recursively as before
  - Skip null propagation and type checking for lazy arguments (they are AST nodes, not values)
- Ensure `pushScope()` and `popScope()` operations on the scope stack are functional and accessible from function implementations via `EvaluationContext`
- Ensure `context.evaluate` callback is accessible for re-entrant calls from function implementations
- Unit tests verifying: lazy args pass AST nodes, normal args still evaluated, pushScope/popScope work correctly

### Out of Scope

- Implementing any specific array function (map, filter, find)
- Modifying existing function registrations (they have no lazyArgs)
- Changing null propagation behavior for non-lazy arguments
- Modifying the parser

## Change Requirements

After this task is complete:

1. `FunctionSignature` has an optional `lazyArgs: number[]` field. When present, it lists 0-based argument indices that should not be pre-evaluated.

2. The evaluator's function dispatch logic, when processing a `FunctionCall` node:
   - Resolves the function from the registry
   - For each argument: if the argument's index is in `signature.lazyArgs`, the raw `AstNode` is placed in the args array; otherwise, the argument is recursively evaluated and its value is placed in the args array
   - Null propagation check runs only against evaluated (non-lazy) arguments
   - Type checking runs only against evaluated (non-lazy) arguments
   - The mixed args array (values + AST nodes) is passed to the function implementation

3. `EvaluationContext` exposes:
   - `pushScope(element: unknown): void` — pushes element onto scope stack
   - `popScope(): void` — pops top element from scope stack
   - `evaluate(node: AstNode, context: EvaluationContext): EvaluationResult` — re-entrant evaluation callback

4. After `pushScope()`, the evaluator's next dispatch correctly derives `currentItem` from the new top of stack and `parentItem` from second-to-top.

5. After `popScope()`, the stack is restored and subsequent `currentItem`/`parentItem` reflect the previous state.

- Unit test: After `popScope()`, evaluating `item("x")` outside context produces E010.

- Typecheck passes with no errors.
- Existing evaluator tests continue to pass.

## Notes

- The `lazyArgs` approach was chosen over alternatives (special-casing by function name, thunk wrappers) for its declarative nature and extensibility. Future scope-creating functions (e.g., `sort()`) would simply declare their own `lazyArgs`.
- The evaluator must NOT attempt type-checking on lazy arguments — they are AST nodes, not runtime values. Type checking for the lazy argument's result happens inside the function implementation after per-element evaluation.
- This task is a prerequisite for T-02 and T-03 but NOT for T-04 or T-05.
