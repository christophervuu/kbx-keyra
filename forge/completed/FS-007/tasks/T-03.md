## Summary

Replace the execute() stub in `src/engine/execute.ts` with the full execution pipeline. The orchestrator iterates over all rules in the mapping config, parses each rule's expression (using the AST cache), constructs an EvaluationContext, evaluates each rule's AST, places results at target paths using setAtPath, collects diagnostics with rule metadata, and returns the assembled ExecutionResult. This task implements phases 2–4 and 7 of the execute pipeline (parsing, context building, rule iteration, output assembly). Bulk behaviors (T-04), trace/stats (T-05), and validateBeforeExecute (T-05) are added in subsequent tasks.

## Change Requirements

The execute() function must:

1. **Parse rules**: For each rule, check the AST cache first. If not cached, call `parse(rule.expression, { registry: defaultRegistry })`. Cache the result. If AST is null, attach parse diagnostics with `ruleIndex`/`targetPath`/`expression` and skip to the next rule.

2. **Build EvaluationContext**: Create a context object with:
   - `sourceData` from the execute() parameter
   - `constants` from `config.config.constants`
   - `externalSources` from `options?.externalSources ?? {}`
   - `registry` set to `defaultRegistry`
   - `options` from the execute() parameter (with defaults)
   - `scopeStack` as an empty mutable array
   - `evaluate` pointing to the `evaluate` function
   - `addDiagnostic` as a callback that appends to the current rule's diagnostic list
   - `pushScope` / `popScope` operating on the scopeStack array

3. **Evaluate each rule**: For each rule with a valid AST:
   - Reset scopeStack to empty
   - Call `evaluate(ast, context)`
   - Collect `value` and `diagnostics` from the result
   - Determine if the rule failed (any error-severity diagnostic from evaluation)
   - If failed, use `null` as the output value
   - Place the value at `rule.target` using `setAtPath(output, rule.target, value)`
   - Attach `ruleIndex`, `targetPath`, `expression` to each diagnostic

4. **Sort diagnostics**: Sort by ruleIndex ascending (undefined-ruleIndex last), then by severity weight (error=0, warning=1, info=2).

5. **Return ExecutionResult**: `{ output, diagnostics, trace, stats }` where trace and stats are placeholder values until T-05 adds real implementations.

6. **Immutability**: The function must not mutate `sourceData`, `config`, or `options`. The output object is a freshly created object.

## Notes

This is the largest single task in the spec. The core pipeline ties together parse(), evaluate(), setAtPath, and AstCache into the end-to-end execution flow.

Placeholder stats should return `{ rulesEvaluated: 0, rulesSucceeded: 0, rulesFailed: 0, durationMs: 0 }` until T-05 replaces them with real computation. Placeholder trace should return `[]` when trace is enabled and `undefined` when disabled, until T-05 adds real trace recording. This allows T-04 and T-05 to build on top of the working core pipeline without circular dependencies.

The AST cache should be created per execute() call. If the same config needs to be re-executed with different source data (test-case-runner), the caller creates a new execute() call — but the cache can be exposed or shared in a future optimization. For now, per-call cache is sufficient and simpler.

Actually, looking at the requirements again: "Cache parsed ASTs for reuse (the same config may be executed multiple times with different source data in test-case-runner scenarios)." This suggests the cache should potentially persist across calls. For Rev 1, implement the cache as a per-call Map inside execute(). If cross-call caching is needed, it can be added as a refinement. The acceptance examples (AE-14) test within a single execution, so per-call caching satisfies them.
