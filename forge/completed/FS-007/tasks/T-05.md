## Summary

Add three cross-cutting capabilities to the execute pipeline: (1) per-rule trace recording that populates TraceEntry objects when `options.trace` is true, (2) execution statistics computation (rulesEvaluated, rulesSucceeded, rulesFailed, durationMs), and (3) optional pre-flight validation that aborts execution if `options.validateBeforeExecute` is true and validation finds errors.

---

## Scope

### In Scope

- Replace placeholder stats with real computation in execute():
  - Track `rulesEvaluated` (total rule count)
  - Track `rulesSucceeded` (rules that produced a value without error-severity diagnostics)
  - Track `rulesFailed` (rules that had parse failures or error-severity evaluation diagnostics)
  - Track `durationMs` using `Date.now()` or `performance.now()` (whichever is available cross-environment)
- Replace placeholder trace with real per-rule TraceEntry recording:
  - Only populate when `options.trace` is true
  - For each rule evaluated, create a TraceEntry with: `ruleIndex`, `targetPath`, `expression`, `inputValue` (the sourceData snapshot — can be the full sourceData reference for now), `outputValue` (the evaluated value), `diagnostics` (diagnostics from this rule's evaluation), and optional `durationMs` (per-rule timing)
  - Trace array is ordered by rule index (evaluation order)
- Implement validateBeforeExecute:
  - If `options.validateBeforeExecute` is true, call `validate(config, sourceSchema, targetSchema, options)` before rule evaluation
  - If validation returns `valid: false`, abort execution immediately
  - Return `ExecutionResult` with `output: null`, validation diagnostics, no trace, and stats: `{ rulesEvaluated: 0, rulesSucceeded: 0, rulesFailed: 0, durationMs: <actual> }`
  - If validation returns `valid: true`, continue with normal execution
- Import `validate` from `src/engine/validate.ts` for pre-flight validation

### Out of Scope

- Bulk behaviors (T-04)
- Test files (T-07)
- Changes to the validate pipeline itself

## Change Requirements

**Stats computation**:
- Wrap the entire execute body in a timing measurement
- Count rules as they are processed:
  - rulesEvaluated = total rules in config.rules
  - A rule "succeeds" if its AST parses successfully AND evaluation produces no error-severity diagnostics
  - A rule "fails" if its AST is null (parse failure) OR evaluation produces at least one error-severity diagnostic
  - rulesSucceeded + rulesFailed = rulesEvaluated
- stats is always present in the result (not optional in practice, even though the type allows undefined)

**Trace recording**:
- If `options.trace` is false or undefined, `result.trace` is undefined
- If `options.trace` is true, `result.trace` is an array of TraceEntry objects:
  - One entry per rule (including failed rules)
  - `inputValue` captures the sourceData reference (not a deep clone — deep cloning is expensive and optional per the spec's `inputSnapshot?: unknown`)
  - `outputValue` is the value placed in the output (null for failed rules)
  - `diagnostics` is the array of diagnostics produced during this rule's evaluation (may be empty)
  - `durationMs` is the time taken to evaluate this single rule (optional — include if easily measurable)

**validateBeforeExecute**:
- Check `options?.validateBeforeExecute === true` at the top of execute()
- If true, call `validate(config, sourceSchema, targetSchema, options)`
- If `result.valid === false`, return early with abort result
- durationMs in stats should include the validation time

**Timing**:
- Use `Date.now()` for timing (available in both browser and Node without polyfills)
- `performance.now()` is preferred for precision but may not be available in all Lambda environments — use `Date.now()` for reliability

## Blockers / Risks

- If `validate()` has side effects or modifies its inputs, that would be a problem. Based on FS-006 implementation, validate() is pure — but verify during implementation.
- `Date.now()` has millisecond precision, which may show `0` for very fast single-rule evaluations. This is acceptable — durationMs for stats is meaningful at the pipeline level.

## Notes

T-04 (bulk behaviors) and T-05 are both additions to the core pipeline from T-03. They are independent of each other and can be implemented in parallel. However, the final execute() orchestrator integrates both, so the implementation order within execute() matters:

1. Optional pre-flight validation (T-05) — earliest, before any parsing
2. Parse rules (T-03)
3. Evaluate rules + trace recording (T-03 + T-05)
4. Bulk behaviors (T-04)
5. Stats assembly (T-05)
6. Return result (T-03)

When implementing trace, be careful not to capture the output value before bulk behaviors modify it — the TraceEntry.outputValue should capture the value from evaluation, not the final post-bulk-behavior value. The trace represents what the rule produced, not what ended up in the final output after nullSubtrees/unmappedTargets.
