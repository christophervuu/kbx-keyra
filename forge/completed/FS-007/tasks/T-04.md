## Summary

Add bulk behavior application to the execute pipeline. After all rules have been evaluated and placed in the output, apply the unmappedTargets strategy (null/omit/error) using SchemaTree to enumerate unmapped required target fields, and apply nullSubtrees by setting specified paths and their descendants to null. These behaviors are inserted into the execute() orchestrator between rule evaluation and final output assembly.

## Scope

### In Scope

- Import `getOrBuildSchemaTree` from `src/engine/validate/schema-tree.ts` for schema analysis
- Implement unmappedTargets logic in execute():
  - `"omit"` — no action needed (default; unmapped fields are simply absent)

  - `"error"` — enumerate required leaf paths from target SchemaTree, find those with no mapping rule, emit KEYRA-W005 diagnostic for each

## Change Requirements

After this task, the execute() function applies bulk behaviors in this order:

1. **Rule evaluation** (already implemented in T-03) — produces output object with rule values
2. **Unmapped targets** — if `config.config.unmappedTargets` is:
   - `"omit"` — no action
   - `"null"` — build SchemaTree from targetSchema, get required leaf paths, compute set of rule target paths, for each required leaf not in the rule target set, call `setAtPath(output, path, null)`
   - `"error"` — build SchemaTree from targetSchema, get required leaf paths, for each required leaf not in the rule target set, emit `KEYRA-W005` diagnostic with `{ path }` and no ruleIndex (this is a config-level diagnostic)
3. **Null subtrees** — for each path in `config.config.nullSubtrees`, call `setAtPath(output, path, null)`. This overwrites any rule-placed values.

The "unmapped" check compares required leaf paths from the schema against the set of `rule.target` values in `config.rules`. A target path is "mapped" if any rule has it as its target, regardless of whether the rule succeeded or failed.

## Notes

The unmappedTargets behavior uses SchemaTree's `getRequiredLeafPaths()` which returns dot-notation paths of required leaf fields. The set comparison with rule targets is a straightforward set difference.

The nullSubtrees application is intentionally simple — just setAtPath to null. For descendant nullification (e.g., nullSubtree "Order" should also null "Order.Header" and "Order.Header.Type"), setAtPath to null at "Order" replaces the entire subtree object with null, which effectively nullifies all descendants since the nested object is replaced. However, if rules set "Order.Header.Type" and nullSubtrees lists "Order", after setting "Order" to null, any subsequent reference to "Order.Header.Type" in the output would need to navigate through null. Since setAtPath replaces "Order" with null, the nested structure is gone. This is the correct behavior per the spec.
