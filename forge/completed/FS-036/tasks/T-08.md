## Summary

Create a `failure-explainer.ts` module that pattern-matches on diagnostic codes and messages to produce plain-language explanations for common mapping failure cases. Wire the explainer into DiagnosticsDisplay via the `explainDiagnostic` prop already defined in T-02. Initial patterns cover null propagation, type mismatch, missing source path, and unresolved function.

## Change Requirements

**FailureExplanation type** (add to `types.ts`):

```typescript
interface FailureExplanation {
  summary: string;
  suggestion?: string;
}
```

**`explainDiagnostic` function:**

```typescript
function explainDiagnostic(
  diagnostic: Diagnostic,
  traceEntry?: TraceEntry
): FailureExplanation | null;
```

Pattern matching logic (ordered by specificity, code-based matching first):

**Matching strategy:** Match by diagnostic `code` first — code-based matches are authoritative. Where no stable code-based pattern exists, allow limited best-effort fallback matching on diagnostic `message` text. Code-based matching always takes precedence over any message-based match.

1. **Null output with missing source:** If `traceEntry?.outputValue === null` and diagnostic message or code indicates source resolution failure → `{ summary: "This field produced null because the source path resolved to no value. Check that the source field name matches your input data.", suggestion: "Verify the source path exists in your test data, or use default() to provide a fallback value." }`

2. **Type mismatch:** If diagnostic code contains `TYPE_MISMATCH` or message contains "type mismatch" (case-insensitive) → `{ summary: "The expression returned a different type than the target field expects.", suggestion: "Consider wrapping with cast() to convert the value, or review the transform chain output type." }`

3. **Missing source path:** If diagnostic code or message indicates an unresolved source path (e.g., contains "source" and "not found" or "undefined") → `{ summary: "The source path referenced in this expression was not found in the input data.", suggestion: "Check for typos in the source() path argument and verify the field exists in your test data." }`

4. **Unresolved function:** If diagnostic code or message indicates an unknown function → `{ summary: "The function name in this expression is not recognized by the DSL.", suggestion: "Check spelling against the DSL function reference panel, or verify the function name is correct." }`

5. **General null output:** If `traceEntry?.outputValue === null` (without a specific source error) → `{ summary: "This field evaluated to null. This may indicate a missing source value or an expression that doesn't produce output for the given input.", suggestion: "Try running with different test data, or check the expression logic." }`

6. **No match:** Return `null`.

**Wiring in AdvancedTestingPage:**

Pass `explainDiagnostic` function reference and `traceEntries` to DiagnosticsDisplay:

```tsx
<DiagnosticsDisplay
  state={state}
  explainDiagnostic={explainDiagnostic}
  traceEntries={state.status === 'success' ? state.result.trace : undefined}
  // ... other props from T-06
/>
```

## Notes

The pattern matching should be ordered from most specific to least specific, with code-based matches always checked before message-based fallbacks. Start with patterns that require both diagnostic AND trace entry data, then fall back to diagnostic-only patterns. The function is pure and deterministic — no side effects, no I/O. This makes it easy to test and extend with new patterns in the future.
