## Summary

Define the TypeScript interfaces for the core domain model referenced across all UI screens. These types form the shared vocabulary that the ApiAdapter interface, LocalStorageAdapter, and all feature components code against. Derived from Section 15 (Data Model) and Section 9.4 (Mapping Config Format) of the product spec.

---

## Scope

### In Scope

- `ui/src/lib/types/domain.ts` — core domain interfaces
- At minimum: `Project`, `MappingConfig`, `MappingRule`, `SchemaMetadata`, `SchemaRef`, `DeploymentRecord`, `Environment`, `DeployStatus`, `Template`, `ActivityEntry`
- Supporting types referenced by the above (e.g., `ProjectMetadata`, `MappingMetadata`, `SchemaDetail`, input types for create/update operations)
- Barrel export from `ui/src/lib/types/index.ts`

### Out of Scope

- ApiAdapter interface (T-03)
- AsyncState types (T-04)
- Engine types (already in `src/engine/types/`)
- Implementation of any adapter methods

## Change Requirements

Define the following interfaces at minimum:

**Core entities:**
- `Project` — id, name, description, slug, schemaRefs, tags, createdAt, updatedAt
- `ProjectMetadata` — lightweight version for list views
- `MappingConfig` — full mapping configuration (name, version, engineVersion, sourceSchemaRef, targetSchemaRef, config, rules)
- `MappingRule` — target, type, expression
- `MappingMetadata` — lightweight version for list views (id, projectId, name, version, status, ruleCount, coverage, etc.)
- `SchemaMetadata` — id, name, format, fieldCount, origin, status, source info, timestamps
- `SchemaDetail` — full schema content + metadata
- `SchemaRef` — schemaId, type (github | local | published), commitSha (optional)
- `DeploymentRecord` — mappingId, environment, version, snapshotId, deployedAt, deployedBy, status
- `Environment` — type alias or enum: "DEV" | "QA" | "PROD"
- `DeployStatus` — type alias: "deployed" | "stale" | "not-deployed" | "deploying"
- `Template` — id, name, description, sourceSchemaType, targetSchemaType, ruleCount, tags
- `TemplateMetadata` — lightweight for lists
- `ActivityEntry` — type, message, timestamp, projectId?, mappingId?, metadata?

**Input types (for create/update operations):**
- `CreateProjectInput`, `UpdateProjectInput`
- `CreateMappingInput`
- `CreateSchemaInput`

**Supporting types:**
- `GitHubFile` — for CDM/published schema listing
- `DeploymentContext`, `DeploymentDiff`
- AI input/result types (can be minimal stubs since AI is out of scope for Phase 0)

All types must be:
- Exported from barrel `ui/src/lib/types/index.ts`
- Compatible with TypeScript strict mode
- Using `readonly` where semantically appropriate for domain entities

## Notes

- These types are the UI's view of the domain — they may diverge slightly from the DynamoDB table structure (Section 15) because the UI sees API responses, not raw DB records
- The MappingConfig type here is the UI representation of the full JSON document from Section 9.4
- Keep AI-related input/result types minimal (stub interfaces with a comment) since they won't be used until much later
- The engine's own types (`src/engine/types/`) should NOT be imported here — the UI has its own type layer. The engine bundle integration comes in a later spec.
