## Summary

Define the `EvaluationContext`, `EvaluationResult`, scope stack types, `TraceVerbosity`, extend `FunctionSignature` with `handlesNull`, and update `FunctionImplementation` to accept `EvaluationContext`. These are the foundation types that all other evaluator tasks depend on.

---

## Scope

### In Scope

- `EvaluationContext` interface — sourceData, scopeStack, constants, externalSources, registry, options, evaluate callback
- `EvaluationResult` interface — value, diagnostics, trace entries
- `ScopeEntry` type — represents one level of the scope stack
- `EvaluatorTraceEntry` type — represents a single trace entry during evaluation (function name, args, result)
- `TraceVerbosity` type — `"functions" | "all"` (add to EngineOptions as optional `traceVerbosity` field)
- Extend `FunctionSignature` with `handlesNull?: boolean` field
- Update `FunctionImplementation` type to accept `EvaluationContext` instead of (or alongside) `ExecutionContext`
- Place `evaluate` callback on `EvaluationContext` — typed as a function that accepts an AstNode and EvaluationContext and returns EvaluationResult
- Place types in `src/engine/dsl/types.ts` (evaluator types alongside AST types) or a new `src/engine/dsl/evaluator-types.ts`

### Out of Scope

- Implementing evaluate() logic
- Implementing path resolution
- Writing tests (T-05 covers this)
- Modifying the registry class behavior
- Any function implementations

## Change Requirements

After this task:

- `EvaluationContext` is defined with:
  - `sourceData: unknown` — the root source document
  - `scopeStack: readonly ScopeEntry[]` — array context stack (LIFO, last element = top)
  - `constants: Readonly<Record<string, unknown>>` — mapping config constants
  - `externalSources: Readonly<Record<string, unknown>>` — runtime-injected externals
  - `registry: FunctionRegistry` — for function dispatch
  - `options: EngineOptions` — trace mode, maxRecursionDepth, traceVerbosity, etc.
  - `evaluate: (node: AstNode, context: EvaluationContext) => EvaluationResult` — re-entrant evaluation callback for array functions
- `EvaluationResult` is defined with:
  - `value: unknown` — the evaluated result
  - `diagnostics: Diagnostic[]` — accumulated warnings and errors
  - `trace?: EvaluatorTraceEntry[]` — evaluation steps when trace mode is on
- `ScopeEntry` is defined (likely `{ element: unknown }` or just `unknown`)
- `EvaluatorTraceEntry` is defined with: function name (if applicable), node type, input summary, output value
- `TraceVerbosity` type: `"functions" | "all"` — exported from options
- `EngineOptions` has a new optional `traceVerbosity?: TraceVerbosity` field (default: `"functions"`)
- `FunctionSignature` has a new optional `handlesNull?: boolean` field
- `FunctionImplementation` type updated to: `(args: readonly unknown[], context: EvaluationContext) => unknown`
  - This replaces the previous `ExecutionContext` parameter
  - The evaluator will populate `ExecutionContext` fields (currentItem, parentItem) on the `EvaluationContext` or pass them alongside — design choice: the evaluator populates a convenience `executionContext` field on `EvaluationContext` or the function reads from `EvaluationContext` directly
- All types are exported from the dsl/ barrel or types/ barrel as appropriate

## Notes

- The `FunctionImplementation` type change is the most impactful part of this task. Since no production functions exist, only test mocks need updating.
- The `evaluate` callback on `EvaluationContext` creates a circular type reference (EvaluationContext references itself via the evaluate function type). This is valid in TypeScript interface definitions.
- For `ExecutionContext` population: the evaluator will construct an `ExecutionContext`-shaped subset and make it available to implementations. Consider adding `currentItem` and `parentItem` directly to `EvaluationContext` as computed convenience fields, OR keeping `ExecutionContext` as a sub-object on `EvaluationContext`. The latter is cleaner.
- Scope stack uses array index convention: last element = top of stack (most recent push).
