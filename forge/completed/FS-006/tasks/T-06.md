## Summary

Implement the validation pass that compares each rule's inferred output type (from T-05's `inferType`) against the target field's declared type in the target schema. Emits E005 when there's a static type mismatch. Skips gracefully when type cannot be inferred.

---

## Scope

### In Scope

- Function `validateTypeCompatibility(rules, parsedAsts, sourceSchema, targetSchema, registry): Diagnostic[]`
- For each rule with a successfully parsed AST:
  1. Infer the expression's output type via `inferType(ast, context)`
  2. Look up the target field's declared type via `targetSchema.getTypeAtPath(rule.target)`
  3. Compare: if both are known and they don't match, emit E005
- Type compatibility rules:
  - Exact match → compatible
  - Either side is `undefined` (unknown) → skip (no diagnostic)
  - Either side is `'any'` → skip (no diagnostic)
  - `'null'` output → compatible with any target (null is valid for any nullable field)
  - `'array'` output targeting `'array'` → compatible
  - `'string'`/`'number'`/`'boolean'` targeting different scalar → E005
  - Scalar targeting `'array'` → E005
  - `'array'` targeting scalar → E005
- E005 diagnostic includes: expected type (from target), got type (from inference), ruleIndex, targetPath
- Unit tests

### Out of Scope

- Modifying inferType (T-05)
- Function argument type checking (T-07/within parse)
- Deep array element type checking (e.g., array-of-string vs array-of-number)
- Object shape validation (object output → object target is always OK)

## Change Requirements

The type compatibility validator:

1. Iterates over rules with valid ASTs
2. For each rule, calls `inferType(ast, { registry, sourceSchema })` to get the inferred output type
3. Calls `targetSchema.getTypeAtPath(rule.target)` to get the expected target type
4. Applies compatibility logic:
   - Both defined and non-'any' → compare
   - Match → no diagnostic
   - Mismatch → emit E005
5. Special case: rule declares `rule.type` — this could serve as a secondary signal if type inference returns undefined. If `rule.type` and target type mismatch, consider emitting E005 (use rule.type as the "got" type).

The message template for E005 in this context should be adapted to say something like: "Type mismatch: rule produces `{got}`, target field `{targetPath}` expects `{expected}`". This reuses the existing E005 code but with a validation-context message.

## Verification Requirements

Unit tests:
- Rule produces string, target expects string → no diagnostic
- Rule produces number, target expects string → E005
- Rule with cast("string") targeting string → no diagnostic
- Rule where type cannot be inferred → no diagnostic (graceful skip)
- Rule produces array (map()), target is array → no diagnostic
- Rule produces string, target is array → E005
- Rule produces null → no diagnostic (compatible with any target)
- Target type unknown (path not in schema) → no diagnostic
- Both types are 'any' → no diagnostic

TypeScript strict compilation passes.

## Notes

The existing E005 code has a message template geared toward function argument mismatches (`"Type mismatch in {function}: expected {expected}, got {actual} for argument {argName}"`). For the rule-level type compatibility check, create the diagnostic manually with a message appropriate to the validation context rather than using the template interpolation — or use the `format.ts` utility with different parameters. The code remains `KEYRA-E005` regardless.
