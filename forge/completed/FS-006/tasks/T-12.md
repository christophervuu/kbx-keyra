## Change Requirements

Add the following to `mapping-engine.md`:

**1. Validate Pipeline section** (after the Execution Pipeline section):
- Diagram showing the pass sequence
- Description of each pass (1-2 sentences each)
- How passes are independent (one failure doesn't block others)
- How the orchestrator aggregates results

**2. SchemaTree subsection:**
- Interface definition (hasPath, getTypeAtPath, getRequiredLeafPaths, isArrayPath)
- What SchemaTree represents (a simplified view of a schema for validation purposes)
- How it's built (JSON Schema adapter, XSD stub)
- Explicit boundary: "The validator uses schemas for static checks. It does not parse, store, version, or manage schemas."

**3. Type Inference subsection:**
- Best-effort model: infers from literals, function signatures, source schema types
- Returns undefined when uncertain → caller skips check → no false positives
- Not a full type system — a pragmatic static analysis tool

**4. Coverage Model subsection:**
- Definition: percentage of required target leaf fields with a corresponding rule
- Vacuous truth for schemas with no required fields
- Coverage is structural (rule presence), not semantic (rule correctness)

**5. Module structure update:**
- Add `validate/` directory with sub-modules:
  - `schema-tree.ts`
  - `source-paths.ts`
  - `target-paths.ts`

  - `array-context.ts`
  - `constants-externals.ts`

  - `ast-utils.ts`

## Notes

This task should be done after T-10 is complete so the documentation reflects the actual implementation. Review the final file structure to ensure the architecture doc matches reality.

The key architecture boundary to document clearly: the validator is a consumer of schema information, not an owner. Schemas are provided to it as input (raw JSON Schema or SchemaTree). The backend is responsible for ingesting, storing, and versioning schemas. The validator just reads the structure for static analysis.
