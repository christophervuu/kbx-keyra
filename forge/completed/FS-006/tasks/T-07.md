## Summary

Implement the validation pass that walks each rule's AST to verify array context constraints: `item()` must appear inside `map()`/`filter()`/`find()`, `parent()` must appear inside 2+ levels of array nesting, and `filter()`/`find()` conditions must have boolean-inferrable return types.

---

## Scope

### In Scope

- Function `validateArrayContext(rules, parsedAsts, registry, sourceSchema): Diagnostic[]`
- AST walking with context tracking:
  - Track "array depth" — increments when entering a `map()`, `filter()`, or `find()` node's second argument (the template/condition)
  - When encountering `item()`: if array depth < 1 → E010
  - When encountering `parent()`: if array depth < 2 → E013
- E017 checking:
  - For each `filter()` and `find()` call, infer the type of the second argument (condition expression)
  - If inferred type is known and is not `'boolean'` → E017
  - If type cannot be inferred → skip (no false positive)
- Diagnostics include ruleIndex, targetPath, expression
- Unit tests

### Out of Scope

- Modifying item()/parent() runtime behavior (FS-005)
- Deep array element type inference
- Checking that the first argument of map/filter/find is actually an array (that's a type check, partially covered by T-06)

## Change Requirements

Implement a recursive AST walker that tracks array context depth:

```
walkWithContext(node, depth):
  if node is FunctionCall:
    if node.name === 'item' and depth < 1:
      emit E010
    if node.name === 'parent' and depth < 2:
      emit E013
    if node.name in ['map', 'filter', 'find']:
      // First arg: walk at current depth
      walk(node.arguments[0], depth)
      // Second arg (template/condition): walk at depth + 1
      walk(node.arguments[1], depth + 1)
      // For filter/find: check condition type
      if node.name in ['filter', 'find'] and node.arguments[1]:
        condType = inferType(node.arguments[1], context)
        if condType is defined and condType !== 'boolean':
          emit E017
      return (don't recurse normally — we handled args manually)
    else:
      // Regular function: recurse into all arguments at same depth
      for arg in node.arguments:
        walk(arg, depth)
  if node is ObjectTemplate:
    for prop in node.properties:
      walk(prop.value, depth)
```

Key behaviors:
- `item()` at top level (depth 0) → E010
- `item()` inside map's template (depth 1) → valid
- `parent()` at depth 0 or 1 → E013
- `parent()` at depth 2+ → valid
- `filter(arr, item("name"))` where item("name") returns string → E017
- `filter(arr, gt(item("price"), 100))` where gt returns boolean → valid

## Verification Requirements

Unit tests:
- `item("x")` at top level → E010
- `map(source("items"), item("name"))` → no E010 (item inside map)
- `parent("x")` at top level → E013
- `map(source("items"), parent("x"))` → E013 (single level only)
- `map(source("depts"), map(item("emps"), parent("name")))` → no E013 (2 levels)
- `filter(source("items"), item("name"))` with name:string → E017
- `filter(source("items"), gt(item("price"), 100))` → no E017 (gt returns boolean)
- `find(source("items"), eq(item("id"), "x"))` → no E017 (eq returns boolean)
- Multiple violations in one expression → all reported
- Rule with null AST → skipped

TypeScript strict compilation passes.

## Notes

The walker must handle the fact that `map`/`filter`/`find` have their second argument in a "deeper" context. This mirrors how the evaluator uses lazyArgs — the second argument is evaluated per-element inside the scope-creating function. The validator needs to simulate this nesting statically.

Be careful with `ObjectTemplate` nodes inside map templates — properties should inherit the parent's depth context.
