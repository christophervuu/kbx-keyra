## Summary

Write comprehensive integration tests that exercise the full `validate()` pipeline end-to-end with realistic mapping configs and schemas. These tests verify that all validation passes work together correctly, diagnostics are properly aggregated, and edge cases are handled gracefully. Includes a performance benchmark test.

## Change Requirements

Create integration tests that call `validate()` through the public API with complete MappingConfig objects and JSON Schema source/target schemas.

Test categories:

**1. Happy path**
- Valid config with all paths, types, and references correct → valid=true, no errors, coverage=100%

**2. Path validation integration**
- Config with invalid source path → E030 with correct metadata
- Config with invalid target path → E031 with correct metadata
- Config with both source and target errors → both diagnostics present

**3. Type compatibility integration**
- Rule output type mismatches target → E005
- cast() corrects the mismatch → no E005
- Type inference failure → graceful skip (no false positive)

**4. Array context integration**
- item() outside map → E010
- parent() in single map → E013
- filter condition returning string → E017
- Correctly nested context → no errors

**5. Reference validation integration**
- Missing constant → E011
- Missing external → E012 (warning, valid=true)

**6. Coverage integration**
- Full coverage → 100%
- Partial coverage → correct percentage + unmapped list
- Empty rules → 0%

**7. Mixed scenarios**
- Config with errors + warnings → valid=false, all diagnostics present
- Config with only warnings → valid=true
- One rule has parse error, others valid → parse error reported, others fully validated

**8. Performance**
- Generate 500 rules with varied expressions
- Generate a schema with 1000+ fields
- Assert validate() completes in < 2000ms

## Notes

For the performance test, generate schemas programmatically (e.g., 50 top-level objects with 20 fields each = 1000 fields). Generate rules that reference various paths. The goal is to verify the < 2s target is achievable, not to do exhaustive performance testing.

Test fixtures should be defined inline or in a `fixtures/` subdirectory for readability. Avoid over-abstracting test helpers — tests should be readable and self-contained.
