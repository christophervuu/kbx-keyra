## Summary

Assess and implement mapping create-model/domain changes required to persist optional Business Context from Create Mapping, including adapter, backend, and persistence contract alignment where needed.

---

## Scope

### In Scope

- Audit current mapping metadata/config contracts for existing description/context field support.
- If absent, add optional mapping context/description field to create payload + storage model + read model.
- Keep change backward-compatible for existing mappings that lack this field.
- Ensure UI can send field without breaking existing adapters.

### Out of Scope

- Editing business context in Mapping Editor (unless already trivially surfaced).
- Non-create mapping metadata redesign.

## Change Requirements

- Business context field remains optional end-to-end.
- Existing create requests without business context remain valid.
- Field naming must be consistent across UI/domain/api/persistence layers.
- Preferred field is `businessContext?: string` on mapping config/metadata.
- Existing `description` may be used only if semantics are clearly equivalent and non-ambiguous.

---

## Verification Requirements

- Adapter/backend tests verifying create payload accepts and persists business context when provided.
- Tests verifying omitted field does not alter existing behavior.
- Typecheck/lint for touched backend + UI API modules.

## Acceptance Checks

- Optional Business Context can be stored when supported by model.
- Existing mappings and create flows remain backward compatible.
