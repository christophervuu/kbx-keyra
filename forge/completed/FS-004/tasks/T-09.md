## Summary

## Change Requirements

**add(a: number, b: number): number**
- Signature: 2 required number params, `handlesNull: false`
- Implementation: `(args[0] as number) + (args[1] as number)`

**subtract(a: number, b: number): number**
- Implementation: `(args[0] as number) - (args[1] as number)`

**multiply(a: number, b: number): number**
- Implementation: `(args[0] as number) * (args[1] as number)`

**divide(a: number, b: number): number**
- Implementation:
  ```
  if (args[1] === 0) → emit E050, return null
  return args[0] / args[1]
  ```

**round(value: number, decimals?: number): number**
- Signature: value (number, required), decimals (number, optional — default 0)
- Implementation: "Round half up" (not banker's rounding)
  - JavaScript's `Math.round` already uses round-half-up for positive numbers
  - For decimal places: `Math.round(value * 10^decimals) / 10^decimals`
  - Edge case: negative numbers with .5 — `Math.round(-2.5)` → `-2` in JS (rounds toward +∞), which IS round-half-up behavior
  - Use: `Math.round(value * factor) / factor` where `factor = 10 ** decimals`
- Default decimals: 0 (round to integer)

**abs(value: number): number**
- Implementation: `Math.abs(args[0] as number)`

## Blockers / Risks

- Floating-point precision: `0.1 + 0.2 !== 0.3` in JavaScript. The spec doesn't address this — accept IEEE 754 behavior as-is.
- `round` with `decimals` precision: `Math.round(3.145 * 100) / 100` may have floating-point issues. Consider using `Number(value.toFixed(decimals))` as an alternative, but note that `toFixed` uses banker's rounding in some engines. The safest approach: `Math.round(value * 10**decimals + Number.EPSILON) / 10**decimals` or a manual implementation.
- Actually for "round half up": `Math.round(3.145 * 100)` = `Math.round(314.5)` = `315`, so `315/100` = `3.15`. This works correctly. The issue only arises with floating-point representation (e.g., `1.005 * 100` = `100.49999...` not `100.5`). Document this limitation or implement a more robust rounding approach.

## Notes

- The "round half up" rule means: when the value is exactly at the midpoint (.5), round away from zero for positive numbers and toward zero for negative numbers. Actually, re-reading the spec: "round half up" specifically means .5 always rounds UP (toward +∞). So `round(2.5)` → `3` and `round(-2.5)` → `-2`.
- JavaScript's `Math.round` already implements round-half-up (rounds .5 toward +∞): `Math.round(2.5)` = `3`, `Math.round(-2.5)` = `-2`. So `Math.round` is correct for the default (no decimals) case.
- For the decimals case, multiply-round-divide is the standard approach. Be aware of floating-point edge cases but don't over-engineer — the DSL spec shows simple examples.
- `round` has an optional second parameter — ensure the signature declares it correctly with `required: false`.
