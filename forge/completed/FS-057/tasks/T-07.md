## Summary

Create an integration test suite that exercises all Lambda handlers end-to-end against DynamoDB Local and mocked S3. Tests verify complete CRUD flows, referential integrity, error envelopes, and response shape compliance. This validates that all acceptance examples work as specified in a realistic environment.

---

## Scope

### In Scope

- Test infrastructure setup: DynamoDB Local table creation (Projects, Mappings, SchemaMetadata, SchemaNodes, MappingVersions), S3 mock configuration
- Integration tests for complete project lifecycle (create → get → list → update → delete)
- Integration tests for complete mapping lifecycle including duplicate and version history
- Integration tests for schema lifecycle including inline ingestion and query
- Cross-entity tests: create project + mapping + schema, verify referential integrity on delete
- Error envelope shape validation across all error scenarios
- CORS header verification on all responses
- Test helper utilities for creating test fixtures (projects, mappings, schemas)

### Out of Scope

- LocalStack setup (use mock S3 library like `aws-sdk-client-mock` or in-memory S3 stub)
- Performance benchmarking
- Load testing
- CI/CD pipeline integration (just the test code)

## Notes

- Integration tests should invoke handlers directly (not through an HTTP server) to avoid requiring API Gateway setup. The handler functions accept `APIGatewayProxyEvent` and return `APIGatewayProxyResult` — tests construct events and parse responses.
- Consider using `@aws-sdk/client-dynamodb` mock capabilities or `jest.mock` for S3 while using real DynamoDB Local for persistence testing.
- Table schemas must match the spec's data model (Section 15 of product spec):
  - Projects: PK=`projectId`
  - Mappings: PK=`mappingId`, GSI `projectId-index` (PK=`projectId`)
  - SchemaMetadata: PK=`schemaId`
  - SchemaNodes: PK=`schemaId`, SK=`path`
  - MappingVersions: PK=`mappingId`, SK=`version` (Number)
