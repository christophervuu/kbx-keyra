## Summary

Implement the 6 Mapping CRUD Lambda handlers (create, get, update, delete, duplicate, list-by-project) under `src/lambda/mapping/`. Mapping configs are stored in S3 (referenced by `configS3Key`); metadata lives in DynamoDB. Update triggers version increment and status/coverage recomputation using the mapping engine's `validate()`. Update enforces optimistic concurrency — request `version` must match stored version or 409 is returned.

---

## Scope

### In Scope

- `src/lambda/mapping/create-mapping.ts` — POST /mappings
- `src/lambda/mapping/get-mapping.ts` — GET /mappings/:id
- `src/lambda/mapping/update-mapping.ts` — PUT /mappings/:id
- `src/lambda/mapping/delete-mapping.ts` — DELETE /mappings/:id
- `src/lambda/mapping/duplicate-mapping.ts` — POST /mappings/:id/duplicate
- `src/lambda/mapping/list-mappings.ts` — GET /projects/:projectId/mappings
- UUID generation for `mappingId` on create
- S3 storage for full `MappingConfig` JSON
- `configS3Key` pattern: `mappings/{mappingId}/config.json`
- Version auto-increment on update (`version: current + 1`)
- Optimistic concurrency on update: compare request body `version` against stored `version`; if mismatch → 409 CONFLICT
- `status` and `coverage` recomputation on create and update using engine `validate()`
- `ruleCount` derived from `rules.length`

### Out of Scope

- Mapping version history (T-04)
- Schema resolution for validation (validate against mapping config structure only, not schema content)
- Full conflict resolution beyond version mismatch rejection
- Cascading delete of versions when mapping is deleted (deferred)

## Change Requirements

- `create-mapping`: validate `projectId` and `name` required, generate UUID, set `version: 1`, compute `ruleCount`/`status`/`coverage`, write config to S3, write metadata to DynamoDB, return 201 with `MappingMetadata`
- `get-mapping`: read metadata from DynamoDB for `configS3Key`, fetch config from S3, return full `MappingConfig` (200 or 404)
- `update-mapping`: validate `projectId` and `name` exist in config, read existing metadata (404 if not found), compare request `version` against stored version (409 CONFLICT if mismatch), overwrite config in S3, increment `version`, recompute `ruleCount`/`status`/`coverage`, update DynamoDB, return 200 with updated `MappingMetadata`
- `delete-mapping`: read existing (404 if not found), delete from DynamoDB + delete S3 object, return 204
- `duplicate-mapping`: read source mapping (404 if not found), generate new UUID, set `name` from request body, reset `version: 1`, copy config to new S3 key, write new DynamoDB record, return 201 with new `MappingMetadata`
- `list-mappings`: query Mappings `projectId-index` for given projectId path param, return `MappingMetadata[]`
- Status derivation logic:
  - If `rules.length === 0`: `status: 'draft'`
  - If engine `validate()` returns errors: `status: 'has-errors'`
  - Otherwise: `status: 'ready'`
- Coverage derivation: percentage of target schema required fields that have a corresponding rule (if targetSchemaRef is present and resolvable; otherwise 0)

## Blockers / Risks

- Engine `validate()` requires a `MappingConfig` and may expect schema content for full validation. For Phase 1, validation without schema content should produce `status: 'draft'` or `'ready'` based on rule syntax only (no schema-path validation). This matches the engine's current permissive XSD behavior.
- S3 eventual consistency is mitigated by DynamoDB being the source of truth for metadata; S3 is only read on `getMapping`.

---

## Notes

- The `MappingConfig` stored in S3 includes `id` and `projectId` fields. These should be set/overwritten by the handler to ensure consistency with the DynamoDB record.
- `coverage` computation without resolved schema content should default to `0` — accurate coverage requires schema tree analysis which is available once schemas are ingested. Phase 1 can derive coverage as `ruleCount / targetSchemaFieldCount` if the target schema's `fieldCount` is available from SchemaMetadata.
- The `list-mappings` handler receives `projectId` as a path parameter from `/projects/:projectId/mappings`.
