## Summary

Implement the schema query handler at `POST /schemas/:id/query` that searches schema nodes by path and field name using DynamoDB `contains` filter expressions. Returns up to 50 `SchemaSearchResult` items matching the query string. This is the Phase 1 implementation — future phases will use OpenSearch for vector + keyword hybrid search.

---

## Scope

### In Scope

- `src/lambda/schema/query-schema-nodes.ts` — POST /schemas/:id/query
- Query SchemaNodes table by `schemaId` (PK) with filter expression matching `query` against `path` and `fieldName` (case-insensitive contains)
- Limit results to 50 items
- Return `SchemaSearchResult[]` shape: `{ path, fieldName, type, description? }`
- Return empty array when no matches (not an error)
- Validate request body has `query` string field

### Out of Scope

- OpenSearch integration (future)
- Relevance ranking / scoring
- Pagination / cursor-based results
- Embedding-based semantic search
- Full-text search beyond simple substring matching

## Change Requirements

- Handler receives `schemaId` from path parameter and `query` from request body
- Validate: `schemaId` path param present, request body has `query` field (string, non-empty)
- Query DynamoDB SchemaNodes table:
  - PK = `schemaId`
  - Filter expression: `contains(#path, :query) OR contains(#fieldName, :query)` (case-insensitive — normalize both stored values and query to lowercase for comparison, or use `contains` on lowercased projection)
- Map DynamoDB items to `SchemaSearchResult` shape
- Limit to 50 results (use `Limit` parameter or truncate after scan)
- Return 200 with `SchemaSearchResult[]`
- Return 404 if no schema metadata exists for the given `schemaId` (check SchemaMetadata table first)
- Return 200 with `[]` if schema exists but no nodes match

## Blockers / Risks

- DynamoDB `scan` with filter for `contains` is not efficient for large node sets (23k+ nodes per schema). For Phase 1 this is acceptable given low concurrency. A `Query` on PK with post-filter is better than a full table scan.
- Case-insensitive matching in DynamoDB requires either storing lowercased copies of fields or doing client-side filtering after query. Recommendation: query all nodes for the schema (bounded by schema size) and filter in handler code for Phase 1 simplicity.

---

## Notes

- The `SchemaSearchResult` type is: `{ path: string, fieldName: string, type: string, description?: string }`
- For large schemas (23k nodes), querying all nodes and filtering in-memory is acceptable for Phase 1 — DynamoDB can return up to 1MB per query, which accommodates typical node sizes (~100 bytes each = ~10k nodes per page). Use pagination tokens for very large schemas if needed.
- This handler depends on schema nodes having been written by the create-schema handler (T-05). If the schema has `status: 'ingesting'`, the query may return partial or no results — this is acceptable behavior.
- The `description` field on nodes is optional and may not be populated until AI-powered field description is implemented.
