## Summary

Implement the 4 Schema CRUD Lambda handlers (create, get, list, delete) under `src/lambda/schema/`. Schema content is stored in S3; metadata in DynamoDB. The create handler includes logic to determine whether ingestion is inline (small schemas, < 500 fields) or async (large schemas, status set to `'ingesting'`). Referential integrity is enforced on delete (fail if schema is referenced by any project).

---

## Scope

### In Scope

- `src/lambda/schema/create-schema.ts` — POST /schemas
- `src/lambda/schema/get-schema.ts` — GET /schemas/:id
- `src/lambda/schema/list-schemas.ts` — GET /schemas
- `src/lambda/schema/delete-schema.ts` — DELETE /schemas/:id
- UUID generation for `schemaId` on create
- Content stored in S3 at key `schemas/{schemaId}/content.json` (or `.xsd`)
- `fieldCount` computation for inline ingestion (quick parse of JSON Schema or XSD)
- Schema size threshold check: if estimated fields > 500, set `status: 'ingesting'` and skip inline parse
- Size estimation heuristic: for JSON Schema, count `"properties"` and `"items"` occurrences; for XSD, count `<xs:element` occurrences
- Inline ingestion: parse content, compute `fieldCount`, write schema nodes to SchemaNodes table, set `status: 'ready'`
- Async ingestion: write metadata with `status: 'ingesting'`, store raw content in S3, placeholder for Step Function kickoff (log intent, actual Step Function integration deferred)
- Delete checks all Projects for `schemaRefs` containing the `schemaId` — if any reference exists, return 409 CONFLICT

### Out of Scope

- Full schema tree node generation for SchemaNodes table (simplified: store basic path/type nodes for query support)
- OpenSearch indexing / embedding generation
- Step Function execution (stubbed — sets status and logs)
- `updateSchema` endpoint (not in Phase 1 API surface per product spec route map — schema content is immutable after create; metadata updates via re-upload)
- Schema sync operations (GitHub scope)

## Change Requirements

- `create-schema`:
  1. Validate required fields: `name`, `format`, `origin`, `content`
  2. Generate UUID `schemaId`
  3. Write content to S3
  4. Estimate field count from content
  5. If estimated fields ≤ 500: parse content, compute accurate `fieldCount`, generate basic schema nodes (path + fieldName + type), write nodes to SchemaNodes table, set `status: 'ready'`
  6. If estimated fields > 500: set `status: 'ingesting'`, `fieldCount: 0` (updated after async processing), log async kickoff intent
  7. Write metadata to SchemaMetadata table
  8. Return 201 with `SchemaMetadata`
- `get-schema`: read metadata from DynamoDB, read content from S3, return `SchemaDetail` (metadata + content) or 404
- `list-schemas`: scan SchemaMetadata table, return `SchemaMetadata[]`
- `delete-schema`:
  1. Read schema metadata (404 if not found)
  2. Scan Projects table, check each project's `schemaRefs` for the schemaId
  3. If any project references this schema: return 409 CONFLICT with project IDs in message
  4. Otherwise: delete metadata from DynamoDB, delete content from S3, delete nodes from SchemaNodes table (query by schemaId PK, batch delete), return 204
- Schema node generation (simplified Phase 1):
  - For JSON Schema: traverse `properties` recursively, generate nodes with `path`, `fieldName`, `type`
  - For XSD: extract `xs:element` entries with `name` and `type` attributes
  - Depth-first traversal, dot-notation paths

## Blockers / Risks

- Schema parsing for node generation is non-trivial. For Phase 1, a simplified parser that handles flat and 2-3 level nested JSON Schemas is sufficient. Deep XSD parsing can produce approximate results.
- The Step Function integration for large schemas is stubbed. The metadata will show `status: 'ingesting'` indefinitely until the async pipeline is implemented in a future spec.

## Notes

- The existing engine has `src/engine/validate/schema-tree.ts` but it currently uses a permissive stub for XSD. The schema node generation here is independent — it's about persistence, not runtime validation.
- `SchemaDetail` type has `content: Record<string, unknown> | string` — JSON Schema is stored as parsed JSON object, XSD is stored as raw string.
- The `scope` field (global/project) and `syncStatus` field should default to `'project'` and `'synced'` respectively if not provided in input.
- `inferred` defaults to `false` if not specified.
- `source` defaults to `{ type: 'upload' }` if not specified.
