## Summary

Implement the Mapping Editor sample payload picker experience, including default sample load, sample switching, and in-context add-sample flow. Ensure selected sample context synchronizes all field-level feedback surfaces without introducing full test-console behavior.

---

## Scope

### In Scope

- Header sample selector trigger and picker modal/popover.
- Default sample auto-selection on editor load.
- Sample switching state management and downstream recompute triggers.
- Add-sample dialog in picker with payload parse/submit/error handling.
- Synchronization of selected sample across grid muted output, source panel value, builder output, and sample-dependent validation.

### Out of Scope

- Full Test Lab test-case creation/execution UX.
- Schema Detail sample management redesign.
- Architecture documentation updates.

---

## Relevant Areas

- `ui/src/features/mappings/components/*` (sample picker/add-sample dialog)
- `ui/src/features/mappings/hooks/*` (sample context state)
- `ui/src/lib/api/http-adapter.ts`
- `ui/src/lib/types/domain.ts`

---

## Change Requirements

- Add-sample flow must validate payload format and surface actionable errors.
- Selected sample must be a single canonical editor context source of truth.
- If no sample available, editor must gracefully degrade with clear empty-state messaging.

---

## Verification Requirements

- Interaction tests for default sample load and switching behavior.
- Add-sample success/failure tests with API mocking.
- Consistency tests asserting all sample-driven surfaces update together.

---

## Acceptance Checks

- Editor auto-loads default sample where available (AE-03).
- Switching sample updates all field-feedback surfaces consistently (AE-04).
- Add-sample flow persists and immediately supports selection for editor context (AE-05).
- No full Test & Preview console surfaces are introduced in this task.

---

## Blockers / Risks

- Payload validation and normalization differences between JSON/XML modes may require shared parser utility reuse.
