## Summary

Write a comprehensive Vitest test suite covering every acceptance example from the spec, all error codes, edge cases, and position tracking accuracy. Tests exercise the public `parse()` API and validate both successful parsing (correct AST structure) and error production (correct diagnostic codes and messages). This is the verification gate for the entire parser implementation.

---

## Scope

### In Scope

- `tests/engine/dsl/parser.test.ts` — main test file covering the public `parse()` API
- `tests/engine/dsl/tokenizer.test.ts` — unit tests for the tokenizer in isolation
- Test groups:
  - **Literals**: every literal type (string, number with variants, boolean true/false, null)
  - **Function calls**: simple, nested (3+ levels), multiple arguments
  - **Object templates**: simple, with function call values, mixed literal and function-call values
  - **Escape sequences**: `\"`, `\\`, `\n`, `\t`, and invalid escape detection
  - **Error codes**:
    - E001: unclosed parenthesis, unclosed string, trailing comma, bare identifier, unexpected token, non-string object key, empty input, whitespace-only input
    - E002: unknown function name (with registry)
    - E003: too few arguments, too many arguments (with registry)
    - E004: nesting at limit (succeeds), nesting one beyond limit (fails)
  - **Position tracking**: verify start/end offsets for multi-token expressions (AE-14)
  - **Whitespace insensitivity**: extra spaces, tabs, newlines between tokens
  - **Edge cases**: single literal (no function call), deeply nested at exactly the limit, expression with only whitespace
  - **Determinism**: same input parsed twice produces identical results
- Registry setup for E002/E003 tests using `createRegistry()` and `registerFunction()`

### Out of Scope

- Modifying implementation code (T-01 through T-04)
- Integration tests with validate/execute (future specs)
- Performance benchmarking
