## Summary

Implement the lexer that converts a raw DSL expression string into an ordered array of `Token` objects. The tokenizer handles string literals with escape sequences, number literals (including negatives and decimals), boolean/null keywords, identifiers (function names), punctuation (parentheses, commas, braces, colons), and produces accurate position information for each token. Whitespace is consumed and discarded. Lexer-level errors (unterminated strings, invalid escape sequences, unexpected characters) produce `Diagnostic` objects with code `KEYRA-E001`.

## Change Requirements

After this task is complete:

- `src/engine/dsl/tokenizer.ts` exports a `tokenize(expression: string): TokenizeResult` function
- `TokenizeResult` is `{ tokens: Token[], diagnostics: Diagnostic[] }`
- The tokenizer processes the entire input string in a single pass (no backtracking)
- Whitespace (` `, `\t`, `\n`, `\r`) between tokens is silently consumed
- String literals:
  - Start and end with `"` (double quote)
  - Support escape sequences: `\"`, `\\`, `\n`, `\t`
  - Invalid escapes (e.g., `\q`) emit E001 with detail about the invalid sequence
  - Unterminated strings (no closing `"`) emit E001
  - The token `value` field contains the resolved string (escapes already processed)
- Number literals:
  - Match pattern: optional `-`, one or more digits, optional `.` followed by one or more digits
  - No leading zeros except for `0` and `0.x` forms
  - The token `value` field contains the raw string representation
- Keywords (`true`, `false`, `null`):
  - Recognized when an identifier matches these exact strings (case-sensitive)
  - Tokenized as `BooleanLiteral` or `NullLiteral`, not as `Identifier`
- Identifiers:
  - Match `[a-zA-Z]+` (letters only, per DSL spec §2.2)
  - Only produced when the matched text is not a keyword
- Punctuation tokens are single characters with obvious mapping
- Every token has accurate `start` (inclusive, 0-indexed) and `end` (exclusive) positions
- When an error is encountered, the tokenizer attempts to recover and continue tokenizing the rest of the input (best-effort for error reporting)
- EOF token: `{ type: "EOF", value: "", start: expression.length, end: expression.length }`
- All diagnostics include `expression` field set to the original input string

## Notes

- The tokenizer should be a single-pass scanner using a position cursor. A class-based approach (e.g., `class Tokenizer` with a `pos` field) or a closure-based approach both work — consistency with the codebase style is more important than the pattern choice.
- Negative numbers: the `-` sign is part of the number token only when it appears at the start of the expression or after `(`, `,`, `:`, `{` (i.e., in positions where a value is expected). Otherwise it would be an unexpected character. However, since the DSL has no subtraction operator, `-` can always be treated as part of a number literal for simplicity at the tokenizer level.
- The tokenizer should not validate whether identifiers are known function names — that's the parser/validator's job (T-03/T-04).
