## Summary

Create the `parse()` public API function that orchestrates tokenization, parsing, and optional registry-based validation. Wire up the function registry integration for E002 (unknown function name) and E003 (wrong argument count) validation. Export `parse`, `ParseResult`, `ParseOptions`, and all AST node types from `src/engine/index.ts`. Create the `src/engine/dsl/index.ts` barrel export.

---

## Scope

### In Scope

- `src/engine/dsl/index.ts` — barrel export for the DSL module: `parse()`, all types
- `parse(expression: string, options?: ParseOptions): ParseResult` implementation:
  1. Call `tokenize(expression)` to get token stream
  2. If tokenizer produced fatal errors and no usable tokens, return failure with diagnostics
  3. Call the internal parser with tokens and `options.maxDepth ?? 32`
  4. If parsing succeeds and `options.registry` is provided, walk the AST and validate:
     - Every `FunctionCallNode.name` exists in the registry (else emit E002)
     - Every `FunctionCallNode.arguments.length` matches the registered signature's arity (else emit E003)
  5. Combine all diagnostics (tokenizer + parser + validation) into the result
  6. Return `ParseResult` with `success` based on presence of error-severity diagnostics
- Registry validation logic:
  - E002: function name not found via `registry.hasFunction(name)`
  - E003: argument count doesn't match signature parameters (accounting for variadic params and optional params)
  - These produce diagnostics but do not prevent AST generation (syntactically valid parse still succeeds)
- Update `src/engine/index.ts` to export from `./dsl/index.js`:
  - `parse` function
  - `ParseResult`, `ParseOptions`, `AstNode`, and all individual node types
  - `Token`, `TokenType` (useful for consumers building tooling)
- `ParseResult.success` is `true` when no error-severity diagnostics exist (warnings are fine)

### Out of Scope

- Modifying the tokenizer or parser implementations (T-02 and T-03)
- Test files (T-05)
- Architecture documentation (T-06)

## Change Requirements

After this task is complete:

- `src/engine/dsl/index.ts` exists and exports `parse`, all types from `types.ts`, and re-exports what consumers need
- `parse(expression, options?)` function:
  - Accepts a raw expression string and optional `ParseOptions`
  - Returns a `ParseResult` object
  - Orchestrates: tokenize → parse → validate (if registry provided)
  - `ParseResult.success` is `false` if any diagnostic has severity `"error"`
  - `ParseResult.success` is `true` if no error diagnostics (warnings okay)
  - `ParseResult.ast` is the root AST node on success, `null` on failure
  - `ParseResult.diagnostics` always contains all collected diagnostics (errors + warnings)
- Registry validation (when `options.registry` is provided):
  - Walks the AST tree recursively
  - For each `FunctionCallNode`:
    - Check `registry.hasFunction(node.name)` — if false, emit E002 with `{ name: node.name }`
    - If function exists, check arity:
      - Get `signature.parameters` from the registered function
      - Count required params (where `required: true` and not `variadic`)
      - Determine max params (if last param is `variadic`, max is unlimited)
      - If `node.arguments.length < minRequired` or `node.arguments.length > maxAllowed`, emit E003
  - Registry validation diagnostics include position info from the `FunctionCallNode`
- `src/engine/index.ts` updated to include: `export * from './dsl/index.js';`
- After this task, `import { parse, ParseResult, AstNode } from '../engine/index.js'` works from test files

## Notes

- The arity check must account for:
  - Required parameters (`required: true`)
  - Optional parameters (`required: false`)
  - Variadic parameters (`variadic: true`) — allows unlimited additional arguments
  - Example: `concat(a: string, b: string, ...rest: string[])` — min 2, max unlimited
- When registry is not provided in options, E002 and E003 are simply not checked — no error, no warning. This allows parsing without a registry context (useful for testing or partial validation).
- The AST walk for validation should be a simple recursive function. It doesn't need to be a separate visitor pattern — the AST is small and the walk is straightforward.
- Drift note: `ParseResult.success` is implemented as parse-validity (`ast !== null`) rather than "no error diagnostics" to remain consistent with FS-002 AE-08 and AE-09, which require syntactically valid parses with E002/E003 diagnostics to still return success.
