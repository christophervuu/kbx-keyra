## Summary

Implement the recursive descent parser that consumes the token stream from the tokenizer and produces a typed AST. The parser handles all expression forms: literals (string, number, boolean, null), function calls with nested arguments, and object templates (`{ "key": expr, ... }`). It enforces a configurable recursion depth limit (default 32) and produces `Diagnostic` objects for syntax errors (E001) and depth violations (E004). Position information from tokens is propagated to AST nodes.

## Scope

### In Scope

- `src/engine/dsl/parser.ts` — new file with the internal parser implementation
- Recursive descent parsing of:
  - String literals → `StringLiteralNode`
  - Number literals → `NumberLiteralNode`
  - Boolean literals → `BooleanLiteralNode`
  - Null literals → `NullLiteralNode`
  - Function calls: `Identifier` `(` arguments `)` → `FunctionCallNode`
  - Object templates: `{` key-value pairs `}` → `ObjectTemplateNode`
- Argument parsing: comma-separated list of expressions, no trailing comma
- Object template property parsing: `StringLiteral` `:` expression
- Recursion depth tracking: increment on each recursive call to parse an expression, check against max depth
- E001 production for:
  - Unexpected token (e.g., `)` where expression expected)
  - Missing closing parenthesis
  - Missing closing brace
  - Trailing comma in argument list
  - Object template with non-string key
  - Bare identifier without following `(`
  - Any other structural violation
- E004 production when recursion depth exceeds configured maximum
- Position propagation: AST node `start` = first token's `start`, AST node `end` = last token's `end`
- `FunctionCallNode.end` includes the closing `)`
- `ObjectTemplateNode.end` includes the closing `}`
- The parser function signature: takes token array and max depth, returns AST or diagnostics

## Change Requirements

After this task is complete:

- `src/engine/dsl/parser.ts` exports a parser function (internal, not the public `parse()` API — that's T-04)
- The parser accepts: `{ tokens: Token[], maxDepth: number }` and returns: `{ ast: AstNode | null, diagnostics: Diagnostic[] }`
- Parsing logic follows recursive descent:
  - Entry: `parseExpression()` dispatches based on current token type
  - `StringLiteral` / `NumberLiteral` / `BooleanLiteral` / `NullLiteral` → produce corresponding AST node
  - `Identifier` → expect `(`, parse argument list, expect `)` → produce `FunctionCallNode`
  - `OpenBrace` → parse object template properties, expect `}` → produce `ObjectTemplateNode`
  - Anything else → E001
- Argument list parsing:
  - If next token is `)`, empty argument list
  - Otherwise, parse expression, then loop: if `,` consume and parse next expression; if `)` stop
  - If `,` followed by `)` → E001 (trailing comma)
- Object template parsing:
  - Properties are `StringLiteral` `:` expression
  - Separated by `,`
  - No trailing comma
  - Non-string key → E001
- Depth tracking:
  - A depth counter increments before each recursive `parseExpression()` call
  - If depth exceeds `maxDepth`, emit E004 and stop parsing
  - Depth resets appropriately (use a parameter or parser state)
- On first fatal error, the parser may stop and return diagnostics (no requirement for error recovery in the parser — the tokenizer handles lexer-level recovery)
- Position on AST nodes:
  - Literals: `start` = token.start, `end` = token.end
  - FunctionCall: `start` = identifier token.start, `end` = close paren token.end
  - ObjectTemplate: `start` = open brace token.start, `end` = close brace token.end
  - ObjectTemplateProperty: `start` = key token.start, `end` = value node.end

## Notes

- The parser does not need to implement error recovery (unlike the tokenizer). On the first fatal syntax error, it can stop and return the diagnostic. This keeps the parser simpler and is acceptable because DSL expressions are typically short.
- The depth counter should count expression nesting levels, not just function call depth. An object template nested inside a function call inside another function call counts as 3 levels.
- Consider implementing the parser as a class with cursor state (current token index) for clarity, or as a closure-based approach. Either is acceptable.
